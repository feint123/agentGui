# 2026-03-18 飞书渠道操作手册

日期：2026-03-18

适用范围：`agentGui` 首版飞书渠道接入

## 1. 当前状态

截至当前代码版本，飞书渠道能力分为两部分：

1. **已落地**
   - 飞书渠道配置模型
   - 飞书凭证存储
   - 飞书 `text` / `post` / `interactive` 消息发送 / 回复 HTTP 客户端
   - 飞书长连接 endpoint 获取与 WebSocket 事件源
   - protobuf `Frame` 编解码、分包重组、ACK 回写
   - `card` callback ACK 的 Base64 `data` 回包基础能力
   - 远程消息路由、去重、回执、远程执行编排框架
   - 设置页中的“渠道”配置入口
   - 设置页中的运行态连接状态、最近错误与握手摘要展示
2. **尚未落地**
   - 真实线上联调后的稳定性收口

这意味着：

1. 当前已经可以完成飞书凭证配置、发送端 API 接入和长连接事件接收主链路实现。
2. 当前代码层已经具备“飞书发消息 -> 长连接收事件 -> 进入本地渠道处理”的基础能力，但还没有经过完整线上稳定性验证。

如果你要的是“现在怎么配置和验证这套接入”，按本文执行即可。

## 2. 使用目标

本手册覆盖两类使用场景：

1. **产品配置**：在 `agentGui` 中完成飞书渠道的启用和凭证录入。
2. **开发验证**：确认飞书凭证、发送消息接口和回复消息接口可以被当前实现正确调用。

如果你要的是完整远程聊天闭环，还需要后续补上飞书长连接事件源实现。

## 3. 前置条件

开始前需要准备好以下条件：

1. 一台可运行 `agentGui` 的 macOS 设备。
2. 可正常打开并编译本项目的 Xcode 环境。
3. 一个飞书**自建应用机器人**。
4. 已拿到飞书应用的 `App ID` 和 `App Secret`。
5. 飞书应用已开启机器人能力。
6. 如果目标是和外部用户或飞书个人版用户单聊，应用还需要开启对外共享能力并按飞书发布要求生效。

## 4. 飞书后台准备

### 4.1 创建应用

在飞书开放平台完成以下操作：

1. 创建一个**自建应用**。
2. 为应用开启**机器人能力**。
3. 在应用凭证页面记录 `App ID` 和 `App Secret`。

不要使用群自定义机器人。群自定义机器人只适合 webhook 推送，不适合本项目的双向聊天接入。

### 4.2 配置权限

至少确认以下权限已申请并生效：

1. 接收机器人单聊消息相关权限。
2. 发送消息相关权限。
3. 如果需要群聊 `@机器人` 触发，还要额外开启群相关权限，例如 `im:message.group_at_msg` 或等效只读权限。

当前实现支持两类文本消息入口：

1. 机器人单聊中的文本消息。
2. 群聊里 `@机器人` 的文本消息。

仍然不要一开始就扩展到卡片、附件、群聊全量消息工作流。

### 4.3 确认可用范围

如果你是给具体用户发送消息，必须确认该用户在机器人可用范围内，否则飞书会返回无权限或不可达错误。

## 5. 在 agentGui 中配置飞书渠道

### 5.1 打开设置页

在 `agentGui` 中打开设置窗口，然后进入：

1. `连接`
2. `渠道`

其中飞书配置入口位于“渠道”页。

### 5.2 填写飞书配置

在“渠道”页中填写以下字段：

1. `启用飞书渠道`
2. `显示名称`
3. `App ID`
4. `App Secret`
5. `默认发送格式`

填写建议：

1. `显示名称` 可写成“飞书 Bot”或你的业务名称，主要用于本地展示。
2. `App ID` 和 `App Secret` 填飞书开放平台中的应用凭证。
3. `默认发送格式` 可选：`文本消息`、`Post 富文本`、`卡片消息`。
4. 其中卡片消息首版是静态展示卡片，不包含按钮交互。
5. 填完后点击 `保存渠道设置`。

### 5.3 保存后的行为

保存成功后：

1. 飞书凭证会进入独立凭证存储。
2. 启用状态和显示名称会保存到渠道绑定模型。
3. 普通 `AppSettings` 不会保存飞书明文密钥。

如果看到连接状态显示为“已配置”，表示本地已成功读取到飞书凭证字段。

## 6. 当前版本如何使用

### 6.1 当前可以使用的能力

当前代码已经具备以下可用能力：

1. 本地保存飞书渠道配置。
2. 在运行时创建 `LiveFeishuClient`。
3. 使用 `App ID` / `App Secret` 获取 `tenant_access_token`。
4. 向飞书会话发送文本消息、Post 富文本消息和静态卡片消息。
5. 基于 `message_id` 调用飞书回复消息接口，并沿用当前设置的默认发送格式。

### 6.2 当前仍需谨慎看待的能力

以下能力虽然已有实现基础，但仍属于首轮协议接入，使用时应按开发态能力理解：

1. 自动重连和断线恢复。
2. 卡片回调、链接预览等非 `event` 类型消息的上层业务处理。
3. 真实生产环境下的大规模长时间稳定运行。

原因是当前长连接层虽然已实现，并已包含首版重连，但还没有完成完整线上联调和非文本协议能力收口。

## 7. 开发验证步骤

如果你当前的目标是验证“飞书发送客户端实现是否正确”，建议按下面顺序验证。

### 7.1 验证本地配置能否保存

操作步骤：

1. 打开 `agentGui` 设置页。
2. 进入“渠道”。
3. 录入飞书 `App ID` / `App Secret`。
4. 打开“启用飞书渠道”。
5. 点击保存。

验证结果：

1. 页面状态显示“已配置”。
2. 再次打开设置时字段仍可被加载。

### 7.2 验证客户端单元测试

当前最直接的开发验证方式是跑定向测试：

```bash
xcodebuild -project agentGui.xcodeproj -scheme agentGui -destination 'platform=macOS' test \
  -only-testing:agentGuiTests/FeishuClientLiveTests
```

这组测试验证：

1. 会先调用飞书 `tenant_access_token` 接口。
2. 再调用飞书发送消息接口，并根据 `msg_type` 发送 `text` / `post` / `interactive`。
3. 如果提供 `replyToMessageID`，会改走回复消息接口。
4. 在 token 未过期时会复用缓存 token。

注意：当前仓库测试目标里仍有无关的全局 type-check 问题，可能导致这条命令最终被其他测试文件的编译问题打断。若出现这种情况，不代表 `LiveFeishuClient` 本身有问题。

### 7.3 验证飞书 API 配置是否正确

你可以基于当前实现重点确认以下几点：

1. `App ID` / `App Secret` 是否正确。
2. 机器人能力是否已开启。
3. 可用范围是否包含目标用户。
4. 是否具备发送消息权限。
5. 如果要回复消息，待回复的 `message_id` 是否真实存在。

## 8. 推荐的联调顺序

如果你准备继续把飞书能力做成完整闭环，推荐联调顺序如下：

1. 先完成本地设置页配置保存。
2. 再验证 `tenant_access_token` 获取成功。
3. 再分别验证发送普通文本消息、Post 富文本消息和卡片消息。
4. 再验证回复已有飞书消息，并确认默认发送格式在 reply 路径同样生效。
5. 最后用真实飞书应用做线上联调，验证长连接入站和回执稳定性。

不要跳过前面几步直接做完整闭环，否则定位问题时会把“凭证错误”“权限错误”“事件源错误”“会话路由错误”混在一起。

## 9. 常见问题排查

### 9.1 保存后仍显示“未配置”

优先检查：

1. `App ID` 是否为空。
2. `App Secret` 是否为空。
3. 保存操作后是否真的执行了持久化。

### 9.2 发送消息失败

优先检查：

1. 飞书机器人能力是否开启。
2. 目标用户是否在机器人可用范围内。
3. `tenant_access_token` 是否获取成功。
4. 消息内容是否包含飞书审查会拦截的敏感信息。
5. 是否触发了消息频率限制。

### 9.3 回复消息失败

优先检查：

1. `replyToMessageID` 是否为真实存在的飞书 `message_id`。
2. 目标消息是否已经撤回。
3. 机器人对该消息是否可见。
4. 当前聊天场景是否支持该类型回复。

## 10. 已知限制

当前版本存在以下明确限制：

1. 只支持三种出站消息格式：`text`、`post`、静态 `interactive` 卡片。
2. 不支持群聊 `@机器人`。
3. 不支持卡片按钮交互、附件、图片、文件上传。
4. 不支持消息编辑同步。
5. 不支持 `card` / callback 的上层业务处理。
6. 不支持通过产品 UI 直接发起“测试发送一条飞书消息”的交互入口。
7. `handshake-status` 的协议语义已经在 API 文档中明确，当前设置页也会显示最近一次握手摘要，但仍缺少真实线上联调后的稳定性结论。

## 11. 下一步建议

如果你的目标是尽快真正用起来，建议按优先级继续：

1. 补齐 `card` / callback 回包，以及更完整的握手错误可观测性。
2. 增加一个开发态“发送测试消息”入口，便于不走完整远程编排也能验证发送 API。
3. 在设置页补充飞书连接状态、最近 token 获取结果和最近一次错误信息。
4. 做真实飞书应用下的端到端“飞书发消息 -> agentGui 自动回复”联调。

## 12. 结论

这套飞书接入当前已经具备“配置 + 发消息 + 回复消息 + 长连接收事件 + ACK”的基础能力，但还不是生产级完成态。

如果你现在要做的是：

1. **准备飞书凭证和本地配置**：本文已经够用。
2. **验证发送端 API**：本文已经够用。
3. **真正开始远程聊天**：建议先做一次真实飞书环境联调，再投入日常使用。
