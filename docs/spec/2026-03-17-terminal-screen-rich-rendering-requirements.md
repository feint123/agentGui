# 终端屏幕高保真渲染需求说明

日期：2026-03-17

关联对象：`TerminalScreenView`、`TerminalScreenSnapshot`、`TerminalScreenModel`、`TerminalSurfaceProjector`、`TerminalVTParser`、终端任务详情页与后续终端交互 UI

参考产品：iTerm2、Ghostty、VS Code Integrated Terminal、Warp

## 1. 背景

当前项目已经具备终端运行时、VT 解析器与 screen model 的基础能力，终端任务也可以在详情页中展示“终端屏幕”。但目前的 UI 展示仍停留在纯文本层：

- `TerminalScreenSnapshot` 只暴露 `plainTextLines`、buffer 类型、cursor 与尺寸。
- `TerminalScreenView` 只把 `plainTextLines` 拼接成单色 `Text`。
- ANSI SGR 样式、前景色、背景色、反显、下划线、粗体、dim、光标样式、行内焦点等信息没有进入视图模型。
- 备用屏、重绘式 TUI、进度条、彩色日志虽然在运行时可能被部分解析，但最终 UI 没有高保真呈现。

这会导致一个直接问题：终端运行时“理解了部分屏幕”，但用户看到的仍像降级后的 transcript，而不是接近主流终端产品的真实终端画面。对于 `git diff --color`、`ls --color`、脚手架向导、包管理器安装器、交互式选择器等场景，当前体验明显低于用户对现代终端的预期。

因此，需要把终端屏幕能力从“纯文本快照展示”升级为“面向主流终端产品对齐的高保真渲染层”，让 agentGui 内的终端屏幕能够稳定呈现常见 ANSI 样式、颜色与 TUI 状态。

## 2. 目标

本次需求目标如下：

1. 终端屏幕渲染效果需要向主流产品看齐，至少在常见 CLI/TUI 场景下达到“信息不丢失、颜色不失真、状态可识别”。
2. 支持终端常见颜色体系与文本样式，包括 8/16 色、256 色、true color，以及粗体、斜体、下划线、反显、删除线、dim 等常用 SGR 属性。
3. 支持主屏与备用屏的正确显示，避免全屏 TUI、向导式 CLI 与普通 shell 输出相互污染。
4. 支持对现代 CLI 重绘场景的稳定展示，包括光标移动、行擦除、局部重绘、进度条、焦点项高亮与选择态。
5. UI 层要有明确降级策略：即便某些控制序列尚未完全支持，也不能退化成难以阅读的乱码或竖排字符。
6. 需求定义必须可直接指导后续的数据模型扩展、SwiftUI 渲染方案与测试基线建设。

## 3. 不在本次范围

- 不在本次需求中实现完整的终端模拟器产品能力，例如多标签页、SSH 会话管理、分屏、会话配置中心。
- 不在本次需求中追求 xterm/DEC 所有私有控制序列的完整兼容。
- 不在本次需求中实现鼠标上报、图像协议、sixel、kitty graphics protocol 等高级扩展。
- 不要求首版达到 `vim`、`tmux`、`htop` 这类强全屏应用的完全交互等价，但至少要保证画面不崩坏、主备屏切换正确、内容可读。
- 不把“终端屏幕高保真渲染”与“agent 自动理解全部交互语义”绑定为同一交付物；前者优先，后者可建立在前者之上继续演进。

## 4. 对标基准

### 4.1 iTerm2 / Ghostty 对标点

对齐方向：渲染保真度。

至少应参考以下能力：

- ANSI 样式与颜色准确映射，不把彩色输出降级成单色文本。
- 备用屏内容独立显示，退出后恢复主屏上下文。
- 宽字符、emoji、box drawing 字符、powerline 符号尽量保持布局稳定。
- 光标位置与焦点区域不漂移。

### 4.2 VS Code Integrated Terminal 对标点

对齐方向：应用内终端嵌入体验。

至少应参考以下能力：

- 在应用 UI 中稳定滚动、选择、复制终端内容。
- 窗口尺寸变化后画面保持可读，不出现大面积布局撕裂。
- 对链接、路径、命令输出块具备后续增强空间，但首版可不全部交付。

### 4.3 Warp 对标点

对齐方向：现代可读性与状态表达。

至少应参考以下能力：

- 对焦点项、选中项、危险提示、成功/失败态有清晰视觉层级。
- 对交互式向导、安装器、选择器的当前状态要一眼可读。
- 在高保真渲染和产品内统一视觉之间取得平衡，而不是简单把原始终端像素搬进应用。

## 5. 产品原则

### 5.1 保真优先于美化

终端 UI 的第一原则是正确表达终端状态，而不是为了统一设计语言去抹平 ANSI 差异。应用可在边框、背景、容器层统一风格，但字符颜色、选中态、反显与焦点态不能被任意重写。

### 5.2 屏幕模型优先于 transcript

渲染必须建立在 screen model 上，而不是继续基于纯文本 transcript 做样式猜测。任何高亮、光标、选中态、备用屏等视觉信息，都必须来自结构化屏幕快照。

### 5.3 降级可读优先于功能空白

当部分控制序列、配色或属性无法完整支持时，UI 仍需保证内容顺序正确、文本可读、关键状态可识别，不允许出现整块空白、字符重叠、明显错位或无法判断当前焦点。

### 5.4 交互态与静态输出统一呈现

彩色日志、命令结果、进度输出、交互式选择器、备用屏应用应共用同一终端渲染体系，而不是分别维护多个简化视图。

### 5.5 UI 视图不直接解释 VT 细节

SwiftUI 视图层只消费结构化渲染模型，不直接解析 ANSI/VT 字节流。VT 解析、screen state 维护、样式投影与 UI 渲染必须分层。

## 6. 当前缺口

基于现状，当前至少存在以下差距：

1. 数据模型缺少 cell 级别样式信息，无法渲染颜色和属性。
2. 视图层使用单个 `Text` 拼接纯文本，无法表达局部样式。
3. 终端重绘场景只能展示最后的字符结果，无法稳定呈现焦点、选中和反显。
4. 备用屏虽然已有 buffer 概念，但 UI 没有真正区分其视觉与状态。
5. 缺少终端主题映射策略，无法支持浅色/深色主题下的可靠显示。
6. 缺少面向真实 CLI/TUI 样例的渲染回归基线。

## 7. 功能需求

### 功能点 1：终端富样式屏幕数据模型

需要把当前 `TerminalScreenSnapshot` 从纯文本快照扩展为可渲染快照。至少应包含：

- cell 级文本内容
- display width 信息
- 前景色
- 背景色
- 文本属性集合
- continuation cell 标记
- 行级属性与截断信息
- 当前活动 buffer 类型
- cursor 信息

颜色模型至少应支持：

- 默认前景/背景
- 8 色
- bright 8 色
- 256 色索引
- true color RGB

文本属性至少应支持：

- bold
- italic
- underline
- strikethrough
- dim
- inverse
- blink
- hidden

要求：

- 样式信息必须从 VT/SGR 语义保留下来，而不是在 UI 层二次猜测。
- 对未知或未支持属性应保留可扩展位，避免未来再次修改主数据结构。

### 功能点 2：高保真终端渲染视图

`TerminalScreenView` 需要升级为富文本/富单元格渲染视图，而不是单色 `Text`。

要求：

- 支持一行内混合多种颜色与样式。
- 支持背景色块、反显与焦点行高亮。
- 支持 box drawing、分隔线、树形字符等终端常见布局元素。
- 支持终端最小可用字号与行高控制，默认观感应接近主流终端产品，而不是 SwiftUI 默认文本组件。
- 支持滚动、文本选择、复制。
- 支持在大输出场景下的按需渲染或分块渲染，避免一次性拼接巨型富文本造成卡顿。

实现层不强制限定为单一技术方案，但渲染结果必须满足上述可视要求。可以基于 `AttributedString`、`TextRenderer`、`NSTextView` 包装层，或自定义 cell grid 渲染器实现。

### 功能点 3：主屏与备用屏正确切换

要求：

- 终端详情页需要明确展示当前活动 buffer，并正确渲染 primary / alternate screen。
- 进入备用屏时，不应把旧的 shell transcript 与当前 TUI 画面混在一起。
- 退出备用屏后，应恢复主屏内容，而不是保留过期的全屏 UI 残影。
- 备用屏状态下如内容不可完整交互，至少也要保持画面可读与光标位置合理。

验收重点：

- `less`
- 现代脚手架选择器
- 带局部重绘的安装器/确认框

这些场景中不出现“屏幕内容串台”或明显画面污染。

### 功能点 4：光标、焦点与重绘行为可见

要求：

- 支持光标位置渲染，至少区分“可见/隐藏”和当前位置。
- 支持常见 cursor shape 的模型承载，首版 UI 可不全部精确复刻，但不能丢失状态。
- 支持局部擦除、回车覆盖、行内重写、进度条刷新、spinner 更新等动态行为。
- 当 TUI 通过反显、背景色或符号表达焦点项时，终端视图应能呈现出“当前焦点在哪里”。

验收口径：

- 同一个交互式选择器在连续刷新过程中，当前焦点项不会随机消失或跳行。
- 进度条与 spinner 不会在 UI 中膨胀成大量历史垃圾字符。

### 功能点 5：主题与配色映射

要求：

- 终端颜色不能直接绑定应用通用文字颜色，必须有独立终端主题映射层。
- 至少支持“跟随系统外观”的浅色/深色终端主题。
- 默认主题需要保证常见 ANSI 配色在深浅主题下都具备足够对比度。
- 对默认前景/背景色、选中文本、反显文本、光标色要有独立定义。
- 后续应保留用户自定义终端主题的扩展能力，但首版可不交付完整主题编辑器。

### 功能点 6：复杂字符与布局稳定性

要求：

- 正确处理中日韩宽字符。
- 正确处理 emoji 与双宽字符的占位。
- 正确处理 combining characters 与 continuation cell，避免后续字符覆盖错位。
- 对 ASCII line drawing、Unicode box drawing、powerline 字符等要保持基本对齐。
- 终端尺寸变化后应能重新投影，不出现大面积错列。

说明：

- 这一项是接近主流终端体验的基础要求，不能只以英文 CLI 作为验收样本。

### 功能点 7：回退与容错策略

要求：

- 遇到未支持的控制序列时，终端视图应尽量忽略该序列并保持其余内容可用。
- 遇到不合法 ANSI 片段或截断输出时，不得导致整个终端区域空白或崩溃。
- 当富样式快照不可用时，可降级到纯文本快照，但必须明确是降级渲染，而不是静默丢失样式。
- UI 需要有可观测信息，便于后续排查是 parser、screen model 还是 renderer 出现问题。

### 功能点 8：终端场景验收样本库

本能力必须建立明确的样本基线，至少覆盖以下类别：

1. 纯 ANSI 彩色输出：`ls --color`、`grep --color`、`git diff --color`
2. 日志类输出：测试失败、构建日志、warning/error/highlight 混合输出
3. 进度类输出：progress bar、spinner、百分比更新
4. 向导类输出：Clack、Prompts、Inquirer 风格单选/多选/确认界面
5. 备用屏类输出：`less` 或等价全屏阅读场景
6. 宽字符输出：中英文混排、emoji、box drawing

要求：

- 每类样本都要有稳定的渲染对照结果。
- 样本应可直接作为单元测试、快照测试或 UI 基线测试输入。

## 8. 架构要求

推荐沿用当前终端三层拆分方向，并补齐渲染层：

1. `TerminalVTParser`：解析 VT/ANSI 字节流与控制序列
2. `TerminalScreenModel`：维护主屏、备用屏、cursor、cell 属性与屏幕状态
3. `TerminalSurfaceProjector`：把 screen state 投影为交互语义与 UI 友好快照
4. `TerminalScreenRendererModel`：为 UI 提供稳定的渲染段落/行/片段结构
5. `TerminalScreenView`：负责最终视觉呈现

要求：

- `TerminalScreenView` 不直接处理原始 ANSI 文本。
- `TerminalScreenSnapshot` 与面向 UI 的 render model 可以分层，避免 runtime 模型直接耦合具体视图实现。
- 交互语义提取与视觉渲染共享同一份底层 screen state，不能各自维护一套不一致的文本推断逻辑。

## 9. 性能与质量要求

### 9.1 性能

- 常规终端输出刷新不应造成明显掉帧或主线程卡顿。
- 中等规模屏幕快照更新应具备增量刷新能力，避免每 300ms 重建整块巨型富文本。
- 长时间运行任务的滚动与刷新应稳定，不随输出累计而线性劣化。

### 9.2 稳定性

- 不允许因为单条异常控制序列导致终端详情页崩溃。
- 不允许因为输出包含彩色日志或宽字符而破坏整块布局。
- 不允许因为切换备用屏而丢失主屏历史。

### 9.3 可测试性

- parser、screen model、projector、renderer 至少分别具备单元测试。
- 关键终端样本需有快照测试或 UI 基线测试。
- 需要保留调试输出或中间快照导出能力，便于定位渲染偏差。

## 10. 分阶段交付建议

### Phase 1：可用的高保真基础渲染

范围：

- cell 级样式模型
- ANSI 颜色与常见文本属性
- 富文本终端视图
- 主屏/备用屏分离
- 常见彩色日志与向导式选择器正确显示

交付标准：

- 绝大多数常见 CLI 输出不再降级为单色纯文本。
- 用户能明显感知到与主流终端产品接近的颜色和状态表达。

### Phase 2：复杂 TUI 稳定性增强

范围：

- 更完整的宽字符与 combining 处理
- 光标渲染增强
- 尺寸变化重排
- 更多备用屏程序适配

### Phase 3：产品化增强

范围：

- 终端主题切换
- 链接/path 检测
- 搜索、高亮查找
- 更完整的交互控件可视反馈

## 11. 验收标准

以下条件同时满足，视为本需求达成：

1. 在终端详情页中，彩色日志、`git diff --color`、常见脚手架选择器能够以接近真实终端的方式展示颜色与焦点状态。
2. 终端视图不再仅由单一 `Text` 拼接纯文本实现，而是具备局部样式渲染能力。
3. 备用屏场景下，UI 不出现主屏与全屏 TUI 内容串台。
4. 中日韩宽字符与 emoji 不会大面积错列。
5. 未支持控制序列不会导致终端内容整体不可读。
6. 至少具备一组可重复运行的终端渲染样本测试，用于后续回归。

## 12. 结论

这项需求的本质，不是“把终端文字染上颜色”，而是把 agentGui 内的终端从“文本回放面板”升级为“真正可用的终端屏幕”。

只有当 screen model、样式模型和渲染视图形成完整链路后，终端 UI 才能真正参考主流产品，并支撑后续的交互理解、用户接管、终端调试和更复杂的 TUI 兼容性建设。
