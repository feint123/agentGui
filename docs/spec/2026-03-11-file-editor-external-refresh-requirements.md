# 文件编辑器外部变更自动刷新需求说明

日期：2026-03-11

关联对象：`FileEditorView`、`WorkspaceState`、`WorkspacePanelView`、块编辑器、macOS UI Tests

## 1. 背景

当前工作区支持打开并编辑文件，但当已经打开的文件被外部程序修改后，编辑器刷新依赖工作区目录树的变更通知间接触发。这种路径存在两个问题：

- 刷新职责绑定在文件树，而不是绑定在当前打开文件本身
- 外部程序直接改写当前文件时，编辑器刷新稳定性不足

这会导致用户在 agentGui 中看到的内容可能落后于磁盘真实状态，尤其是在配合外部格式化器、脚本、生成器或其他编辑器共同工作时。

## 2. 目标

让中间编辑器对“当前打开文件被外部程序修改”这个事件具备稳定、自动、可预期的刷新能力。

## 3. 不在本次范围

- 不处理多人协作冲突合并
- 不实现复杂的三方 diff 合并界面
- 不改变现有手动保存模型
- 不为未打开文件增加额外预览刷新提示

## 4. 功能点

### 功能点 1：当前打开文件独立监听

需求：

- 编辑器在打开文件后，必须建立针对该文件的独立监听，而不是仅依赖工作区目录树刷新
- 当用户切换到其他文件或关闭文件时，旧监听必须立即停止
- 文件监听应能覆盖常见外部写入方式，包括直接改写和原子替换

### 功能点 2：外部变更自动重载

需求：

- 当前打开文件发生外部修改后，编辑器应自动重新读取磁盘内容
- 自动刷新应作用于文本文件；图片和 PDF 也应沿用同一外部变更通知路径重新加载
- 刷新后，编辑器内部的基线内容快照必须同步更新，避免误判为脏状态

### 功能点 3：未保存修改保护

需求：

- 如果当前编辑器存在未保存本地修改，外部变更不能直接覆盖当前文本
- 发生冲突时，界面需要给出明确交互，至少提供“保留当前编辑”和“重新加载磁盘版本”两个动作
- 该场景下允许暂不自动刷新，但后续策略必须保留扩展空间，例如冲突提示或手动恢复入口

### 功能点 4：测试模式下的稳定可观测性

需求：

- UI 自动化必须能够稳定观测编辑器当前内容是否已经刷新
- 仅在 UI test 模式下，可以暴露低干扰的内容镜像，供 XCTest 做断言
- 正常用户模式下不应引入额外噪声或视觉干扰

## 5. 交互要求

- 用户打开文件后，不需要手动重新点选文件即可看到外部更新
- 有未保存修改时，界面不得悄悄覆盖用户当前编辑内容
- 自动刷新行为必须足够安静，不应额外弹窗打断正常阅读流程

## 6. 验收标准

- 已打开文本文件被外部程序修改后，编辑器内容会自动更新
- 切换文件时，旧文件监听不再继续触发当前编辑器刷新
- 本地存在未保存修改时，外部变更不会覆盖当前编辑内容
- 本地存在未保存修改且磁盘再次变化时，界面会显示冲突提示，并允许用户选择保留当前编辑或重新加载
- UI 自动化可以稳定复现“打开文件、外部写入、编辑器刷新”完整流程

## 7. 测试覆盖

- 单元测试：`agentGuiTests/OpenFileRefreshMonitorTests`
- UI 测试：`agentGuiUITests/FileEditorExternalRefreshUITests`

## 8. 优先级

- P0：当前打开文件独立监听、无未保存修改时自动重载
- P1：未保存修改场景的冲突提示与恢复交互
- P2：更细粒度的外部变更来源展示与手动回溯能力
