# StoryProjectInspectorView 标签页化与差异化展示需求说明

日期：2026-03-10

关联对象：`StoryProjectInspectorView`

替代关系：本文档替代 [docs/spec/2026-03-09-story-project-inspector-display-requirements.md](/Volumes/T7/文稿/Projects/agentGui/docs/spec/2026-03-09-story-project-inspector-display-requirements.md) 中“继续使用单页分组展开”的主方案。后续实现计划应以本文为准重新整理。

## 1. 背景

当前 `StoryProjectInspectorView` 已经从轻量摘要页补全为一张较完整的只读总览页，能够覆盖：

- 项目概览
- 章节与场景
- 角色档案
- 地点档案
- 世界规则
- 时间线事件
- 伏笔追踪
- 连续性问题
- 风格档案

但当前界面仍然采用“单页长滚动 + 所有模块连续堆叠”的组织方式。这会带来几个持续性问题：

- 当项目数据变多时，页面长度迅速失控，浏览成本高
- 不同类型的创作记忆共用近似相同的卡片布局，缺少语义区分
- 用户切换阅读目标时需要反复滚动，而不是在明确的信息域之间切换
- 时间线、伏笔、连续性问题这类天然具有强结构特征的数据，没有获得最适合它们的可视化方式

Story memory 本身已经是按领域对象建模的，因此 Inspector 也应从“通用详情页”升级为“按创作记忆域组织的浏览工作台”。

## 2. 问题定义

当前版本的核心问题不是数据不够，而是信息架构过于扁平。

具体表现如下：

### 2.1 单页模式不适合中大型项目

随着章节、角色、事件、伏笔数量增长，单页滚动会让用户越来越难回到目标信息块。Inspector 会逐渐退化为“能展示很多信息，但不方便使用”的页面。

### 2.2 不同记忆域没有形成稳定心智模型

用户在阅读角色信息、检查时间线、追踪伏笔、查看风格约束时，实际上是在做四种不同任务。但当前界面把它们作为一种浏览动作处理，缺少明确入口。

### 2.3 视觉语言没有体现数据类型差异

时间线事件更适合纵向时间轴；伏笔更适合按状态跟踪；连续性问题更适合风险清单；风格档案更适合分析面板；角色更适合卡片网格。当前全部采用近似的堆叠卡片，导致信息优势被削弱。

## 3. 目标

本次需求目标如下：

- 将 `StoryProjectInspectorView` 改造为基于 Tab 标签页的项目浏览界面
- 让不同创作记忆类型拥有独立入口，而不是依赖单页滚动定位
- 针对不同记忆类型采用最适合的布局和内容组织方式
- 保持基础视觉风格与当前应用一致，不引入割裂的全新设计体系
- 继续保持 Inspector 的定位为“浏览与检查”，而不是完整编辑器

目标效果：

- 用户可以先判断“我要看哪类记忆”，再进入对应标签页
- 每个标签页首屏都能立即呈现该类记忆最重要的信息
- 大型项目中，导航成本明显低于现有单页模式
- Inspector 具备更清晰的产品层级，可支撑后续逐步加入筛选、联动和只读分析功能

## 4. 方案对比

### 方案 A：继续优化单页长滚动

做法：保留当前结构，只增加折叠、锚点和更强摘要。

优点：实现成本最低，改动最小。

缺点：

- 无法从根本上解决信息域切换成本
- 仍然把所有记忆类型挤在同一阅读平面
- 难以为时间线、伏笔、连续性问题提供真正差异化布局

### 方案 B：改成 Tab 标签页 + 每页专用布局

做法：以创作记忆类型作为一级导航，将当前单页内容拆到多个标签页中；每个标签页根据其内容结构采用最适合的布局。

优点：

- 最符合 story memory 的领域划分
- 导航路径清晰，可扩展性强
- 能自然承载差异化视觉与交互

缺点：

- 需要重新组织快照与视图结构
- 需要定义标签页之间的联动规则和默认落点

### 方案 C：改成侧边二级导航工作台

做法：在项目详情内部再做一层侧边导航，类似小型 CMS 或 IDE inspector。

优点：信息管理能力最强，适合超大型项目。

缺点：

- 交互复杂度偏高
- 对当前应用的轻量风格侵入较大
- 当前阶段容易过度设计

### 推荐方案

推荐采用方案 B。

原因：

- 它是解决当前问题的最短路径
- 它能保留现有应用的简洁气质，同时显著提升结构清晰度
- 它为后续新增只读筛选、实体跳转、跨域联动保留了空间

## 5. 产品定位与范围

### 5.1 本期范围

本期需要完成：

- Inspector 一级信息架构改为 Tab 标签页
- 定义每个标签页的内容范围、首屏重点与布局方式
- 统一基础风格规范
- 定义标签页计数、空态、筛选、跨页跳转等交互规则
- 定义验收标准，便于后续实现

### 5.2 非本期范围

本期不包含：

- 完整 CRUD 编辑器
- 拖拽排序和批量修改
- 复杂图谱视图或关系图编辑
- 自动生成更多 story memory 数据
- 重新设计项目列表页

说明：如果后续要增加编辑功能，应建立在本次标签页结构稳定之后，而不是反过来把编辑需求塞进当前改造里。

## 6. 总体信息架构

Inspector 应采用“三层结构”：

1. 顶部固定项目概览区
2. 一级 Tab 标签条
3. 当前标签页内容区

### 6.1 顶部固定项目概览区

该区域在所有标签页顶部保持一致，用于提供全局上下文，不随标签页切换而变化。

必须展示：

- 项目标题
- 一句话梗概或简介摘要
- 当前会话绑定状态
- 归档状态
- 创建时间 / 更新时间
- 关键统计摘要
- 绑定到当前会话 / 解除绑定按钮

要求：

- 概览区不能过高，避免每个标签页首屏都被头部占满
- 统计摘要应保留当前应用已经使用的 metric card 风格
- 标签页切换后，概览区内容不重新布局或闪动

### 6.2 一级 Tab 标签定义

推荐使用以下标签页：

- 总览
- 结构
- 角色
- 地点
- 规则
- 时间线
- 伏笔
- 连续性
- 风格

说明：

- “结构”承载章节与场景
- “地点”与“规则”拆开，而不是继续合并为一个世界观大区，原因是两类数据的浏览任务不同
- “总览”保留为默认标签页，用于快速感知项目成熟度和风险状态

### 6.3 标签页通用规则

所有标签页都应遵循以下规则：

- 标签标题显示名称与数量徽标
- 当对应数据为空时，标签页仍保留入口，不因数据为空而隐藏
- 标签切换不应触发项目级数据重载或明显卡顿
- 每个标签页应有自己独立的滚动区域
- 返回某个标签页时，优先保留该标签页此前的滚动位置

## 7. 各标签页需求

### 7.1 总览 Tab

定位：项目级仪表盘，不负责承载全部详情。

推荐布局：摘要面板 + 风险面板 + 最近结构概览。

应展示：

- 核心统计卡片
- 最近更新时间与归档状态
- 最近 3 个章节摘要
- 最近 3 个时间线事件
- 未解决伏笔摘要
- 开放连续性问题摘要
- 风格摘要一句话

布局要求：

- 首屏必须能看出项目规模、风险点和当前上下文状态
- 总览只展示摘要，不承载完整长列表
- 每个摘要模块都应提供“查看全部”跳转到对应 Tab

适合的视觉表达：

- 仪表盘式卡片编排
- 风险项用更强的状态色强调
- 章节和事件摘要使用紧凑列表而非大卡片

### 7.2 结构 Tab

定位：查看章节与场景的层级结构，是写作推进时最常访问的主工作页之一。

推荐布局：左侧章节导航列表 + 右侧章节详情与场景卡片；在窄宽度下退化为单列分组列表。

应展示：

- 章节号、标题、锁定状态、场景数
- 章节摘要、大纲、语气指令
- 场景序号、标题、摘要、POV、地点、出场角色
- 场景正文状态
- 是否关联上一场景 / 时间线事件

布局要求：

- 章节导航区应支持快速跳转，而不是要求用户继续长滚动
- 当前选中章节应有明确高亮
- 场景卡片应突出顺序和层级感
- “有正文 / 暂无正文”这类状态应使用轻量 badge，而不是藏在正文说明里

适合的视觉表达：

- 大纲浏览器风格
- 分层清晰的章节-场景结构
- 强化目录感，而不是纯卡片堆叠

### 7.3 角色 Tab

定位：角色资料浏览面板，应优先支持人物对比与快速扫描。

推荐布局：可自适应卡片网格，支持按名称、最近出场章节、角色弧线阶段排序。

应展示：

- 角色名
- 简介
- 性格特征
- 目标
- 说话风格
- 角色弧线阶段
- 最近出场章节
- 最近已知位置
- 关系摘要

布局要求：

- 首屏优先展示更多角色卡片，而不是超高卡片
- 关系摘要应在视觉上弱于人物主体信息
- 未完善角色应明确标记“档案未完善”
- 若角色较多，应支持顶部快速筛选或本页搜索

适合的视觉表达：

- 人物卡组风格
- 信息重心放在角色识别与状态把握
- 避免把角色页做成纯文本详情页

### 7.4 地点 Tab

定位：地点与空间信息浏览页，应强调场景感与容器属性。

推荐布局：地点卡片网格或双列列表，每张卡片突出地点摘要、特征、常驻角色和相关规则。

应展示：

- 地点名称
- 简介
- 特征标签
- 相关规则
- 常驻角色

布局要求：

- 地点卡片要比角色卡片更强调“环境信息”和“关联约束”
- 相关规则和常驻角色用标签块表达，方便快速扫读
- 当地点数据很少时，也应保持完整布局，不退化成一行文本

适合的视觉表达：

- 轻地图索引风格
- 更强调空间特征，而不是人物维度

### 7.5 规则 Tab

定位：世界规则与约束系统的浏览页，应支持按分类检查设定一致性。

推荐布局：按分类分组的规则列表，支持组内展开；分类可固定排序。

应展示：

- 规则标题
- 分类
- 详细说明
- 适用范围
- 例外
- 建立章节
- 相关实体
- 可变策略

布局要求：

- 分类是一级阅读入口，不能退化成普通字段
- 规则卡片应突出“约束”语义，而不是展示为普通描述卡
- 可变策略和建立章节应始终可见
- 例外条件需视觉区分，避免和主规则混读

适合的视觉表达：

- 规则手册风格
- 分类分组 + 约束标签 + 例外区块

### 7.6 时间线 Tab

定位：事件时间序浏览页，应成为时间一致性检查的核心入口。

推荐布局：纵向时间轴，而不是普通卡片列表。

应展示：

- 章节 / 场景定位
- 事件标题
- 事件摘要
- 参与者
- 地点
- 时间标记
- 事件类型
- 关联伏笔
- 是否已解决
- 是否已被覆盖

布局要求：

- 必须有明显的时间线视觉锚点，例如竖轴、节点、章节断点
- 章节和场景定位应易于扫描
- 已被覆盖或已解决的事件需要弱化显示
- 当前有效事件应比历史失效事件更突出

适合的视觉表达：

- 时间轴式浏览
- 节点状态明确
- 让“顺序”和“状态”同时可读

### 7.7 伏笔 Tab

定位：伏笔跟踪页，应优先服务“未解决项检查”和“回收进度判断”。

推荐布局：按状态分组的泳道式或分段列表式布局，默认把未解决状态放在最前。

应展示：

- 伏笔标签
- 伏笔详情
- 引入章节
- 解决章节
- 当前状态
- 关联事件数量

布局要求：

- `open`、`planned`、`resolved` 等状态必须形成清晰分组
- 未解决项必须拥有最高视觉优先级
- 解决章节为空时应明确显示“未解决”
- 关联事件数量应帮助用户判断该伏笔是否已进入推进链路

适合的视觉表达：

- 任务跟踪板风格
- 强调状态推进感，而不是静态资料展示

### 7.8 连续性 Tab

定位：风险与矛盾检查页，应优先支持问题扫描、排序和处理判断。

推荐布局：按处理状态分组的风险清单，组内按严重级别优先排序。

应展示：

- 问题类型
- 严重级别
- 所属章节
- 所属场景
- 问题详情
- 处理状态

布局要求：

- `open` 问题必须显示在最前
- `critical` 与 `warning` 的视觉区分要明显，但不能刺眼
- 这是最接近“问题中心”的页面，信息组织应比其它页更紧凑、更偏列表化
- 后续可扩展筛选，但本期至少要预留筛选条位置

适合的视觉表达：

- 风险清单 / 审核收件箱风格
- 强调优先级与处理状态

### 7.9 风格 Tab

定位：项目级文风与写作约束浏览页，应偏分析面板而不是普通档案卡。

推荐布局：顶部量化指标区 + 下方双栏内容区。

应展示：

- 叙事声音
- 作者偏好
- 平均句长
- 对话占比
- 意象密度
- 示例段落
- 反模式

布局要求：

- 量化指标应集中放在顶部，便于快速判断风格特征
- 示例段落与反模式应明显分区
- 示例段落更适合较宽的阅读列，反模式更适合标签或警示块

适合的视觉表达：

- 轻分析面板风格
- 指标 + 样本 + 禁忌项并置

## 8. 统一视觉与交互规范

### 8.1 基础风格必须继承当前应用

必须继承当前应用已有的基础设计语言：

- 材质感卡片
- 圆角矩形容器
- 轻量 badge / chip
- 清晰但不过度装饰的层级排版
- macOS 原生分栏和导航气质

不应出现：

- 与主应用割裂的全新配色体系
- 过重的插画化背景
- 为了区别标签页而给每一页套一整套完全不同的主题皮肤

### 8.2 差异化应建立在“布局与层级”而不是“换皮”上

不同标签页的差异化重点应是：

- 信息结构不同
- 列表方式不同
- 重点字段不同
- 状态表达不同

而不是：

- 每个标签页都采用完全不同颜色系统
- 每个标签页都重新发明卡片样式

### 8.3 标签条设计要求

标签条应满足：

- 位于概览区下方、内容区上方
- 支持图标 + 文本 + 数量徽标
- 当前选中态明确
- 当窗口宽度不足时允许水平滚动，不强行压缩到不可读

不建议采用：

- iOS 风格底部 Tab Bar
- 过于粗重的浏览器式标签页外观

## 9. 标签页联动与导航规则

### 9.1 摘要跳转

总览页中的摘要模块应支持跳转到对应标签页，例如：

- 点击“未解决伏笔”跳到“伏笔”
- 点击“开放连续性问题”跳到“连续性”
- 点击“最近章节”跳到“结构”

### 9.2 实体联动

跨标签页的实体信息应支持轻量联动。示例：

- 时间线事件中的地点 chip 可跳到“地点”并定位到对应卡片
- 场景中的 POV 或角色 chip 可跳到“角色”
- 地点卡片中的相关规则 chip 可跳到“规则”

本期不要求实现复杂深链接协议，但应在结构上预留该能力。

### 9.3 默认落点

默认进入 Inspector 时：

- 若是第一次进入某项目，默认打开“总览”
- 若用户在本次应用运行期间已经切换过该项目的标签页，则优先恢复上次所停留的标签页

## 10. 空态、筛选与排序规则

### 10.1 空态

每个标签页都必须有针对本域的空态文案与图标，不允许只显示大片空白。

空态原则：

- 文案应说明“当前还没有什么数据”
- 如果适合，可提示用户应从什么写作动作开始积累这类记忆

### 10.2 筛选

本期推荐至少预留以下筛选能力的位置：

- 角色：名称 / 弧线阶段 / 最近出场
- 规则：分类
- 时间线：章节
- 伏笔：状态
- 连续性：状态 / 严重级别

若实现成本受限，本期可先只做排序与分组，不做完整筛选逻辑，但界面结构应允许后续无痛加入。

### 10.3 排序

应维持下列默认排序：

- 结构：章节升序，场景升序
- 角色：名称升序
- 地点：名称升序
- 规则：分类优先，标题次序
- 时间线：章节升序，场景升序
- 伏笔：状态优先，章节次序
- 连续性：状态优先，严重级别优先，再按章节 / 场景排序

## 11. 非功能要求

### 11.1 性能

- 中等规模项目下切换标签页应保持流畅，不出现明显阻塞
- 长列表必须使用惰性容器，不应一次性渲染全部复杂卡片
- 标签切换不应重复执行高成本数据整形逻辑

### 11.2 可维护性

- 视图层不应直接承担 JSON 解码和业务映射
- 应按标签页拆分展示层结构或快照子模型，避免单个 view 文件继续膨胀
- 新结构要支持后续给某个标签页单独增强，而不牵动全部页面

### 11.3 可测试性

- 展示快照需要能按标签页维度被测试
- 排序、分组、空值兜底和状态映射应有独立测试覆盖
- 至少应能验证标签数量、默认标签、摘要跳转和主要排序规则

## 12. 验收标准

满足以下条件，视为本期需求达成：

### P0 验收

- Inspector 已改为顶部概览区 + Tab 标签页结构
- 不同创作记忆类型拥有独立标签页入口
- 每个标签页都采用与其内容结构匹配的布局，而不是简单复制同一种卡片堆叠
- 基础视觉风格与当前应用保持一致
- 总览可跳转到其它标签页
- 各标签页空态、排序、数量徽标齐备

### P1 验收

- 标签页间基础联动可用
- 主要标签页具备轻量筛选或至少预留明确筛选区
- 标签切换可记住用户最近浏览位置或最近标签

### 失败判定

出现以下情况之一，应判定为未满足需求：

- 只是把原单页内容机械拆成多个 Tab，但各页仍然使用同一种布局
- 标签页视觉与主应用明显割裂
- 时间线、伏笔、连续性问题仍按普通列表思路弱化处理
- 为了做标签页而牺牲概览效率，导致用户进入后无法快速获得项目全局状态

## 13. 后续实现建议

建议后续实现按以下顺序推进：

1. 先重构展示快照与标签页信息架构
2. 再完成总览、结构、角色三个高频页
3. 再补齐地点、规则、时间线、伏笔、连续性、风格页
4. 最后补摘要跳转、实体联动和轻量筛选
