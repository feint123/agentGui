# StoryProjectInspectorView 数据展示补全需求说明

日期：2026-03-09

## 1. 背景

当前 StoryProjectInspectorView 已经能展示项目标题、简介、风格摘要、基础统计、角色名称、章节标题、未解决伏笔、连续性问题和时间线标题。

但从现有数据模型看，`WritingProject` 及其关联实体已经承载了更完整的故事信息，包括：

- 角色详情
- 章节摘要与章节锁定状态
- 场景结构
- 地点档案
- 世界规则
- 时间线事件详情
- 伏笔详情与状态
- 连续性问题严重级别与处理状态
- 风格档案量化信息

因此当前 Inspector 的问题不是“没有数据”，而是“已有数据没有被完整展示出来”，导致项目详情页更像一个轻量摘要，而不是一个可用于浏览项目 canon 的总览面板。

## 2. 目标

补齐 StoryProjectInspectorView 的数据展示，使其成为故事项目的只读总览页。

目标效果：

- 用户可以在一个页面中查看项目级核心信息和各类结构化故事数据
- 用户可以快速判断当前项目的结构完整度、风险点和上下文状态
- 展示逻辑覆盖当前已存在的 SwiftData 模型字段，不再只停留在标题级摘要
- 保持当前页面定位为“浏览和检查”，不扩展为编辑器

## 3. 范围

### 3.1 本期范围

本期仅设计和实现数据展示增强，包含：

- 展示分组补全
- 展示字段补全
- 排序与分层规则
- 空态与折叠态规则
- 统计信息补全

### 3.2 非本期范围

本期明确不包含：

- 新增项目编辑能力
- 新增角色、章节、地点、规则、伏笔、时间线的编辑入口
- 内联修改、删除、拖拽排序、批量操作
- 在 Inspector 中录入新数据
- 将 Inspector 改造成富编辑工作台

说明：当前页面已存在“绑定到当前会话 / 解除绑定”操作，本需求不扩展该能力，也不围绕该能力新增更多交互。

## 4. 现状差距

### 4.1 当前已展示的数据

当前 Inspector 已展示：

- 项目标题
- 项目简介
- 风格摘要文本
- 角色数量、章节数量、未解决伏笔数量、连续性问题数量
- 角色名称列表
- 章节标题列表
- 未解决伏笔标签列表
- 连续性问题文本列表
- 时间线标题列表

### 4.2 当前未充分展示的数据

以下数据已存在于模型中，但当前未展示或仅展示了标题级摘要：

- 项目元数据：创建时间、更新时间、归档状态
- 角色详情：简介、特征、目标、说话风格、角色弧线阶段、最近出场章节、当前位置、关系图
- 章节详情：大纲、摘要、语气指令、锁定状态、场景数量
- 场景详情：场次、POV、地点、出场角色、摘要、内容长度、与上一场景/时间线事件的关联
- 地点详情：简介、特征、相关规则、常驻角色
- 世界规则详情：分类、适用范围、例外、建立章节、相关实体、可变策略
- 时间线详情：摘要、参与者、地点、时间标记、事件类型、关联伏笔、是否已解决、是否被后续事件覆盖
- 伏笔详情：详情、引入章节、解决章节、状态、关联事件
- 连续性问题详情：严重级别、发生章节、发生场次、处理状态
- 风格详情：叙事声音、作者偏好、平均句长、对话占比、意象密度、示例段落、反模式

## 5. 展示方案选择

### 方案 A：继续维持单页摘要式布局，仅增加更多列表

优点：实现最简单，改动最少。

缺点：信息密度失控，长文本和复杂结构会混在一起，用户难以定位不同类型的数据。

### 方案 B：按信息域分组展示，组内支持折叠与摘要

优点：最符合 Inspector 的定位，既能在首屏保留概览，也能逐层展开查看细节；适合项目规模持续增长。

缺点：需要重新定义快照结构和分组顺序。

### 方案 C：改为多标签页或侧边二级导航

优点：适合超大型项目，单次阅读负担较低。

缺点：交互复杂度更高，超出当前 Inspector 的轻量定位。

### 推荐方案

推荐采用方案 B。

原因：

- 当前页面本质上是详情检查面板，不是独立工作台
- 数据域较多，但大多数内容天然适合按模块分组
- 方案 B 可以在不引入复杂导航的前提下，显著提升信息覆盖度和可读性

## 6. 信息架构要求

Inspector 应按以下顺序展示信息。

### 6.1 项目概览

项目概览区应展示：

- 项目标题
- 项目简介
- 项目风格摘要
- 创建时间
- 最近更新时间
- 是否已归档
- 当前会话是否绑定该项目

展示要求：

- 归档状态应以明确标签显示，而不是隐含在文案中
- 时间字段应使用统一的本地化日期时间格式
- 项目简介为空时显示占位文本，不留空白区域

### 6.2 全局统计区

统计区应至少包含以下卡片：

- 角色数
- 章节数
- 场景总数
- 地点数
- 世界规则数
- 时间线事件数
- 未解决伏笔数
- 开放连续性问题数

展示要求：

- 统计卡片优先展示总量与风险量，不展示重复指标
- 当对应模块为空时，统计值仍需显示为 0

### 6.3 章节与场景结构

章节模块应成为核心主区块之一。

每个章节应展示：

- 章节号
- 标题
- 摘要
- 大纲
- 语气指令
- 是否锁定
- 场景数量

每个章节下应展示其场景列表。每个场景应展示：

- 场次编号
- 标题
- 摘要
- POV 角色
- 地点
- 出场角色
- 是否关联时间线事件
- 是否存在上一场景引用
- 正文长度摘要，例如字数或“有无正文”

展示要求：

- 章节按 `number` 升序展示
- 场景按 `sceneIndex` 升序展示
- 长摘要和长大纲默认截断，支持展开阅读，但不进入编辑态
- 锁定章节应有明确视觉标记

### 6.4 角色档案

角色模块应从“名称标签云”升级为“角色摘要卡片列表”。

每个角色应展示：

- 名称
- 简介
- 性格特征
- 目标
- 说话风格
- 角色弧线阶段
- 最近出场章节
- 最近已知位置
- 关系图摘要

展示要求：

- 默认按名称排序
- `traitsJSON`、`goalsJSON`、`relationshipMapJSON` 需解码后展示，而不是原样输出 JSON
- 当某个角色只有名称、没有补充资料时，应展示为“基础档案未完善”而不是空白卡片

### 6.5 地点档案

地点模块应展示：

- 地点名称
- 简介
- 特征
- 相关规则
- 常驻角色

展示要求：

- 默认按名称排序
- `traitsJSON`、`relatedRulesJSON`、`occupantNamesJSON` 需解码后展示为标签或文本列表
- 无地点数据时，模块仍保留并显示空态

### 6.6 世界规则

世界规则模块应展示：

- 规则标题
- 分类
- 详细说明
- 适用范围
- 例外
- 建立章节
- 相关实体
- 可变策略

展示要求：

- 优先按 `category` 分组，再按 `title` 排序
- `exceptionsJSON` 与 `relatedEntitiesJSON` 需解码展示
- `mutablePolicy` 应使用易懂标签表达，例如“不可变 / 可变 / 条件可变”

### 6.7 时间线事件

时间线模块不应只展示标题，应展示完整事件摘要。

每个事件应展示：

- 所属章节与场次
- 标题
- 摘要
- 参与者
- 地点
- 时间标记
- 事件类型
- 关联伏笔标签
- 是否已解决
- 是否被后续事件覆盖

展示要求：

- 按 `chapterNumber`、`sceneIndex` 升序排序
- `participantNamesJSON` 与 `foreshadowTagsJSON` 需解码后展示
- 若 `supersededByEventId` 非空，应明确标注该事件已被后续事件覆盖

### 6.8 伏笔追踪

伏笔模块应从“仅展示未解决标签”升级为“按状态分组的伏笔列表”。

每个伏笔应展示：

- 标签
- 详情
- 引入章节
- 解决章节
- 当前状态
- 关联事件数量或摘要

展示要求：

- 默认按状态分组展示：`open`、`planned`、`payoff`、`resolved`
- 同一状态内按 `introducedInChapter` 升序排序
- 首屏优先展开未解决状态组，已解决组默认可折叠
- `relatedEventIdsJSON` 应转换成可读的数量或引用摘要，不能直接显示 JSON 字符串

### 6.9 连续性问题

连续性问题模块应展示：

- 问题类型
- 严重级别
- 发生章节
- 发生场次
- 问题详情
- 处理状态

展示要求：

- 默认按处理状态分组，开放问题优先
- 开放问题组内按严重级别优先级排序，再按章节倒序排序
- 严重级别需要明确视觉区分，至少区分高风险与普通警告

### 6.10 风格档案

风格模块应从“单行摘要”升级为完整风格卡片。

应展示：

- 作者偏好
- 叙事声音
- 平均句长
- 对话占比
- 意象密度
- 示例段落
- 反模式

展示要求：

- 百分比或比例字段使用统一格式显示
- `samplePassagesJSON` 与 `antiPatternsJSON` 需解码后展示为列表
- 若风格档案不存在，则显示明确空态说明

## 7. 通用展示规则

### 7.1 只读原则

本页面新增内容必须遵守只读原则。

允许的交互：

- 展开/收起
- 模块内滚动
- 只读标签过滤或分组切换
- 跳转到相关只读详情页（如果后续已有）

不允许的交互：

- 新建
- 编辑
- 删除
- 排序写回
- 直接修改状态

### 7.2 空态规则

每个模块都应定义空态，避免模块直接消失。

空态文案需要表达两层信息：

- 当前没有该类数据
- 这不是错误，而是项目尚未补齐该维度

### 7.3 排序规则

若模块未指定排序，默认采用：

- 结构化对象优先按业务字段排序，而不是按插入顺序
- 名称类对象按名称升序
- 风险类对象按风险优先级排序

### 7.4 长文本规则

对于简介、摘要、大纲、规则说明、场景内容摘要等长文本：

- 默认显示摘要或截断版本
- 提供只读展开能力
- 展开后仍保持在当前 Inspector 内浏览，不切换到编辑态

### 7.5 JSON 字段展示规则

以下 JSON 存储字段不能原样展示：

- `traitsJSON`
- `goalsJSON`
- `relationshipMapJSON`
- `characterNamesJSON`
- `participantNamesJSON`
- `foreshadowTagsJSON`
- `exceptionsJSON`
- `relatedEntitiesJSON`
- `relatedRulesJSON`
- `occupantNamesJSON`
- `samplePassagesJSON`
- `antiPatternsJSON`
- `relatedEventIdsJSON`

这些字段必须在展示层解码为结构化文本、标签组或摘要列表。

### 7.6 可读性规则

为了避免 Inspector 变成长页面噪音区，必须遵守：

- 首屏先展示项目概览和全局统计
- 重信息模块采用分组卡片或折叠段落
- 列表项优先展示“识别信息 + 状态 + 一句摘要”
- 长内容默认收起

## 8. 数据聚合要求

当前 `StoryProjectInspectorSnapshot` 只覆盖少量摘要字段，不足以支撑完整 Inspector。

因此需要补充一个更完整的展示快照，负责：

- 在 View 外部完成排序和分组
- 统一解码 JSON 字段
- 提供适合 UI 直接消费的只读展示模型
- 对空值、异常值、缺失值做统一降级处理

要求：

- View 层不直接拼接复杂业务字符串
- View 层不直接处理 JSON 解码
- 展示排序规则集中在 presentation 层维护

## 9. 验收标准

满足以下条件可视为需求达成：

1. Inspector 能覆盖 `WritingProject` 及其关联实体的主要业务字段，而不是只显示标题级摘要。
2. 用户可以在 Inspector 中查看章节、场景、角色、地点、世界规则、时间线、伏笔、连续性问题和风格档案的主要信息。
3. 所有 JSON 存储字段都被转换为可读展示内容，不出现原始 JSON 字符串泄漏到 UI。
4. 页面中新增内容不提供任何编辑、删除、录入入口。
5. 空数据项目不会出现大片空白，仍能稳定展示各模块空态。
6. 排序规则稳定，章节、场景、时间线、风险项的显示顺序符合用户理解。
7. 在数据量较大的项目中，页面仍能通过折叠、摘要和分组保持可读性。

## 10. 交付建议

建议按两步实施：

第一步：补齐展示快照与展示模型。

- 扩展 `StoryProjectPresentation`
- 将所有关联模型映射为 Inspector 专用只读结构
- 统一处理排序、状态分组和 JSON 解码

第二步：重构 Inspector UI 分组。

- 保留现有顶部概览卡片
- 将现有简单列表升级为按模块分组的详情卡片
- 对章节、伏笔、连续性问题等高信息密度模块增加默认折叠策略

这样可以在不引入编辑功能的前提下，把 StoryProjectInspectorView 提升为完整的项目浏览面板。
