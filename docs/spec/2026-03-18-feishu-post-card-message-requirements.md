# 2026-03-18 飞书 Post / 卡片消息支持需求文档

日期：2026-03-18

适用范围：agentGui 飞书渠道出站消息能力增强

## 1. 背景

当前 agentGui 的飞书渠道已经具备以下能力：

1. 飞书凭证配置与保存。
2. 基于 `tenant_access_token` 的消息发送与回复。
3. 飞书长连接入站事件接收与文本消息归一化。
4. 设置页中的飞书启用状态、显示名称、凭证和运行态诊断。

但当前出站消息链路只支持文本消息：

1. `LiveFeishuClient` 仅暴露 `sendText(...)`。
2. `FeishuChannelAdapter` 固定调用文本发送。
3. 设置页没有“默认消息格式”配置。

这导致 agent 在飞书中的回复始终只能以纯文本呈现，无法切换到飞书官方支持的 `post` 富文本消息或 `interactive` 卡片消息。

## 2. 需求目标

本次需求目标是：参考官方 SDK 的消息发送模型，为 agentGui 的飞书渠道增加 `post` 消息和卡片消息支持，并允许用户在设置页切换默认发送格式。

首版目标聚焦于“出站回复格式切换”，不扩展为完整的飞书卡片交互平台。

## 3. 官方 SDK 对齐要求

参考官方 Python SDK 中的 IM v1 模型：

1. 创建消息请求体字段为 `receive_id`、`msg_type`、`content`、`uuid`。
2. 回复消息请求体字段为 `msg_type`、`content`、`reply_in_thread`、`uuid`。
3. `msg_type` 与 `content` 的组合决定实际消息类型。
4. `content` 仍然是字符串类型，内部承载 JSON 字符串。

因此，Swift 侧需求必须保持与该接口组织方式一致：

1. 继续使用当前创建消息与回复消息 API。
2. 将现有“只支持 text”的实现扩展为“根据消息格式生成不同的 `msg_type` 和 `content`”。
3. 不引入与官方接口不一致的私有消息发送协议。

## 4. 用户场景

### 4.1 核心场景

1. 用户在设置页启用飞书渠道，并将默认发送格式设置为“文本”。
2. agent 回复飞书消息时，继续按当前文本模式发送。
3. 用户将默认发送格式改为“Post 富文本”。
4. agent 后续回复自动以飞书 `post` 消息发送。
5. 用户将默认发送格式改为“卡片消息”。
6. agent 后续回复自动以飞书 `interactive` 卡片发送。

### 4.2 回复场景

1. 对已有飞书消息进行回复时，所选格式同样生效。
2. 无论是新消息还是 reply，格式选择规则保持一致。

## 5. 范围定义

### 5.1 本次纳入范围

1. 飞书出站消息新增 `text`、`post`、`interactive` 三种发送格式。
2. 设置页新增默认发送格式选择项。
3. 格式配置需要被持久化，并在下次打开设置页时正确恢复。
4. 飞书 adapter 根据配置选择格式并发送。
5. 创建消息与回复消息两条链路都支持三种格式。
6. 新增对应单元测试，覆盖格式切换、请求体生成和持久化读取。

### 5.2 本次不纳入范围

1. 不做飞书卡片按钮点击后的完整业务回调处理。
2. 不做卡片模板编辑器或原始 JSON 编辑器。
3. 不做按消息内容自动选择格式的策略引擎。
4. 不做多语言 `post` 自动翻译，仅要求首版输出单语言版本。
5. 不做图片、文件、附件、分享卡片等其他消息类型支持。
6. 不改变当前入站消息只以文本归一化进入 agent 的主路径。

## 6. 方案选型

本次需求有三种可选方向：

### 6.1 方案 A：设置页切换默认格式，发送时自动渲染为对应结构

这是推荐方案。

特点：

1. 用户心智简单，设置一次即可全局生效。
2. 不要求用户理解飞书原始 JSON 结构。
3. 能复用当前 agent 输出的纯文本结果，只在飞书出站层做渲染转换。
4. 与现有渠道架构最兼容，改动集中在设置、adapter、client 和 formatter。

### 6.2 方案 B：在设置中提供原始 JSON 模板编辑能力

不推荐作为首版。

问题：

1. 用户需要理解飞书 `post` / `interactive` JSON 结构。
2. 设置页复杂度会明显上升。
3. 校验、预览、版本管理成本高。
4. 更像一个卡片编辑平台，超出当前需求。

### 6.3 方案 C：保留文本为默认，运行时按内容自动升级为 post 或 card

不推荐作为首版。

问题：

1. 自动判断规则不稳定。
2. 同一会话中消息样式会不可预测。
3. 出错后难以向用户解释为何这次是文本、下次是卡片。

结论：首版采用方案 A。

## 7. 功能需求

### 7.1 设置页

设置页中的飞书分组需要新增“默认发送格式”配置项。

可选值至少包括：

1. 文本消息
2. Post 富文本
3. 卡片消息

要求：

1. 该选项和现有飞书启用状态、显示名称、凭证处于同一设置入口。
2. 保存后立即持久化。
3. 再次打开设置页时能正确回显。
4. 默认值为“文本消息”，以保证与现有行为兼容。

### 7.2 文本消息

文本消息保持现有行为不变：

1. `msg_type = text`。
2. `content` 保持现有 `{"text":"..."}` 结构。
3. 现有文本链路测试应继续通过。

### 7.3 Post 富文本消息

当用户选择“Post 富文本”时：

1. 出站消息 `msg_type` 必须为 `post`。
2. `content` 必须是飞书要求的 JSON 字符串。
3. 首版以单语言内容输出，推荐固定生成 `zh_cn` 版本。
4. agent 的原始文本输出需要按段落或换行转换为 `post` 段落节点。

首版要求：

1. 支持标题为空时正常发送。
2. 支持多段文本。
3. 保留换行语义，不把整段内容压成单个不可读节点。
4. 不要求首版支持复杂富文本标记映射，例如超链接、mention、代码块高保真还原。

### 7.4 卡片消息

当用户选择“卡片消息”时：

1. 出站消息 `msg_type` 必须为 `interactive`。
2. `content` 必须是飞书卡片 JSON 的字符串表示。
3. 首版采用内置固定卡片模板，不允许用户自由编辑模板结构。

首版卡片模板至少满足：

1. 有清晰标题，例如使用渠道显示名称或固定标题。
2. 有主体文本区域，用于展示 agent 回复内容。
3. 对长文本保持基本可读性。
4. 不包含需要后端回调处理的交互按钮。

换句话说，首版“卡片消息”是静态展示型卡片，而不是交互工作流卡片。

### 7.5 创建消息与回复消息一致性

无论是主动发送还是回复现有飞书消息，格式选择都必须一致。

要求：

1. 创建消息接口支持三种 `msg_type`。
2. 回复消息接口支持三种 `msg_type`。
3. reply 场景下仍复用当前 `reply_in_thread = false` 默认行为，除非后续另立需求。

## 8. 数据与状态要求

### 8.1 配置持久化

飞书默认发送格式必须进入现有渠道设置持久化体系。

要求：

1. 不写入凭证存储。
2. 与飞书凭证分离保存。
3. 不影响其他渠道配置读取。
4. 对未配置旧数据要自动兼容为“文本消息”。

### 8.2 运行态读取

渠道运行时在发送飞书消息时，必须能读取到当前配置的默认发送格式。

要求：

1. 设置保存后，新产生的出站消息按新格式发送。
2. 不要求对“已在途消息”做动态重写。

## 9. 技术要求

### 9.1 抽象层要求

当前 `sendText(...)` 接口不足以承载三种格式，需扩展为更通用的出站消息发送模型。

需求约束：

1. 不能继续把 Feishu client 的公共能力硬编码为文本专用方法。
2. 需要引入消息格式枚举或等价抽象。
3. 需要将 `msg_type` 与 `content` 生成逻辑从 adapter 发送流程中解耦。

推荐拆分：

1. Feishu client 负责发请求。
2. formatter / renderer 负责把 agent 文本输出转换为飞书具体消息体。
3. settings view model 负责保存和读取默认格式。

### 9.2 错误处理

当 `post` 或卡片 JSON 生成失败时：

1. 需要记录明确的运行日志。
2. 需要将错误暴露到现有飞书渠道错误诊断路径。
3. 首版不要求自动静默降级为文本消息。

原因是：用户显式选择了格式，静默降级会掩盖问题并使行为不可预测。

### 9.3 向后兼容

要求：

1. 旧用户不做任何设置变更时，行为与现在一致。
2. 现有文本测试不能被破坏。
3. 现有飞书长连接、入站消息归一化、callback ACK 行为不受影响。

## 10. 测试要求

本需求必须补齐自动化测试，至少覆盖以下场景：

1. 文本格式下，创建消息请求体保持现有结构。
2. Post 格式下，创建消息请求体的 `msg_type` 和 `content` 正确。
3. 卡片格式下，创建消息请求体的 `msg_type` 和 `content` 正确。
4. 文本、Post、卡片三种格式在 reply 接口下都能正确生成请求体。
5. 设置页保存后能正确回显已选格式。
6. 未配置历史数据时默认回退为文本格式。

如果实现过程中引入 formatter 组件，还应增加 formatter 的纯单元测试，而不是只在 client 测试中间接覆盖。

## 11. 验收标准

满足以下条件即可认为本需求完成：

1. 设置页可以在文本、Post、卡片三种默认发送格式之间切换。
2. 设置保存后重启应用，所选格式仍然存在。
3. 飞书新消息发送会按所选格式落为对应 `msg_type`。
4. 飞书 reply 消息发送会按所选格式落为对应 `msg_type`。
5. 文本模式下与当前版本行为完全兼容。
6. `post` 与卡片模式在真实飞书环境中能够成功显示。
7. 本次改动不影响当前飞书入站消息、长连接与 ACK 的既有能力。

## 12. 风险与边界

### 12.1 Post 渲染风险

agent 当前输出是普通文本，而不是结构化富文本。

这意味着首版 `post` 只能做“文本到富文本节点”的有限转换，不能承诺高保真还原所有 Markdown 结构。

### 12.2 卡片模板边界

如果首版卡片模板设计得过于复杂，会把本需求拖向“卡片设计器”。

因此需要严格限制：

1. 模板固定。
2. 不做按钮交互。
3. 不做动态表单。
4. 不做卡片回调业务编排。

### 12.3 配置模型扩展风险

当前渠道配置模型较轻量，如果直接往通用模型塞飞书特有字段，需要注意后续多渠道扩展的一致性。

因此实现时应优先选择“可演进”的配置表达，不要把飞书特例写成难以扩展的临时字段组合。

## 13. 后续可选扩展

本次需求完成后，可继续考虑以下增强，但不属于当前交付范围：

1. 卡片模板多样化。
2. 基于 Markdown 的更高保真 `post` 映射。
3. 针对不同会话或不同消息单独指定发送格式。
4. 飞书卡片按钮回调与 agent 工作流联动。
5. 开发态“发送测试飞书消息”按钮。

## 14. 结论

本需求的核心不是“再加两个字符串枚举值”，而是把当前仅支持文本的飞书出站链路升级为可配置的消息格式发送能力。

首版应明确采用“设置页选择默认格式 + 出站层自动渲染”的方案，以最小复杂度支持：

1. 文本消息。
2. Post 富文本消息。
3. 静态展示型卡片消息。

同时保持当前文本路径完全兼容，并避免把本次改动扩展成完整的飞书卡片交互平台。
