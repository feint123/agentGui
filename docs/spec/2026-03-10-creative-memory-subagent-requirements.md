# 创作项目记忆下沉到独立 Subagent 的需求说明

日期：2026-03-10

关联对象：创作记忆系统、主 Agent Loop、Subagent 系统、Workflow Runtime、写作项目管理

## 1. 背景

当前的创作项目记忆已经接入主聊天循环：

- 主 agent 在启动时直接注入创作记忆 prompt slice
- 主 agent 直接暴露一组 story-memory 工具
- 主 agent 同时承担写作、检索、记忆维护、一致性检查等多类职责

这套实现已经可用，但有一个越来越明显的问题：创作记忆相关能力长期占用主 agent 的上下文预算和工具注意力。

对于普通写作轮次，主 agent 实际更需要关注的是“当前要写什么”和“如何推进当前任务”，而不是始终携带完整的项目记忆工具集合与记忆维护规则。随着创作记忆继续扩展到事件抽取、伏笔追踪、角色弧线、风格档案、retcon 和一致性校验，这部分上下文只会越来越重。

因此，需要把“创作项目记忆的管理职责”从主 agent 中拆出来，交给一个独立的 memory subagent 负责。主 agent 只在需要时委托它处理项目记忆相关任务，而不是在每一轮对话里自己携带全部记忆管理能力。

## 2. 核心目标

本需求的目标不是删除创作记忆，而是重构其运行方式。

目标如下：

- 让主 agent 不再直接承载完整的创作记忆工具集合
- 让创作项目记忆由一个独立、专职、可审计的 subagent 管理
- 把“写作生成”和“项目记忆维护”分成两个不同职责域
- 降低主 agent 的 prompt 体积、工具噪音和决策分叉
- 为后续更复杂的写作工作流预留可扩展的多代理结构

## 3. 问题定义

当前方案的主要问题有四类。

### 3.1 上下文被长期占用

- 主 agent 即使在只做普通续写、润色或讨论时，也要携带创作记忆相关规则
- 主循环中直接注入创作记忆切片，会挤占当前轮次真正用于写作推理的上下文空间
- story-memory 工具数量多，主 agent 容易被诱导去做过细的记忆操作，而不是先完成当前写作任务

### 3.2 职责边界不清晰

- 主 agent 同时负责内容生成、项目查询、结构化更新和连续性校验
- “写作助手”与“项目记忆管理员”混成一个角色后，行为策略难以稳定
- 记忆写入时机、写入粒度、写入依据容易不一致

### 3.3 可扩展性不足

- 如果后续继续增加事件抽取、角色状态归纳、伏笔生命周期管理、风格演进分析，主 agent 的工具面会继续膨胀
- 这与当前系统已经形成的“主 agent + subagent / workflow role”架构方向不一致
- 创作场景未来更适合演进为“写作者 + 记忆管理员 + 校验员”的协作模式，而不是继续把能力堆到主 agent 上

### 3.4 观测与治理成本高

- 目前很难区分：某次写作结果是主 agent 自己决定的，还是受记忆切片或某个记忆工具调用影响的
- 记忆更新和内容生成混在同一条主链路中，不利于后续审计、回放和策略调整

## 4. 设计原则

本需求遵循以下原则：

- 职责单一：创作记忆的检索、整理、更新、校验应由专职 subagent 负责
- 按需激活：只有在当前任务涉及项目记忆时，才唤起 memory subagent
- 主链路轻量：主 agent 默认只关注当前写作目标，不默认携带完整记忆管理工具面
- 保持兼容：底层 SwiftData 模型、现有 StoryMemoryService、RetrievalService、PromptAssembler 应尽量复用
- 可审计：memory subagent 的输入、输出、写入决策、失败原因需要可见
- 可回退：当 subagent 不可用或任务极简单时，系统需要有明确降级策略

## 5. 范围

### 5.1 本次范围

- 定义一个独立的创作记忆 subagent / workflow role
- 把现有 story-memory 管理职责从主 agent 中迁移出去
- 重新定义主 agent 与 memory subagent 之间的调用契约
- 重新定义创作记忆切片的装配时机
- 增加相关状态展示、日志和失败回退要求

### 5.2 不在本次范围

- 不重写现有创作记忆数据模型
- 不重做完整的创作项目 UI 编辑器
- 不引入任意层级的无限递归 subagent
- 不在本次需求里定义完整的多角色写作 workflow 编排 DSL
- 不把长期记忆和创作项目记忆合并成同一套用户记忆系统

## 6. 目标方案概述

系统需要引入一个独立的“创作记忆管理员”角色。该角色可以表现为现有 subagent 的一种专用定义，也可以表现为 workflow runtime 中的一个专职 role，但对上层产品语义来说，它是同一个能力：

- 负责项目级创作记忆的查询
- 负责结构化记忆更新
- 负责连续性检查与问题归档
- 负责把与当前任务最相关的记忆摘要返回给主 agent

主 agent 不再默认直接拥有全部 story-memory 工具，而是通过委托方式与该角色交互。

推荐的默认模式是：

- 主 agent 负责理解用户写作意图并推进当前任务
- memory subagent 负责提供“当前任务所需的最小相关记忆上下文”
- 当写作结果可能影响项目 canon 时，由 memory subagent 决定是否写入、写入什么、以什么结构写入

## 7. 功能需求

### 功能点 1：独立的创作记忆 Subagent

需求：

- 系统必须提供一个专职的创作记忆 subagent，职责与写作主 agent 明确分离
- 该 subagent 的系统提示、工具权限、输出格式与主 agent 分开定义
- 该 subagent 默认不负责长篇创作生成，只负责记忆相关决策与处理
- 该 subagent 的身份需要在 UI 和日志中明确可见，而不是伪装成主 agent 的普通工具调用

### 功能点 2：主 Agent 工具面收缩

需求：

- 主 agent 默认不应直接暴露完整的 story-memory 工具集合
- 主 agent 与创作项目记忆的交互应通过单一委托入口完成，而不是保留十多个细粒度工具在主上下文中
- 主 agent 的默认 prompt 中不应长期包含大段创作记忆维护规则
- 主 agent 是否需要记忆帮助，应根据当前任务动态判断

验收重点：

- 从主 agent 视角看，创作记忆应该是一个外部协作者，而不是一组常驻工具

### 功能点 3：按需检索与最小切片返回

需求：

- 当任务涉及世界观、角色状态、时间线、伏笔、一致性或项目绑定时，主 agent 可以唤起 memory subagent
- memory subagent 必须返回与当前请求直接相关的最小记忆切片，而不是原样回灌整个项目摘要
- 返回结果必须区分“事实记忆”“推测”“待确认风险”三类信息，避免主 agent 把不确定信息当 canon 使用
- 返回结果应尽量面向当前任务消费，而不是面向底层存储结构暴露所有字段

### 功能点 4：写入策略由 Memory Subagent 决定

需求：

- 项目级创作记忆的新增、更新、归档、连续性问题记录，应由 memory subagent 决定是否执行
- 主 agent 完成写作后，如结果可能改变 canon，应把候选内容交给 memory subagent 审核
- memory subagent 需要能够区分以下情况：
  - 可直接写入的结构化事实
  - 需要用户确认后再写入的内容
  - 只应作为临时推理结果，不应写入项目记忆的内容
- 记忆写入应优先保持幂等和可追踪，避免每轮都产生重复记录

### 功能点 5：连续性检查与记忆治理独立化

需求：

- 连续性检查应优先由 memory subagent 承担，而不是让主 agent 自己同时扮演作者和审稿人
- memory subagent 可以对草稿、章节、事件更新做一致性核对，并返回结构化问题列表
- 未解决问题、已接受冲突、已修复问题的状态流转，应由 memory subagent 负责维护
- 后续如增加风格漂移、角色弧线偏移、伏笔回收状态等治理能力，也应落在这个角色下

### 功能点 6：项目绑定与路由规则清晰化

需求：

- memory subagent 必须明确知道自己当前操作的是哪个 WritingProject
- 当当前会话未绑定项目、绑定失效或存在歧义时，memory subagent 必须返回明确状态，而不是静默猜测并写错项目
- 主 agent 不应绕过该路由规则直接写入任意项目记忆
- 多项目场景下，必须支持显式切换当前目标项目

### 功能点 7：可观测性与审计

需求：

- UI 需要把 memory subagent 呈现为一次“委托任务”或“记忆处理步骤”，而不是主消息里的隐形内部行为
- 用户可以看到该 subagent 被唤起的原因、处理结果、是否发生写入、是否发现连续性问题
- 对失败场景，需要展示是“未绑定项目”“检索为空”“写入被拒绝”“连续性校验失败”还是“subagent 调用失败”
- 后续如做工作流回放，需要能够还原主 agent 与 memory subagent 的输入输出边界

### 功能点 8：失败回退与兼容路径

需求：

- 当 memory subagent 无法调用时，系统必须有明确回退策略
- 回退策略至少包括：
  - 只继续当前写作，不做项目记忆更新
  - 通知用户当前结果未写入创作记忆
  - 在必要时允许用户手动触发一次记忆整理
- 回退路径必须显式可见，不能让用户误以为项目记忆已经更新成功

## 8. 交互要求

- 在聊天时间线中，memory subagent 应呈现为一个独立步骤或任务卡
- 当主 agent 请求记忆支持时，界面应显示本次委托的目的，例如“查询角色状态”“更新章节事件”“执行连续性检查”
- 当 memory subagent 返回结果时，应默认显示精简摘要，并允许展开查看详细结构化结果
- 当本轮写作未触发任何记忆委托时，界面不应强行显示创作记忆相关噪音
- 当写作结果未写入项目记忆时，用户应能明确知道这是“未触发”还是“触发后被拒绝”

## 9. 架构要求

### 9.1 对主 Agent Loop 的要求

- 主循环不再默认预注入完整创作记忆切片
- 主循环只在当前任务需要时请求 memory subagent 返回最小上下文
- 主循环中的创作记忆相关提示词，应从“常驻规则”改为“委托协议”

### 9.2 对 Memory Subagent 的要求

- 允许其持有 story-memory 相关工具权限
- 允许其复用现有 StoryMemoryService、StoryMemoryRetrievalService、StoryMemoryPromptAssembler 等底层能力
- 输出必须尽量结构化，方便主 agent 消费和 UI 呈现
- 应支持后续升级为 workflow role，而不是把实现锁死在一次性 run_subagent 壳里

### 9.3 对工具层的要求

- 底层 story-memory 工具可以继续存在，但默认应收拢到 memory subagent 所属能力域
- 主 agent 面向模型暴露的工具面需要显著收缩
- 不应为了兼容而继续把全部工具同时暴露给主 agent 和 subagent，除非存在明确迁移期开关

## 10. 数据与状态要求

- 现有 WritingProject 及相关 SwiftData 模型应继续复用
- 现有项目绑定关系应继续复用
- 需要新增或保留足够的运行时状态，用于记录：
  - 本轮是否触发 memory subagent
  - 本轮 memory subagent 的任务类型
  - 返回了哪些记忆切片
  - 是否执行了写入
  - 是否发现连续性风险
  - 是否发生失败或回退

## 11. 验收标准

- 主 agent 默认上下文中不再长期暴露完整的 story-memory 工具集合
- 在普通写作、闲聊、润色等不依赖项目记忆的轮次中，memory subagent 不会被无意义唤起
- 在涉及角色、设定、时间线、伏笔或章节连续性的任务中，主 agent 能正确委托 memory subagent 获取相关上下文
- 当写作结果改变 canon 时，系统能通过 memory subagent 决定是否写入并给出清晰结果
- 用户能在 UI 中区分“主 agent 的写作行为”和“memory subagent 的记忆处理行为”
- subagent 失败时，系统不会伪装成已成功更新项目记忆

## 12. 优先级

- P0：独立 memory subagent、主 agent 工具面收缩、按需委托、失败可见
- P1：结构化最小切片返回、写入策略治理、连续性检查独立化
- P2：更细粒度的审计视图、项目级回放、与 workflow runtime 的深度整合

## 13. 分阶段落地建议

### Phase 1：职责拆分

- 定义 memory subagent 身份与提示词
- 把 story-memory 工具收拢到该角色下
- 主 agent 改为通过单一委托入口请求创作记忆帮助

### Phase 2：最小上下文协议

- 定义主 agent 与 memory subagent 之间的输入输出协议
- 让 memory subagent 返回“最小相关切片 + 风险说明 + 写入建议”
- 移除主循环中的常驻创作记忆切片注入

### Phase 3：治理与工作流化

- 让连续性检查、问题归档、canon 更新逐步转入 memory subagent
- 与 workflow runtime 对齐，使其可升级为长期存在的专职 role
- 增强 UI 审计与回放能力

## 14. 结论

创作项目记忆不应继续作为主 agent 的常驻附属能力存在。对写作场景来说，更合理的结构是：主 agent 负责当前创作任务，memory subagent 负责项目级事实、检索、更新和一致性治理。

这次需求的本质，是把“创作记忆”从一组占用主上下文的工具，升级为一个独立的协作者。只有完成这次职责拆分，后续的角色弧线管理、伏笔治理、风格演进和多代理写作工作流才有稳定的架构基础。
