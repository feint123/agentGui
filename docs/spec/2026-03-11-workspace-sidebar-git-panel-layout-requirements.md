# Workspace 侧栏 GitPanel 简化与布局收敛需求文档

日期：2026-03-11

关联对象：`WorkspacePanelView`、`GitPanelView`、`GitPanelViewModel`、`WorkspaceState`、`WorkspacePanel` 中文件树区域

## 1. 背景

当前 `WorkspacePanelView` 在同一个侧栏内同时承载以下几类信息：

- 工作目录栏
- GitPanel
- TodoList
- 文件树

其中 GitPanel 已逐步演化出摘要、分组、文件级操作、提交区、diff 导航等较高信息密度能力，导致它与文件树在纵向空间上直接竞争。当前最明显的问题不是单个控件样式，而是职责边界已经模糊：

- GitPanel 想承担 Source Control 主面板职责
- 文件树也已经承担了文件浏览与 diff 入口职责
- 两者都占据侧栏核心空间，造成重复与拥挤

结合当前产品阶段，继续在侧栏内维护一个“完整版 GitPanel”并不合适。文件树已经能够打开 diff，这条链路已经覆盖最常用的变更查看需求。GitPanel 没必要继续承担文件级 diff 浏览、行内操作和提交入口等重量级职责。

## 2. 本次需求结论

本次需求不再继续增强 GitPanel，而是明确进行能力收敛：

> GitPanel 只保留 Git 汇总信息与分支切换能力，不再承担 diff 预览、文件级操作、提交输入等职责。

同时，侧栏布局要围绕这一简化方向重组：

- 文件树重新成为侧栏的绝对主区域
- GitPanel 退化为轻量信息条或紧凑功能卡片
- 所有文件级 diff 查看继续统一走文件树入口
- 重复的 GitPanel 交互代码应在实现阶段删除，而不是保留为隐藏能力

## 3. 目标

本次调整完成后，应达到以下结果：

- 侧栏结构更简单，主次关系清晰
- GitPanel 不再与文件树争夺主要空间
- 用户仍能快速看到当前仓库状态
- 用户仍能完成基础分支切换
- 文件级 diff 入口统一收敛到文件树，不再有两套并行心智模型
- 冗余 Git 交互代码被清理，避免后续继续膨胀

## 4. 设计原则

### 4.1 文件树优先

左侧侧栏的主任务始终是浏览项目内容，因此文件树必须是主区域，默认占据剩余空间。

### 4.2 Git 信息轻量化

GitPanel 只负责回答两个问题：

- 当前仓库整体状态如何
- 当前分支是什么，能否切换分支

除此之外的交互，原则上不再放在 GitPanel 中。

### 4.3 单一入口

同一种任务应只有一条主路径：

- 查看文件 diff：走文件树
- 浏览项目文件：走文件树
- 查看仓库摘要：走 GitPanel
- 切换分支：走 GitPanel

### 4.4 删除冗余实现

本次不是“保留旧能力但默认隐藏”，而是要明确删除已经不再符合产品方向的多余代码，避免未来维护成本继续增加。

## 5. 现状问题

### 5.1 空间竞争

- GitPanel 与文件树在同一 `VStack` 中直接竞争高度
- GitPanel 内容一多，文件树可视区域明显下降
- 文件树目录稍深时，GitPanel 也会被压缩得无法稳定阅读

### 5.2 职责重叠

- GitPanel 内部已有 diff 打开路径
- 文件树也能根据 Git 状态打开 diff
- 两者形成重复入口，增加认知成本

### 5.3 交互复杂度过高

- GitPanel 内存在文件级操作、提交区、危险操作确认等逻辑
- 这些能力占用大量侧栏空间，也抬高了状态管理复杂度
- 对当前产品阶段而言，这些能力并非左侧侧栏的必要职责

## 6. 范围定义

### 6.1 在本次范围内

- 重新定义 GitPanel 的职责边界
- 调整侧栏布局，使 GitPanel 变为紧凑汇总区
- 保留 Git 汇总信息展示
- 保留分支展示与分支切换能力
- 保留文件树中的 Git 状态装饰与 diff 打开能力
- 删除 GitPanel 中多余的 diff、提交、文件级操作相关代码

### 6.2 不在本次范围

- 完整 Source Control 面板
- 提交输入与提交执行 UI
- GitPanel 内文件级暂存 / 取消暂存 / 丢弃 / 删除
- GitPanel 内 diff 浏览能力
- 分支管理高级功能，例如创建、删除、rebase、merge

## 7. 功能需求

### 7.1 GitPanel 的保留能力

GitPanel 保留以下信息与交互：

- 当前仓库名
- 当前分支名
- ahead / behind 等基础同步摘要（如已有）
- staged / modified / untracked 数量汇总
- 刷新仓库状态
- 切换分支

其中“切换分支”能力的目标是满足常用分支切换，而不是扩展成完整 Git 分支管理中心。

### 7.2 GitPanel 明确移除的能力

GitPanel 应移除以下职责：

- 按分组展示文件变更列表
- 从 GitPanel 打开文件 diff
- 文件级暂存 / 取消暂存 / 丢弃 / 删除未跟踪文件
- 提交消息输入框
- 提交按钮
- 危险操作确认弹窗中仅服务于 GitPanel 文件级动作的逻辑

### 7.3 文件树的职责强化

文件树继续承担以下职责：

- 浏览目录与文件
- 展示 Git 状态装饰
- 作为文件 diff 的主要入口
- 承接与文件相关的后续扩展交互

若当前文件树已经能够打开 diff，则该能力应被视为正式主路径，而非临时替代方案。

## 8. 布局需求

### 8.1 推荐布局

侧栏应调整为以下结构：

- 顶部：工作目录栏
- 中上：紧凑 GitPanel
- 中部：TodoList（如存在）
- 下部：文件树主区域

关键要求：

- GitPanel 高度应明显收敛为紧凑区块
- 文件树占据侧栏剩余主要空间
- TodoList 不应破坏“GitPanel 轻量、文件树主导”的结构

### 8.2 GitPanel 高度策略

- GitPanel 不再需要大面积滚动区域
- GitPanel 默认应接近固定高度或接近内容自适应高度
- GitPanel 不应因为仓库状态变化而突然膨胀成主区域

### 8.3 文件树高度策略

- 文件树必须是侧栏主滚动区域
- 无论 GitPanel 内容如何，文件树都应拥有稳定、可用的浏览高度
- 小窗口下优先压缩 GitPanel，而不是压缩文件树

## 9. 分支切换需求

### 9.1 基本要求

- GitPanel 中应提供当前分支展示
- 用户应可从 GitPanel 发起分支切换
- 分支切换入口应尽量轻量，例如菜单、下拉选择、弹出列表，而不是额外打开复杂管理面板

### 9.2 行为要求

- 切换分支后，Git 摘要应自动刷新
- 文件树状态应随仓库状态更新
- 若切换失败，应给出用户可理解的错误反馈

### 9.3 非目标

本次不要求：

- 新建分支
- 删除分支
- 处理复杂 checkout 冲突流程
- 提供远端分支高级管理

## 10. 代码清理要求

本次实现必须包含“删除多余代码”，不能只停留在界面隐藏层。

需要清理的对象包括但不限于：

- GitPanel 内已不再使用的文件分组视图代码
- GitPanel 内文件项行视图与相关交互辅助方法
- GitPanel 内提交区相关视图与状态绑定
- 仅服务于 GitPanel 文件级动作的 ViewModel 状态和方法
- 仅为 GitPanel 文件级 diff 入口服务的可访问性标识与 UI 测试夹具

清理原则：

- 如果某段代码不再为“汇总信息 + 分支切换”服务，就应删除
- 如果某段状态只为已废弃交互存在，就应从 ViewModel 中移除
- 如果文件树已经承担该职责，不应再在 GitPanel 中保留等价实现

## 11. 验收标准

### 11.1 布局验收

- GitPanel 不再与文件树明显抢占纵向空间
- 文件树重新成为侧栏主区域
- 小窗口下侧栏仍以文件树可用性优先

### 11.2 功能验收

- 用户可在 GitPanel 中看到仓库摘要与当前分支
- 用户可从 GitPanel 完成分支切换
- 用户仍可从文件树打开 diff
- 用户不会再在 GitPanel 中看到文件变更列表、提交区和文件级动作

### 11.3 清理验收

- GitPanel 中与文件级 diff / 提交 / 文件操作相关的多余代码已删除
- ViewModel 中仅为旧 GitPanel 交互服务的状态和方法已清理
- UI 测试与 accessibility 标识同步收敛，不再保留失效接口

## 12. 优先级

- P0：GitPanel 职责收敛为“汇总 + 分支切换”，文件树恢复主区域地位
- P1：删除 GitPanel 冗余交互代码与相关状态
- P2：根据简化后的侧栏结构，再评估是否需要进一步做可折叠辅助区块

## 13. 后续扩展方向

在本次简化完成后，如后续确实需要更强 Git 能力，应优先考虑以下方向，而不是再次把 GitPanel 塞回侧栏主区：

1. 独立 Source Control 面板或标签页
2. 右侧 Inspector 风格的仓库摘要与分支信息区
3. 面向高级用户的独立 Git 工作流视图

结论上，本次需求的重点不是“让 GitPanel 更强”，而是“让侧栏重新变简单、清晰、可用”。
