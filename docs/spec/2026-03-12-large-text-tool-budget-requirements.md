# 内置工具大文本预算治理需求说明

日期：2026-03-12

关联对象：`ToolRegistry`、`ClaudeService+ToolBuilder`、`ClaudeService+ToolDispatch`、`ClaudeService+AgenticLoop`、`BashSession`、`ToolCall`、工具结果展示 UI、未来的临时载荷存储层

设计基准：将当前“工具直接把原始大段文本塞回上下文”的模式，升级为“预算感知的结果分级返回 + 可续读载荷句柄 + 分段读取协议”，避免大文件、长终端输出、长网页正文直接耗尽上下文预算。

## 0. 当前现状与结论

本需求不是从零开始。当前系统已经存在一些与大文本相关的局部能力，但它们分散、规则不统一，仍不足以形成可靠的上下文预算治理方案。

### 0.1 当前已存在的局部能力

- 文本编辑工具 `str_replace_based_edit_tool` 已支持 `view_range [start, end]`，可以按行读取文件片段
- `web_fetch` 已支持 `max_chars`，可以限制单次返回字符数
- `bash` 已支持后台执行，长任务可输出到临时 log 文件，再由后续命令读取
- `BashSession` 内部已经对输出缓冲做了上限裁剪，当前最大约为 50 KB
- Agent loop 已记录工具结果长度，例如 `outputLength`，说明系统已经意识到工具输出体积是一个重要信号

### 0.2 当前根本问题

尽管存在这些局部能力，系统仍然缺少统一的大文本处理协议。当前问题主要在于：

- 不同工具各自发明自己的“限流方式”，模型需要分别记忆 `view_range`、`max_chars`、临时 log 文件等约定
- 工具结果在 agent loop 中仍主要以纯文本结果注入上下文，而不是统一的“摘要 + 预览 + 续读句柄”结构
- 是否内联全文、何时转摘要、何时转分段读取，目前缺少统一预算门控规则
- UI、持久化层和后续工具调用之间没有共享的“大载荷引用”对象，导致大结果只能靠文本本身流转
- 文本工具虽然支持 `view_range`，但当前更多依赖 agent 自己主动想到要分段；系统不会把“大文件应先看摘要/目录/局部区间”提升为默认行为

结论：当前系统已经有若干正确方向的能力雏形，但缺少一套统一、可扩展、可观测的大文本预算治理层。

## 1. 背景

随着 agentGui 内置工具越来越多，工具返回的数据体积也越来越大。最典型的几类场景包括：

- 读取超大源文件、日志文件、配置文件
- Bash 执行测试、构建、抓取命令后产生长输出
- Web fetch 拉取长网页、文档页、PDF 提取文本
- Web search 结果过多，后续再 fetch 多个页面后累计正文过长

这些场景的共同点不是“结果大”，而是“结果大但并不需要一次性全部进入模型上下文”。真正影响决策的，通常只是以下几层信息：

- 结构化摘要
- 少量关键预览片段
- 模型按需继续拉取的局部块

主流 agent 系统在处理大文本时，通常遵循以下原则：

- 渐进披露：先给摘要和导航，再按需读取正文
- 游标或分段协议：结果可以续读，而不是只能整段重来
- 原始载荷脱离上下文保存：全文存储在临时对象、缓存或文件中，不直接长期占用 prompt
- 预算门控：是否内联、内联多少、何时退化为摘要，由预算策略决定，而不是由工具作者临时拍脑袋
- 相关性优先：能过滤就先过滤，能提取就不直接灌原文

Anthropic `web_fetch` 新版本已经明确采用“dynamic filtering 后再进入上下文”的路线，这说明“大文本先过滤、后入窗”已经是行业共识。你的想法也一致，即：大文件分段读取，bash 长输出落临时文件后再分段读，web fetch / web search 同样不要把全部正文直接塞进当前轮上下文。

## 2. 目标

本需求的目标如下：

- 建立统一的大文本结果协议，适用于文本工具、bash、web fetch、web search 等内置工具
- 让系统默认优先返回摘要和局部预览，而不是默认回填整段原始正文
- 让所有大结果都具备“可续读”能力，而不是一次性消费
- 让预算治理成为运行时策略，而不是依赖 agent 临时发挥
- 让 UI、持久化层、agent loop、工具调用层共享同一套“大载荷引用”模型
- 在不牺牲可用性的前提下，显著降低上下文被大文本工具结果挤爆的概率

## 3. 不在本次范围

- 不要求本期引入完整向量检索或 RAG 基础设施
- 不要求本期支持对所有文件类型做语义切块，只需先支持稳定的文本型分段
- 不要求本期重做所有工具 UI，但需要为后续 UI 展示预留结构化字段
- 不要求本期把所有历史 `ToolCall` 数据迁移为新格式
- 不要求本期解决图片、音频、视频等非文本大载荷问题

## 4. 问题定义

### 4.1 当前是“文本直返”模型，不是“载荷引用”模型

当前多数工具仍将结果组织为一个大的 `String` 返回给 agent loop。即使工具本身存在 `view_range`、`max_chars` 或后台 log 文件等机制，最终进入 agent loop 的仍主要是文本，而不是结构化引用。

这会导致：

- 大结果一旦被返回，就会直接参与后续 prompt 拼装
- 工具之间难以共享“继续读取上一份结果”的语义
- UI 只能展示文本摘要，无法对原始大载荷做稳定导航

### 4.2 当前缺少统一预算策略

不同工具目前分别有：

- 行范围限制
- 字符数限制
- 输出 buffer 限制
- 临时 log 文件

但这些限制都只是工具局部实现细节，系统尚未定义：

- 每轮总共允许多少工具结果进入上下文
- 单个工具结果超过多少时必须转摘要模式
- 多个工具连续返回长文本时，谁优先保留正文、谁必须降级
- 续读结果是否也要受到本轮剩余预算约束

### 4.3 当前缺少统一续读协议

理论上，今天已经可以这样做：

- 大文件靠 `view_range` 分段看
- Bash 后台落 log 后再 `cat` / `tail`
- Web fetch 靠 `max_chars` 自己多次拉

但这仍然是碎片化方案，问题在于：

- agent 需要记住每个工具不同的续读方式
- 同一份大结果没有稳定的 `payload_id` / `cursor` 概念
- 结果跨轮次、跨 UI、跨恢复场景时不具备统一引用能力

### 4.4 当前缺少“先结构、后正文”的默认交互

面对超大文本，主流实践不是“截断前 N 个字符”，而是先返回能支持决策的导航信息，例如：

- 文件的总行数、区间信息、命中点摘要
- Bash 输出的 exit code、错误摘要、尾部关键片段
- 网页提取后的标题、章节索引、命中段落、可读区块数
- 搜索结果的标题、域名、snippet、相关性排序

当前系统还没有把这层结构化导航设为默认返回。

## 5. 方案对比

### 方案 A：按工具分别补丁式限流

做法：继续在每个工具上单独补充 `max_chars`、`view_range`、日志文件、截断逻辑。

优点：

- 开发成本低
- 可快速缓解部分问题

缺点：

- 规则继续碎片化
- agent 继续承担协议记忆成本
- 无法形成统一预算治理与可观测性

### 方案 B：统一大载荷协议层

做法：为所有文本型大结果建立统一返回壳层，正文默认不直接灌入上下文，而是保存为临时载荷；上下文只接收摘要、预览和续读句柄；继续读取通过统一工具或统一协议完成。

优点：

- 解决的是根因，不是局部补丁
- 各工具行为一致，模型更容易学会稳定用法
- 能统一做预算门控、缓存、观测和 UI 导航

缺点：

- 需要引入新的载荷存储与读取层
- 工具结果 contract 需要调整

### 方案 C：只做自动摘要，不保留续读能力

做法：一旦结果过大，系统只返回自动摘要，不提供原文分段读取。

优点：

- 实现最简单
- 上下文最省

缺点：

- 丢失可验证性
- agent 无法继续深入查看原文局部，容易误判
- 不适合代码、日志、规范文档这类要求精读的任务

### 推荐方案

推荐采用方案 B，并在第一阶段吸收方案 A 的低成本缓解手段。

也就是说：

- 短期先把明显会爆预算的路径改成摘要 + 预览
- 中期建立统一载荷句柄和分段读取协议
- 长期再补充更智能的结构提取、相关性过滤和 UI 导航

## 6. 总体方案

### 6.1 核心原则

- 默认不内联全文：大文本结果默认只进摘要和小预览
- 全文必须可续读：任何被截断或降级的大结果都必须能继续读取
- 预算优先于便利：是否直接回填正文由预算决定，不由工具作者随意决定
- 一次只给模型当前需要的那一小段：避免重复传输和重复占用
- 工具协议统一：不同工具的大结果应共享相同的壳层字段和续读方式

### 6.2 目标形态

系统需要建立三层统一抽象：

1. `LargeTextPayload`
表示脱离当前 prompt 保存的一份大文本载荷，可来自文件读取、bash 输出、网页正文、搜索聚合结果。

2. `ToolResultEnvelope`
工具面向 agent loop 返回的统一壳层。小结果可直接内联；大结果返回摘要、预览和 `payloadRef`。

3. `PayloadReadProtocol`
统一的续读协议。agent 不再依赖每个工具自定义续读方式，而是使用同一套“按段读取上一份大结果”的方式。

## 7. 功能需求

### 功能点 1：建立统一结果壳层

所有文本型工具结果必须支持统一结构，至少包含以下字段或等价语义：

- `summary`：一段可直接进上下文的摘要
- `preview`：有限长度的原文预览，可为空
- `payload_ref`：指向完整大载荷的引用；小结果可为空
- `is_truncated`：当前结果是否已降级或截断
- `estimated_chars`
- `estimated_tokens`
- `retrieval_hint`：告诉 agent 下一步应如何继续读取
- `source_kind`：file / bash / web_fetch / web_search / other

要求：

- 当结果体积低于预算阈值时，允许 `preview` 即完整正文，`payload_ref` 为空
- 当结果体积高于阈值时，必须生成 `payload_ref`，并且 `summary` 与 `preview` 仍然足够支持下一步决策
- agent loop 不应只持有裸文本，还应感知该结果是否为“可续读大载荷”

### 功能点 2：建立统一大载荷存储层

系统必须提供统一的临时载荷存储层，用于保存大文本原文。

要求：

- 支持把大文件片段、bash 长输出、网页正文、搜索结果聚合保存为临时载荷
- 每份载荷必须有稳定 `payload_id`
- 必须记录：来源工具、来源参数、生成时间、估计长度、编码方式、过期时间
- 载荷应默认存储在 app 私有临时目录或等价持久化区域，而不是工作区文件树
- 载荷必须支持 TTL 或主动清理，避免无限堆积
- 载荷读取必须可审计，便于定位上下文预算问题

### 功能点 3：建立统一分段读取协议

系统必须提供统一的“继续读取大载荷”能力，建议表现为一个新的内置工具，例如 `read_tool_payload`，或等价的统一读取入口。

最小能力要求：

- 按字符区间读取
- 按行区间读取
- 按逻辑块读取，例如 section / paragraph / chunk
- 支持游标或 `next_cursor`
- 支持返回当前块的前后文信息，例如总块数、当前块序号、剩余块数
- 支持只读取摘要、只读取目录、只读取命中块

推荐返回结构：

- `content`
- `cursor`
- `next_cursor`
- `has_more`
- `chunk_index`
- `chunk_count`
- `range_summary`

### 功能点 4：建立统一预算门控策略

系统必须在工具执行完成后、结果进入上下文前，统一判断该结果应采用哪种返回级别。

至少需要三档：

- `inline`：小结果，允许直接内联全文
- `preview`：中结果，只返回摘要 + 局部片段
- `referenced`：大结果，只返回摘要 + 预览 + `payload_ref`

预算门控最低应考虑以下输入：

- 当前模型上下文窗口大小
- 当前轮已用输入 token
- 当前轮已累计工具结果体积
- 当前仍待注入的其他 artifacts 或 memory 内容
- 当前工具的重要性和可压缩性

规则要求：

- 不允许多个工具各自认为“自己只占一点”，累计后把上下文挤爆
- 预算策略应保留一段安全余量给后续模型思考和生成
- 当预算不足时，应优先保留摘要、关键信号和引用句柄，而不是盲目裁切原文前缀

### 功能点 5：把“结构化导航”作为默认返回

大文本结果进入上下文前，应尽量先生成结构化导航，而不是直接返回前 N 个字符。

最低要求：

- 文件：总行数、建议阅读区间、命中位置、首尾预览
- Bash：exit code、是否超时、错误摘要、尾部关键片段、日志句柄
- Web fetch：页面标题、域名、主要区块数、摘要、关键段落预览
- Web search：结果列表、域名、snippet、排序理由，不直接展开所有正文

### 功能点 6：工具级适配要求

#### 6.1 文本编辑工具

要求：

- 保留现有 `view_range` 能力
- 对超大文件，不应默认返回整文件文本；应先返回文件统计、结构预览和建议区间
- 当 agent 请求 `view` 但未给区间且文件明显过大时，系统应自动降级为“摘要 + 建议区间 + `payload_ref`”
- 允许继续按行读取，且分段边界应稳定，不因编码差异产生漂移

#### 6.2 Bash 工具

要求：

- 前台命令输出过长时，不应直接把整个 transcript 返回到上下文
- 长输出必须支持自动落到临时载荷，或等价的私有临时文件，再通过统一协议分段读取
- 默认返回内容应优先包含：命令摘要、状态、exit code、错误片段、尾部预览、`payload_ref`
- 对后台任务，继续保留日志文件/任务跟踪机制，但 agent 不应被迫手写 `cat` / `tail` 才能稳定续读；系统应提供更直接的读取入口

#### 6.3 Web fetch 工具

要求：

- 保留 `max_chars`，但其不应继续作为唯一的大文本控制手段
- 页面正文过大时，应优先做正文提纯、区块提取或章节索引，再决定哪些片段进入上下文
- 原始清洗正文应保存为 `payload_ref`
- 若未来引入动态过滤能力，应接入同一预算门控与载荷协议，而不是另起一套返回格式

#### 6.4 Web search 工具

要求：

- 默认只返回有限数量结果及 snippet，不直接扩展成长文聚合
- 若搜索结果需要进一步聚合为“大搜索报告”，该聚合结果也必须走统一 `payload_ref`
- 后续从搜索结果进入 fetch 时，应尽量复用前一轮的 URL 列表与结构摘要，减少重复塞入上下文

### 功能点 7：避免重复注入与重复读取

系统必须减少对同一大文本的重复传输。

要求：

- 同一 `payload_ref` 的相同 chunk 在同一轮内不应重复注入
- 若 agent 已读过某些 chunk，后续应优先提示继续位置，而不是从头再读
- 工具结果摘要应尽量引用既有载荷，而不是重复复制正文

### 功能点 8：可观测性与调试能力

系统必须能回答以下问题：

- 某次工具结果为什么被降级为摘要模式
- 当前轮有多少字符或 token 被工具结果占用
- 哪些结果被保存为 `payload_ref`
- 某个 payload 被读取了几次、读取了哪些区间
- 该机制总共节省了多少上下文预算

建议记录的指标：

- `toolResultCharsRaw`
- `toolResultCharsInjected`
- `toolPayloadCreated`
- `toolPayloadReadCount`
- `toolPayloadCacheHit`
- `contextBudgetPreventedOverflow`

## 8. 交互与提示词约束

仅靠运行时改动还不够，系统 prompt 与工具描述也必须同步更新，让模型形成稳定用法。

要求：

- 当工具返回 `payload_ref` 时，提示词必须明确告诉模型：若需查看更多，请按段读取，不要重复请求整段全文
- 工具描述应统一强调：面对大结果，优先看 `summary` / `preview` / `range_summary`
- 对文本工具、bash、web 工具，应在提示词中明确“超大文本必须分段处理”的原则
- 若当前剩余预算过低，系统可在工具结果中增加一条 machine-readable 提示，建议模型延后续读或仅读关键块

## 9. 错误处理要求

大载荷治理引入新对象后，必须补齐错误模型。

最低要求包括：

- `payload_not_found`
- `payload_expired`
- `invalid_range`
- `cursor_invalid`
- `payload_too_large_for_inline`
- `budget_insufficient`
- `payload_storage_failed`

错误返回要求：

- 必须提示 agent 使用可行替代路径
- 不应因某个大载荷读取失败而导致整轮 agent loop 崩溃

## 10. 分阶段实施建议

### 第一阶段：快速止血

- 为 bash、web fetch、文本工具接入统一的结果分级逻辑
- 超阈值时不再直接回填全文，而是返回摘要 + 少量预览
- 补充 `ToolCall` 元数据，记录是否创建了 `payload_ref`

### 第二阶段：统一续读协议

- 引入统一 `payload_ref` 存储层
- 新增统一读取入口
- 让 bash / web / file 三类工具共用同一套分段读取 contract

### 第三阶段：增强相关性与导航

- 文件支持命中区间推荐
- Web fetch 支持章节索引与区块提取
- Bash 支持错误段、warning 段、尾部片段等结构化导航

### 第四阶段：UI 与恢复能力

- ToolCall 详情页显示大载荷状态、可读区间和读取历史
- 崩溃恢复或重启后，仍可在 TTL 范围内继续读取最近一次大结果

## 11. 验收标准

以下条件全部满足，才视为本需求完成：

- 读取超大文件时，系统不会默认把整文件内容塞入上下文，而是返回摘要、建议区间或 `payload_ref`
- Bash 产生超长输出时，agent 仍能继续分析结果，但上下文中只出现摘要和小预览，完整输出通过统一协议续读
- Web fetch 抓取长网页或 PDF 时，不会因为正文过长直接挤爆上下文
- 至少文本工具、bash、web fetch 三类工具共享统一的大文本结果壳层
- agent 能基于统一方式继续读取上一份大结果，而不必记住每个工具不同的续读技巧
- 系统可观测层能够展示：原始结果大小、注入大小、是否创建 `payload_ref`、读取次数

## 12. 成功指标

- 工具结果导致的 `max_tokens` / 上下文超预算错误显著下降
- 单轮工具结果总注入字符数明显下降
- agent 在大文件、长日志、长网页场景下的任务完成率提升
- 用户不再需要频繁提醒“请分段读取，不要把全文塞进去”

## 13. 开放问题

- 统一续读入口是做成新工具，还是挂在现有文本工具上扩展 `payload://` 路径语义
- `payload_ref` 应存于 SwiftData、内存缓存、临时文件还是混合方案
- 分段单位应优先按字符、按行，还是优先按语义块
- 历史 `ToolCall` 是否需要显示“预算节省估算”
- 子代理与 workflow worker 是否共享同一 payload 命名空间，还是每次运行独立隔离

## 14. 结论

这不是一个“给某个工具加个 `max_chars`”的问题，而是 agent 运行时的数据流问题。

推荐路线是：以统一大载荷协议层为核心，把你提出的“文件分段读取、bash 长输出落临时文件后续读、web fetch / search 同样不要一次性灌全文”的思路，升级为整个内置工具体系的通用约束。

只有这样，系统才能从“偶尔记得截断”进化到“默认就不会让大文本把上下文吃光”。
