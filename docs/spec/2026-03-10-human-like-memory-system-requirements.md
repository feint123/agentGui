# agentGui 类人分层记忆系统需求说明

日期：2026-03-10

关联对象：ContextMemory、TaskMemory、StoryMemory、主 Agent Loop、Subagent / Workflow Runtime、SwiftData 持久层、Prompt 组装层

## 1. 背景

当前 agentGui 已经有几类记忆雏形，但它们还没有被统一成一套“像人类一样工作”的记忆系统：

- 对话窗口内消息历史承担了最基础的即时记忆作用
- `ContextMemory` 承担了上下文压缩与工作摘要作用
- `TaskMemory` 承担了会话级持久状态作用，更接近任务日志
- `StoryMemory` 承担了创作项目级结构化记忆作用，适合角色、事件、规则、伏笔等长期对象

这些能力已经能支持部分长任务，但仍存在明显问题：

- 记忆类型按“实现来源”划分，而不是按“认知功能”划分
- 缺少瞬时记忆、短期记忆、中期记忆、长期记忆之间的统一流转规则
- 缺少“领域记忆模式”，创作、编码、研究、通用助手仍复用近似同一套逻辑
- 写入、巩固、遗忘、召回、验证仍分散在多个实现中，没有统一治理面
- 长期记忆更多是事实堆积，尚未显式区分情节性记忆、语义记忆、程序性记忆

如果继续在现有基础上逐点加功能，短期内可以工作，但长期会出现：

- Prompt 预算越来越重
- 记忆工具面越来越杂
- 不同任务之间互相污染
- 领域扩展越来越难
- 记忆可信度越来越难审计

因此，需要设计一套面向 agentGui 的类人分层记忆系统，将当前零散能力统一到可扩展架构下。

## 2. 设计目标

本需求的目标是定义一个统一的、模块化的、可扩展的记忆系统，使 agentGui 在不同领域下都能具备更接近人类的记忆工作方式。

核心目标如下：

- 以认知分层为核心，建立瞬时记忆、短期记忆、中期记忆、长期记忆的统一模型
- 在长期层内明确区分情节性记忆、语义记忆、程序性记忆、归档记忆
- 支持领域化记忆模式，使创作记忆和编码记忆可以共享底层机制但拥有不同 schema 与策略
- 建立统一的写入、巩固、检索、遗忘、验证机制，而不是让各领域各写一套临时逻辑
- 保持与现有 `ContextMemory`、`TaskMemory`、`StoryMemory` 的兼容演进，而不是推倒重来
- 为后续多代理协作、后台记忆巩固、记忆审计和质量评估预留清晰接口

## 3. 理论与实践依据

本方案结合当前主流理论与工程实践，采用“理论映射到工程层”的方式设计。

### 3.1 人类记忆分层理论

参考 Atkinson-Shiffrin 多存储模型，可将记忆首先拆成：

- 瞬时记忆：非常短暂地保留当前感知输入
- 短期记忆 / 工作记忆：当前任务正在操作的信息
- 长期记忆：可跨时段保存并按需召回的稳定信息

同时参考 Baddeley 的工作记忆理论，工程上不应把“短期记忆”只理解成消息历史，而应理解成“当前任务可操作的临时认知面板”，其中可以包括：

- 对话上下文
- 当前目标
- 当前子任务状态
- 当前活跃对象
- 当前工具结果

### 3.2 长期记忆类型理论

参考 Tulving 及相关认知心理学划分，长期记忆在工程上至少应拆成：

- 情节性记忆：经历过什么，发生过什么
- 语义记忆：稳定事实、概念、规则、对象关系
- 程序性记忆：如何做事，遵循什么流程、策略、偏好与操作规范

这一定义与当前生产实践高度一致。LangGraph 的 memory 指南也采用了 semantic / episodic / procedural 的工程映射。

### 3.3 Agent Memory 工程实践

结合 Generative Agents、MemGPT、LangGraph 等方案，可提炼出以下共识：

- 当前上下文窗口只能承载最热、最相关的一小部分信息
- 事件流应与稳定事实分离，不能把所有内容都压成一段摘要
- 记忆写入不应只有热路径写入，也应支持后台巩固
- 检索不应只依赖向量相似度，而应结合结构化过滤、时序过滤、对象过滤
- 复杂系统应有明确 write policy、read policy、forget policy 和 audit policy
- 不同任务需要不同的记忆视图，不能用一个固定 prompt slice 解决所有问题

## 4. 当前系统问题定义

结合 agentGui 现状，当前系统的核心缺口有六类。

### 4.1 分层不完整

现有系统大致只有“上下文摘要”“任务持久状态”“创作项目记忆”三类，没有形成从瞬时到长期的统一层级。

### 4.2 记忆类型混用

`TaskMemory` 更偏任务过程日志，`StoryMemory` 更偏项目事实库，两者职责不同，但当前没有被统一抽象成“情节性 / 语义性 / 程序性”能力。

### 4.3 领域无差异

创作任务和编码任务对记忆的需求显著不同：

- 创作任务更强调人物、设定、情节连续性、风格一致性
- 编码任务更强调代码事实、尝试记录、失败原因、验证状态、工作区边界

当前缺少领域模式层，导致扩展新领域时只能不断增加分支逻辑。

### 4.4 缺少巩固与遗忘机制

当前更像“写入一些东西，然后希望后面能用上”，尚未显式定义：

- 什么信息只停留在瞬时层
- 什么信息需要晋升到中期层
- 什么信息值得固化为长期层
- 什么信息过期后应衰减、归档或丢弃

### 4.5 缺少统一治理面

目前记忆写入、提示注入、领域检索、连续性检查、失败反思分布在不同服务里，缺少统一的运行时编排面。

### 4.6 缺少跨领域扩展点

当前只有 StoryMemory 具备比较明确的领域模型，但未来至少还需要：

- Coding Memory
- Research Memory
- User Preference Memory
- Workflow Memory

如果没有统一扩展协议，后续每增加一个领域都会增加系统耦合。

## 5. 总体设计原则

- 分层明确：每一层记忆都有明确的时效、容量、可信度和写入成本
- 领域解耦：领域模式复用底层引擎，但拥有独立 schema、检索器和写入策略
- 结构优先：高价值记忆优先使用结构化或半结构化存储，不把长期关键状态只存成大段文本
- 最小召回：进入 prompt 的永远是当前任务所需的最小相关切片，而不是整个记忆库
- 热冷分离：热路径以低延迟为先，复杂巩固和重写优先走后台流程
- 可验证：关键记忆必须能标注来源、置信度、最后验证时间与适用范围
- 可审计：系统应能回答“这段记忆从哪来、何时写入、由谁写入、是否已被更新或作废”
- 可扩展：新增领域模式时，不应修改核心记忆引擎的基本协议

## 6. 目标记忆分层模型

建议将 agentGui 的统一记忆系统分成六层。

### 6.1 M0：瞬时记忆（Sensory / Immediate Memory）

定义：当前一轮输入中尚未整理为稳定语义的原始刺激。

典型内容：

- 用户最新输入
- 当前工具返回的原始结果
- 当前消息附件的局部内容
- 当前编辑器 / 终端 / 工作区状态快照

要求：

- 生命周期极短，只服务当前一轮或当前步骤
- 默认不持久化为长期真相源
- 可以被提炼进入 M1 或触发后台写入候选

### 6.2 M1：短期工作记忆（Working Memory）

定义：当前任务正在操作的信息面板，是最接近人类工作记忆的一层。

典型内容：

- 当前目标与子目标
- 最近几轮对话摘要
- 当前活跃对象清单
- 当前工具链中间结果
- 当前推理约束、风险和待确认项

要求：

- 与当前线程 / 会话强绑定
- 支持动态裁剪、滑动窗口和摘要刷新
- 优先低延迟读写
- 可从 M0 提炼生成，可向 M2 输出巩固候选

### 6.3 M2：中期任务记忆（Session / Task Memory）

定义：跨多轮会话但仍围绕当前任务、当前项目或当前阶段的操作态记忆。

典型内容：

- 已确认事实
- 已尝试动作
- 失败原因与避免重复尝试的信息
- 当前阶段决策
- 未完成检查项
- 当前项目或当前分支的临时状态

要求：

- 可跨上下文重置继续使用
- 允许持续更新和覆盖
- 默认比长期记忆更容易过期或重整
- 与领域 profile 联动，决定字段形态和生存期

`TaskMemory` 属于该层的现有雏形。

### 6.4 M3：情节性中长期记忆（Episodic Memory）

定义：记录经历、事件、行动序列与上下文经过，是“发生过什么”的记忆层。

典型内容：

- 编码任务中的调查路径、执行轨迹、失败-修复链路
- 创作任务中的章节事件、角色经历、伏笔建立与回收事件
- 研究任务中的检索过程、来源选择、证据链

要求：

- 以时间顺序为核心
- 保留来源和上下文
- 支持按时间、对象、任务阶段进行检索
- 是反思、总结、模式提炼的重要输入

`StoryMemory` 中的 timeline / scene / continuity 数据可视为该层的一部分。

### 6.5 M4：语义长期记忆（Semantic Long-Term Memory）

定义：稳定事实、规则、对象知识、用户偏好、项目设定等长期可复用知识。

典型内容：

- 用户偏好与协作习惯
- 编码领域中的项目结构、接口约束、已验证架构事实
- 创作领域中的角色卡、世界规则、地点档案、风格档案
- 工作流领域中的稳定约束、权限边界、路由规则

要求：

- 必须支持结构化检索和状态更新
- 应区分“稳定事实”“可演化事实”“推测结论”
- 默认是跨会话、跨上下文的主要真相源

### 6.6 M5：程序性与归档记忆（Procedural + Archive Memory）

该层包含两个子域。

子域 A：程序性记忆

- 系统提示词演化结果
- 领域写入策略
- 工具使用偏好
- 任务执行模板
- 失败后的反思规则与恢复策略

子域 B：归档记忆

- 旧版本摘要
- 被替代或作废的设定
- 历史方案快照
- 已关闭但需审计保留的问题记录

要求：

- 默认不直接进入 prompt
- 主要用于治理、回放、溯源和少量按需召回
- 需要明确版本与 superseded 关系

## 7. 领域化记忆模式

统一引擎之上，系统必须支持领域化记忆模式（Memory Domain Profile）。每个领域 profile 决定：

- 本领域有哪些核心对象
- 哪些对象属于情节性记忆
- 哪些对象属于语义记忆
- 何时触发写入
- 何时触发巩固
- 召回时优先哪些切片
- 一致性检查关注什么

### 7.1 创作记忆模式

创作模式应重点支持：

- 角色、地点、世界规则、章节、场景、风格档案
- 剧情事件流、伏笔生命周期、连续性问题
- 当前章节与当前场景的 prompt slice
- 风格一致性、角色一致性、时间线一致性

特征：

- 语义长期记忆比编码场景更重
- 情节性事件流是核心输入
- 强依赖一致性治理

### 7.2 编码记忆模式

编码模式应重点支持：

- 工作区边界、仓库结构、构建方式、测试入口
- 已确认代码事实、接口契约、故障现象
- 已尝试修复、失败原因、待验证项
- 关键文件、关键符号、变更影响面

特征：

- 中期任务记忆比长期人物设定更重要
- 失败反思与验证状态是高价值对象
- 记忆可信度需要与工具证据绑定

### 7.3 通用用户偏好模式

该模式用于保存跨任务稳定偏好，例如：

- 语言偏好
- 输出风格偏好
- 协作方式偏好
- 常用工具或常见禁忌

特征：

- 写入频率低
- 生命周期长
- 应与项目 / 领域事实严格隔离

### 7.4 后续可扩展模式

后续至少应允许新增：

- Research Memory Profile
- Workflow Execution Profile
- Customer Support Profile
- Personal Knowledge Base Profile

新增 profile 不应要求修改核心记忆层协议，只应注册新 schema 与策略。

## 8. 模块化架构需求

系统需要拆成一组清晰可替换的模块，而不是继续把逻辑写进单个服务类中。

### 8.1 Memory Runtime Coordinator

职责：统筹一轮请求中的记忆读写行为。

要求：

- 管理 M0 到 M5 的读写顺序
- 根据领域 profile 决定本轮启用哪些记忆层
- 决定热路径与后台路径的分工
- 产出当前轮次最终 prompt memory slice

### 8.2 Memory Domain Profile Registry

职责：注册和解析领域记忆模式。

要求：

- 支持按任务类型、工作流角色、项目绑定自动选择 profile
- 支持多个 profile 组合，例如“编码 + 用户偏好”
- 支持 profile 版本化，避免 schema 变更破坏旧数据

### 8.3 Memory Store Adapters

职责：对接不同存储后端。

至少需要支持：

- SwiftData 结构化存储
- 本地文件型持久化存储
- 向量索引或语义检索索引
- 归档与版本存储

要求：

- 核心引擎不直接依赖单一存储实现
- 不同层可选择不同存储介质

### 8.4 Memory Consolidation Engine

职责：把 M0 / M1 的内容提炼为 M2 / M3 / M4 的候选项。

要求：

- 支持规则驱动和模型驱动两种巩固路径
- 支持后台异步运行
- 支持候选记忆的合并、去重、冲突检测和升降级

### 8.5 Memory Retrieval Planner

职责：为当前任务制定记忆召回计划。

要求：

- 根据任务意图、领域 profile 和上下文预算选取召回源
- 支持结构化过滤、时间过滤、对象过滤、语义检索混合使用
- 输出面向 prompt 的最小切片，而不是原始对象全集

### 8.6 Memory Governance Layer

职责：统一处理可信度、冲突、遗忘、权限和审计。

要求：

- 记录来源、作者、时间、证据、置信度
- 支持冲突标记、人工确认、软删除、版本替代
- 区分用户级、项目级、会话级、线程级命名空间

## 9. 核心数据要求

所有中长期记忆对象至少应支持以下公共元数据：

- `id`
- `memory_layer`
- `memory_kind`
- `domain_profile`
- `scope`
- `source`
- `source_refs`
- `confidence`
- `created_at`
- `updated_at`
- `last_accessed_at`
- `verification_status`
- `retention_policy`
- `superseded_by`
- `tags`

说明：

- `memory_layer` 用于表示属于 M2 / M3 / M4 / M5 哪一层
- `memory_kind` 用于表示 episodic / semantic / procedural / archive 等类型
- `scope` 至少应区分 user / workspace / project / session / thread / workflow-run
- `source_refs` 用于记录消息、工具输出、文件、场景、章节、测试结果等来源

## 10. 记忆生命周期要求

### 10.1 写入阶段

系统必须区分两类写入。

热路径写入：

- 当前轮必须立即可见的最小写入
- 适用于短期工作记忆更新、少量高确定性状态写入

后台写入：

- 允许延迟执行的总结、反思、聚合、归档和去重
- 适用于事件流抽取、事实巩固、风格提炼、失败模式总结

### 10.2 巩固阶段

系统必须支持从低层向高层的巩固。

示例：

- M0 工具输出提炼为 M1 当前工作状态
- M1 当前工作状态提炼为 M2 当前任务记忆
- 多条 M2 / M3 事件经反思形成 M4 稳定事实
- 多次失败与修复经验沉淀为 M5 程序性规则

### 10.3 遗忘与衰减阶段

系统必须支持至少三种处理方式：

- 过期删除：低价值临时状态在 TTL 后失效
- 归档降温：不再热召回，但保留审计价值
- 覆盖替代：新事实替代旧事实，但保留 superseded 链路

### 10.4 验证与纠偏阶段

高价值记忆必须支持：

- 工具证据验证
- 用户确认写入
- 冲突检测
- 失效标记
- 再验证调度

## 11. 召回与 Prompt 组装要求

### 11.1 最小相关切片原则

任何时候进入 prompt 的都不应是“某层的全量内容”，而应是：

- 当前目标最相关
- 当前预算可承受
- 当前可信度足够
- 当前领域 profile 允许注入

### 11.2 召回优先级

默认优先级建议如下：

1. M1 当前工作记忆
2. M2 当前任务 / 当前项目的中期记忆
3. M3 与当前对象直接相关的事件流
4. M4 稳定规则与事实
5. M5 只有在需要策略或审计时才进入

### 11.3 召回内容分组

返回给主 agent 或 subagent 的记忆结果应默认分组为：

- 已验证事实
- 当前推测
- 风险 / 冲突 / 待确认项
- 建议写入或建议忽略项

这可以避免模型把不确定结论误当成长期真相。

## 12. 与现有系统的映射关系

本需求不是推翻现有实现，而是定义统一演进方向。

建议映射如下：

- 当前消息历史与工具返回原文：映射到 M0
- `ContextMemory`：映射到 M1 的现有实现基础
- `TaskMemory`：映射到 M2 的现有实现基础
- `StoryMemory` 的 timeline / scenes / continuity：映射到 M3
- `StoryMemory` 的 characters / rules / locations / style：映射到 M4
- 反思结果、领域规则、提示策略演化、历史版本：逐步映射到 M5

要求：

- 保持现有功能继续可用
- 通过新增抽象层逐步收敛实现，而不是一次性重写

## 13. 对产品与 UI 的需求

### 13.1 记忆可见性

用户应能知道当前系统在用哪类记忆，而不是把所有行为都隐藏在 prompt 后面。

至少应支持展示：

- 本轮是否命中工作记忆
- 本轮是否读取项目级长期记忆
- 本轮是否触发后台巩固
- 本轮是否发现冲突或待确认写入

### 13.2 记忆管理界面

后续 UI 至少应允许：

- 查看不同 scope 下的记忆对象
- 查看不同 memory layer 的对象统计
- 查看冲突、失效、待确认、已归档对象
- 针对领域 profile 浏览核心对象

### 13.3 用户控制

用户需要至少拥有以下控制项：

- 开启或关闭某类长期记忆
- 控制领域 profile 是否启用
- 控制自动写入与人工确认门槛
- 清理某个 scope 的中期记忆或长期记忆

## 14. 非功能需求

### 14.1 性能

- M1 读写必须低延迟，不显著拖慢主对话链路
- M3 / M4 检索应支持预算控制和分页
- 后台巩固任务不得阻塞主线程交互

### 14.2 可靠性

- 记忆对象写入必须具备幂等与冲突处理能力
- 核心对象需要版本和来源追踪
- 异步巩固失败时不得污染主链路状态

### 14.3 可测试性

系统必须可以分别测试：

- 不同层之间的流转
- 不同领域 profile 的检索与写入策略
- 冲突检测与写入拒绝
- 提示注入预算控制
- 失效与归档逻辑

### 14.4 可扩展性

- 新增领域模式时不应修改核心记忆协调器的主流程
- 存储适配器和检索器应支持替换
- 记忆 schema 需要支持演进和迁移

## 15. 分阶段落地建议

### Phase 1：统一抽象层

- 定义 Memory Layer、Memory Kind、Memory Scope、Domain Profile 等核心协议
- 为现有 `ContextMemory`、`TaskMemory`、`StoryMemory` 建立统一映射
- 引入 Memory Runtime Coordinator，但先不大规模迁移实现

### Phase 2：领域模式与召回治理

- 落地 Creative Profile 与 Coding Profile
- 把 prompt 组装从“按功能写死”迁移到“按 profile 规划召回”
- 落地来源、置信度、状态等公共元数据

### Phase 3：巩固与后台写入

- 引入 Consolidation Engine
- 建立热路径写入与后台巩固分流
- 增加遗忘、归档和再验证机制

### Phase 4：UI 与治理面

- 增加记忆可视化、冲突治理、用户控制面板
- 支持审计和回放
- 支持跨领域 profile 管理

## 15.1 当前迁移状态（2026-03-10）

截至当前实现，统一记忆运行时已经完成第一批可用基座，但仍处于迁移中。

已完成：

- `MemoryLayer`、`MemoryKind`、`MemoryScope`、`MemoryRecord`、`MemoryRuntimeRequest` 等核心抽象
- `creative-writing`、`coding-task`、`user-preferences` 三个基础 profile
- `TaskMemoryStoreAdapter` 与 `StoryMemoryStoreAdapter` 的读侧映射
- `MemoryRetrievalPlanner`、`MemoryPromptAssembler`、`MemoryRuntimeCoordinator`
- 主 Agent loop 启动时优先使用统一读路径注入记忆切片
- `MemoryGovernanceService` 第一版静态规则与 `memory_write` 的受治理包装
- 设置页中的统一运行时 / 治理开关，以及工具详情中的运行时 metadata 可见性

尚未完成：

- 后台巩固驱动的真实写回编排
- 归档、TTL、superseded 链与再验证调度
- 更完整的 UI 治理面与记忆管理面板
- 把 legacy `memory_write`、`TaskMemoryService`、`StoryMemoryService` 全面收敛到统一写路径

## 16. 验收标准

满足以下条件可视为本需求成立：

1. 系统有统一的瞬时、短期、中期、长期分层定义，并能映射当前实现。
2. 系统明确区分 episodic、semantic、procedural、archive 等长期记忆类型。
3. 创作记忆和编码记忆能够共享底层机制，但拥有不同的领域 schema 与策略。
4. 系统具备统一的写入、巩固、召回、遗忘、验证、审计接口。
5. Prompt 注入基于最小相关切片，而不是继续拼接大段全量记忆。
6. 现有 `ContextMemory`、`TaskMemory`、`StoryMemory` 可以作为迁移基底继续演进。
7. 新增一个领域记忆模式时，不需要重写核心记忆引擎。

## 17. 优先级建议

- P0：统一分层模型、统一元数据模型、Creative / Coding 两个领域 profile、召回规划器
- P1：后台巩固、冲突治理、遗忘与归档机制、记忆可见性 UI
- P2：程序性记忆自演化、跨领域联合召回、记忆质量评估体系
