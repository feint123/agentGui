# 测试体系与发布质量需求说明

日期：2026-03-10

关联对象：`agentGuiTests`、`agentGuiUITests`、工作流运行时、工具系统、消息 UI、发布前验证流程

## 1. 背景

当前项目的单元测试已经覆盖了 Markdown 解析、Bash 命令分类、Story Memory 和部分展示逻辑，这是一个不错的基础。但整体质量体系仍偏“功能开发驱动”，缺少真正面向发布的验证分层。

目前最明显的缺口：

- `agentGuiUITests` 仍基本是模板工程
- 缺少跨模块集成测试和端到端场景测试
- 缺少性能基线、回归基线、发布前检查矩阵
- 缺少对工作流、工具权限和恢复场景的系统化验证

## 2. 目标

建立一套覆盖单元、集成、场景、UI、性能和发布前检查的质量体系，让项目可以持续迭代而不依赖人工记忆来防回归。

## 3. 不在本次范围

- 不搭建完整云端 CI 平台
- 不引入复杂的外部测试农场
- 不要求所有功能都一开始达到 100% 自动化

## 4. 功能点

### 功能点 1：测试分层定义

需求：

- 明确五类测试：单元测试、集成测试、场景测试、UI 回归测试、性能测试
- 为每类测试定义覆盖对象、触发时机和最小通过门槛
- 新功能需求文档需标注应补充的测试层级

### 功能点 2：关键用户路径场景测试

需求：

- 至少覆盖以下场景：首次配置 API Key、普通对话、工具调用、Bash 任务、工作流执行、Story Memory 使用、会话恢复
- 场景测试强调“用户目标是否完成”，而不是仅验证单个方法输出

### 功能点 3：UI 自动化回归

需求：

- 把 UI Tests 从模板升级为真实用例
- 覆盖会话列表、消息区、工具详情、工作区切换、设置页、错误提示
- 关键状态切换必须可自动校验，不依赖人工目测

### 功能点 4：性能与稳定性基线

需求：

- 为长消息渲染、Markdown 增量解析、长会话加载、文件树加载、工作流运行建立性能基线
- 为异常场景建立稳定性基线：API 失败、工具失败、保存失败、应用重启恢复

### 功能点 5：发布前检查矩阵

需求：

- 定义发布前必须通过的检查项：构建、单元测试、关键 UI 流程、迁移验证、数据恢复、权限提示、导出路径
- 输出标准化发布清单，而不是每次人工临时决定

### 功能点 6：回归问题沉淀机制

需求：

- 每个线上或手测发现的关键回归都应转化为测试样例
- 建立 bug -> 测试 -> 修复 的闭环记录

## 5. 交互要求

- 开发者应能快速知道某次修改需要跑哪些测试
- 发布前检查不能只存在于口头约定或聊天记录中

## 6. 验收标准

- UI Tests 不再只是默认模板，而是覆盖至少 5 条关键用户路径
- 工作流、工具调用和恢复场景具备至少一层自动化验证
- 发布前存在明确的检查矩阵和执行顺序
- 新增 P0/P1 功能时，需求文档能映射到对应测试层级

## 7. 优先级

- P0：关键路径场景测试、发布前检查矩阵
- P1：真实 UI 自动化、性能基线
- P2：更完整的回归沉淀和稳定性报告
