# 工具扩展框架与生态接入需求说明

日期：2026-03-10

关联对象：`ClaudeService+ToolBuilder`、`ClaudeService+ToolDispatch`、`SkillService`、内置工具体系、未来 MCP / 第三方工具接入

## 1. 背景

当前项目的工具能力已经足够丰富，但注册方式仍以代码硬编码为主。`SkillService` 解决的是提示词技能的加载问题，并没有解决“工具如何被注册、发现、版本协商、授权、禁用和扩展”的问题。

如果后续继续新增工具、接 MCP、做工作流复用或开放社区扩展，当前方式会很快进入不可维护状态。

## 2. 目标

建立一套工具扩展框架，让内置工具、外部工具和未来第三方扩展都能通过统一注册表、统一 schema、统一权限和统一展示层接入。

## 3. 不在本次范围

- 不实现完整的在线工具市场
- 不直接实现远程代码执行平台
- 不替换现有所有工具逻辑，只先搭接入框架

## 4. 功能点

### 功能点 1：统一工具注册表

需求：

- 建立 `ToolRegistry` 或等价抽象，统一管理工具元数据、输入 schema、执行器、可见性、权限需求
- 内置工具不再直接散落在 `buildTools(...)` 的条件分支中
- 工具元数据需要支持名称、分类、版本、描述、风险等级、支持的执行上下文

### 功能点 2：工具能力声明与 schema 版本化

需求：

- 每个工具都需要声明 schema 版本和兼容策略
- 输入参数解析失败时返回结构化错误，而不是仅返回字符串错误
- UI 需要能展示工具版本与 schema 摘要

### 功能点 3：扩展入口统一化

需求：

- 定义三类扩展入口：内置工具、桥接工具、外部协议工具
- 兼容未来接入 MCP Server、本地脚本工具或插件包
- 为每类入口定义生命周期：安装、启用、禁用、更新、卸载

### 功能点 4：工具发现与配置

需求：

- 设置页需要展示全部可用工具，而不是只提供零散布尔开关
- 用户可以查看工具说明、依赖条件、风险级别和启用状态
- 支持按会话或工作流声明需要哪些工具集

### 功能点 5：工具输出标准化

需求：

- 不同工具需要统一输出成功、失败、重试建议、附件、摘要等结构
- 便于消息区、时间线、工作流和导出模块复用
- 工具调用记录与 UI 展示不应强绑定在具体工具实现细节上

### 功能点 6：工具适配层与沙盒联动

需求：

- 扩展工具必须经过统一权限中心审批
- 工具注册时声明所需能力：文件系统、网络、子进程、外部服务
- 未满足依赖或权限的工具不能直接暴露给模型

## 5. 交互要求

- 用户应能清晰知道当前模型实际可调用哪些工具
- 对于未启用或不可用的工具，界面要说明原因
- 工具的启用不能只依赖编译时集成和隐藏配置

## 6. 验收标准

- 新增一个内置工具时，不需要在多个分散位置重复写注册信息
- 工具参数错误可返回结构化校验错误
- 设置页可统一展示工具目录、状态和权限需求
- 桥接类工具或外部协议工具可以通过统一入口挂接

## 7. 优先级

- P0：工具注册表、输出标准化、schema 版本化
- P1：扩展入口与配置 UI
- P2：插件包管理与生态分发机制
