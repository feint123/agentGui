# 2026-03-21 主工作台布局、会话治理与 Liquid Glass 交互重构需求文档

日期：2026-03-21

状态：需求草案

关联对象：`ContentView`、`MainSplitView`、`WorkspacePanelView`、`SessionListView`、`Session`、`ChatView`、`ChatView+Toolbar`、`ChatView+InputArea`、`SettingsBackgroundTasksView`、`BackgroundTaskManagementViewModel`、`BackgroundSessionResultWriter`、`RemoteConversationRouter`、`RemoteConversationBinding`、`SessionProjectionBinding`、`SkillsView`、`ReliabilityCenterView`

## 0. 文档结论

当前主界面最大的结构问题，不是单个控件不够精致，而是信息架构已经被拆散：

1. 主窗口顶层用 `TabView` 在“对话 / Skills / 诊断”之间切换。
2. 主聊天工作台的左栏却只承担 `WorkspacePanelView`。
3. 会话管理退化成聊天页工具栏里的 `Picker`，没有形成真正的一等工作台。
4. 渠道会话与后台任务会话已经存在真实业务链路，但它们只是“普通 Session + 关系绑定”，没有被建模为明确的会话类型。
5. `glassEffect`、`.glass`、`.glassProminent` 已在若干视图落地，但仍是局部点缀，不是统一的界面层语义。

因此，本次需求不能继续在现有布局上打补丁，而应整体重构为：

1. 一个统一的 `Workbench Shell`。
2. 一个明确的 `Session Kind / Session Source / Read-Only Policy` 模型。
3. 一个“后台任务一任务一会话”的自动绑定机制。
4. 一个以 Apple 最新导航层、动效层和 Liquid Glass 指南为约束的视觉与交互体系。

一句话概括本次改造目标：

> 把当前“分散式主界面 + 隐式会话来源 + 局部玻璃效果”升级为“统一工作台 + 显式会话治理 + Apple-native 动效与 Liquid Glass 功能层”。

## 1. 代码 Review 结论

## 1.1 当前主界面结构存在双轨导航

当前根视图有两套顶层导航：

1. `ContentView` 使用 `TabView` 管理“对话 / Skills / 诊断”。
2. `MainSplitView` 再使用 `NavigationSplitView` 管理“工作区 / 编辑器 / 聊天”。

这带来两个直接问题：

1. “Skills / 诊断”脱离了主工作台上下文，不再与当前会话、工作区、编辑器形成连续关系。
2. 左侧栏明明是最适合承载工作台导航的位置，却被 `WorkspacePanelView` 独占。

结论：`ContentView` 顶层 `TabView` 不应继续作为主工作流入口，主导航应收敛到统一的左侧工作台标签栏。

## 1.2 会话已经是核心对象，但还不是可治理对象

当前 `Session` 已具备标题、时间戳、工作目录、执行器偏好，以及与消息、远端绑定、投影绑定的关系，但缺少下列核心语义：

1. 会话类别：本地 / 渠道 / 后台任务。
2. 来源标识：来源任务 ID、来源外部会话 ID、来源渠道类型。
3. 只读策略：当前是否允许手工输入、删除、清空、重命名。
4. 展示元数据：来源摘要、只读原因、分类图标、来源状态。

这导致现有系统只能“推断”会话来源，而不能“表达”会话来源。

结论：会话分类、搜索、只读和自动化绑定，都必须建立在显式模型之上，不能继续依赖关系表侧推。

## 1.3 会话管理入口退化，无法支撑数量增长

当前会话管理有三个明显短板：

1. 主工作台里没有一等的会话目录，只有聊天工具栏里的 `Picker`。
2. `SessionListView` 存在，但不是主工作台第一入口。
3. 缺少搜索、分类、重命名、来源标签和状态筛选。

这意味着只要会话数量稍大，用户就会陷入“知道会话存在，但不知道去哪找”的状态。

结论：会话目录必须回到左侧主工作台，并提供按类型分组、搜索、筛选和有限编辑能力。

## 1.4 后台任务链路与目标需求正面冲突

当前后台任务创建流程明确要求用户手动选择一个已存在会话：

1. `BackgroundTaskManagementViewModel` 把 `draftSessionID` 视为必填字段。
2. `makeNewTask()` 默认将其设置为第一个可用会话。
3. `saveDraft()` 保存时要求 `draftSessionID` 非空。
4. `BackgroundSessionResultWriter` 只会把结果写回该既有会话。

这与“新建后台任务后自动创建并绑定后台任务会话”的目标完全相反。

结论：后台任务必须从“绑定既有会话”切换为“持有自己专属会话”。

## 1.5 渠道和后台任务会话还没有真正只读

当前代码已经会自动创建渠道会话、自动往后台任务目标会话写回结果，但这些会话仍被当作普通会话：

1. `RemoteConversationRouter` 在收到渠道消息时会新建 `Session`，但不会写入只读语义。
2. `ChatView` 发送逻辑不会根据会话来源阻止用户手动输入。
3. 会话删除、清空、执行器切换、标题修改也没有来源级限制。

结论：渠道和后台任务会话必须升级为“来源驱动的只读会话”，而不是“普通会话上的业务约定”。

## 1.6 Liquid Glass 已局部使用，但缺少统一策略

当前仓库已经使用以下能力：

1. `glassEffect`
2. `GlassEffectContainer`
3. `.buttonStyle(.glass)`
4. `.buttonStyle(.glassProminent)`

但问题也很明显：

1. 使用点分散在输入区、编辑器浮层、设置字段、Onboarding 等局部区域。
2. 没有统一约束哪些区域属于“导航层 / 功能层 / 内容层”。
3. 没有形成统一的 morph、grouping、scroll-edge、background extension 规则。

结论：本次需求必须把 Liquid Glass 从“局部视觉效果”提升为“导航与高价值交互层的材质规范”。

## 2. 外部调研结论

本次需求参考了 Apple 关于 Liquid Glass 与系统导航层的公开资料，核心约束如下：

1. 优先使用标准 `NavigationSplitView`、toolbar、sidebar、sheet、control，让系统自动获得最新的 Liquid Glass 外观与行为。
2. 自定义控件上的 Liquid Glass 需要节制使用，只应用在最重要的功能层，而不是铺满内容层。
3. 多个玻璃元素应放在 `GlassEffectContainer` 中，以获得更好的渲染性能以及元素间融合、形变和过渡表现。
4. `glassEffect` 应在布局和视觉修饰之后应用，否则捕获到的形状与内容外观不一致。
5. 自定义交互组件应优先使用 `.glass` / `.glassProminent` 按钮风格，而不是自己叠一层自制玻璃背景。
6. 导航层应和内容层明确分离，侧边栏、工具栏、搜索与关键动作浮在上层，内容仍保持可读、可聚焦。
7. 自定义动效应服务于状态表达、阶段切换和结构收束，而不是持续性噪音。

这意味着本次改造不能理解为“多加一点玻璃和动画”，而必须遵守：

1. 内容层尽量保持轻背景、低装饰。
2. 导航层与功能层承担主要材质表达。
3. 动画只在切换、聚焦、生成、收束、只读锁定等有明确语义的场景中出现。

## 3. 目标

本次需求目标如下：

1. 将主窗口升级为统一的左侧工作台架构，左栏可在“会话 / 工作区 / 技能 / 诊断”之间切换。
2. 将会话升级为显式分类、可搜索、可筛选、可治理的对象。
3. 为后台任务建立“一任务一专属会话”的自动创建与绑定机制。
4. 将渠道会话与后台任务会话定义为只读会话，并在 UI 与行为层真正执行只读约束。
5. 建立符合 Apple 设计规范的动画系统与 Liquid Glass 使用规范，并在文档中明确 API、使用方式和场景。

## 4. 非目标

本次需求不包含以下内容：

1. 不在第一期内重做文件编辑器本体。
2. 不在第一期内重做聊天消息气泡视觉语言。
3. 不在第一期内扩展渠道种类，只基于现有渠道链路定义会话治理规则。
4. 不在第一期内引入云同步、多人共享或跨设备会话合并。
5. 不在第一期内把后台任务中心从设置页完全迁出，但必须重做其会话绑定逻辑。

## 5. 方案比较

### 方案 A：保留顶层 `TabView`，只把左栏从 `WorkspacePanel` 扩成多标签

优点：

1. 改动相对局部。
2. 当前 `SkillsView` 和 `ReliabilityCenterView` 可继续复用。

缺点：

1. 顶层导航和左侧导航会继续并存。
2. 用户仍然要在两个不同层级理解“我现在在哪个工作区”。
3. 会话、技能、诊断仍然不是一个统一工作台。

### 方案 B：收敛为单一 `Workbench Shell`，左侧承载全部主工作台入口

优点：

1. 信息架构清晰，所有高频入口回到统一壳层。
2. 会话、工作区、技能、诊断能共享相同的上下文与视觉层级。
3. 最符合 Apple 对导航层和内容层分离的建议。

缺点：

1. 需要调整 `ContentView` 的顶层结构。
2. 需要重新梳理 `SkillsView` 和 `ReliabilityCenterView` 在主窗口内的承载方式。

### 方案 C：继续保留当前结构，但新增一个独立“会话中心”窗口

优点：

1. 改动可避开主工作台。
2. 实现路径看似最短。

缺点：

1. 会把会话治理进一步推向次级场景。
2. 与用户提出的“左侧边栏通过 tab 页切换”目标不一致。
3. 会话、技能、诊断、工作区仍然分散。

### 推荐

推荐采用方案 B。

原因很直接：这次不是单点增量，而是主工作台语义重整。继续保留双轨导航只会让后续改造越来越难收敛。

## 6. 顶层信息架构需求

## 6.1 新的主窗口结构

主窗口必须重构为单一 `Workbench Shell`，由统一的 `NavigationSplitView` 承载。

左侧第一列不再固定是 `WorkspacePanelView`，而是 `WorkbenchSidebar`，包含四个工作台标签：

1. 会话
2. 工作区
3. 技能
4. 诊断

要求：

1. 标签切换状态必须可持久化。
2. 左侧标签必须是主导航，而不是辅助导航。
3. 当前所选标签必须在视觉上具有明确的系统级高亮与动效反馈。

## 6.2 各标签承载规则

### 会话

左列显示会话目录、搜索、筛选与分类。

主内容区要求：

1. 保持当前文件编辑器与聊天协作模式可用。
2. 选中会话后，聊天区继续显示该会话内容。
3. 若未选中会话，显示“创建本地会话”空状态。

### 工作区

左列显示当前 `WorkspacePanelView` 的能力集合，包括文件树、工作区搜索、LSP 状态、Git 相关上下文。

主内容区保持现有编辑器和聊天协作模式。

### 技能

不再通过顶层 `TabView` 进入。

要求：

1. 左列显示技能分组或安装概览。
2. 主内容区显示技能启用、描述、刷新与管理视图。
3. 需要保留当前技能开关能力，但承载到统一工作台中。

### 诊断

不再通过顶层 `TabView` 进入。

要求：

1. 左列显示诊断分组或关键健康项摘要。
2. 主内容区显示可靠性中心、恢复项、运行时状态、关键问题列表。
3. 保持与当前会话上下文可联动，而不是脱离主工作台单独存在。

## 6.3 顶层 `TabView` 收敛要求

当前 `ContentView` 中承载“对话 / Skills / 诊断”的顶层 `TabView` 不应继续作为主产品入口。

需求：

1. 主窗口顶层入口必须收敛为单一工作台壳层。
2. `SkillsView` 与 `ReliabilityCenterView` 应转为工作台内部页面。
3. 不允许出现“同一套主功能既能从顶层 Tab 进，也能从左栏 Tab 进”的双重入口。

## 7. 会话模型与治理需求

## 7.1 会话必须显式分型

`Session` 需要新增显式会话类型语义。

建议最小分类：

1. `local`
2. `channel`
3. `backgroundTask`

每个会话还需要最少具备以下来源元数据：

1. `sourceKind`
2. `sourceIdentifier`
3. `sourceDisplayName`
4. `isReadOnly`
5. `readOnlyReason`

要求：

1. 不允许继续通过关系表侧推“这大概是渠道会话”或“这大概是后台会话”。
2. UI 列表、搜索、筛选、权限与行为判断都必须依赖显式类型。

## 7.2 会话目录必须按类别组织

会话目录至少支持以下一级分类：

1. 本地
2. 渠道
3. 后台任务

目录要求：

1. 默认按类别分组展示。
2. 组内按最近更新时间排序。
3. 每一类会话需要显示来源图标、来源标签和状态提示。

本地会话至少显示：

1. 标题
2. 最近摘要
3. 更新时间

渠道会话至少显示：

1. 渠道类型
2. 外部会话或外部用户摘要
3. 是否只读
4. 最近外部活动时间

后台任务会话至少显示：

1. 任务标题
2. 调度状态摘要
3. 是否只读
4. 最近运行时间或最近结果时间

## 7.3 会话搜索必须成为一等入口

会话目录必须提供搜索框，不能隐藏在二级菜单。

搜索范围至少包括：

1. 会话标题
2. 最近消息摘要
3. 来源展示名
4. 渠道会话的外部会话标识或用户标识
5. 后台任务会话的任务标题

要求：

1. 搜索输入应在当前工作台左栏顶部固定可见。
2. 搜索结果需要保留分类语义，而不是完全丢失来源类型。
3. 搜索无结果时应给出按类别解释的空状态。

## 7.4 会话重命名规则

重命名必须支持，但不是对所有类型一刀切。

规则：

1. 本地会话允许重命名。
2. 渠道会话不允许用户手工重命名。
3. 后台任务会话不允许用户手工重命名。

原因：

1. 渠道与后台任务会话需要维持来源一致性和只读语义。
2. 后台任务会话标题应与任务标题保持一致，不应被人工打散。

要求：

1. 本地会话提供右键、快捷操作或内联重命名。
2. 只读会话在菜单中仍可看到“不可重命名”的说明，但操作应禁用。

## 7.5 会话删除规则

删除行为也必须按类型收敛：

1. 本地会话允许直接删除，保留二次确认。
2. 渠道会话不允许直接删除为普通操作，建议提供“隐藏 / 归档 / 停止接收后再删除”的来源级流程。
3. 后台任务会话不允许绕过任务生命周期直接删除。

后台任务会话删除要求：

1. 默认通过后台任务详情入口处理。
2. 删除后台任务时必须允许用户选择：只删除任务，或任务与关联会话一并删除。

## 8. 后台任务自动会话绑定需求

## 8.1 移除手动会话选择

新建后台任务时，不再允许用户手动选择现有会话。

要求：

1. 后台任务表单中移除“结果写回会话”选择器。
2. `draftSessionID` 不再作为新建任务的必填输入。
3. 后台任务创建成功后，系统必须自动创建一个类型为 `backgroundTask` 的专属会话。

## 8.2 一任务一会话

后台任务必须与专属会话形成 1:1 关系。

要求：

1. 首次保存任务时自动创建会话。
2. 后续编辑同一任务时复用原会话，不重复创建。
3. 任务标题更新后，其会话标题需要同步更新。
4. 会话来源信息必须能反查到任务 ID。

## 8.3 任务表单需要改为“会话预览”而不是“会话选择”

后台任务编辑界面应展示：

1. 系统自动生成的会话标题。
2. 当前绑定状态。
3. 打开关联会话的快捷入口。

但不应再显示“让我把这个任务结果写回哪个已有会话”的设计。

## 8.4 结果回写链路必须改为专属会话

后台任务运行结果必须只写回该任务的专属会话。

要求：

1. 成功结果写回时不允许漂移到其他人工会话。
2. 失败结果也写回同一专属会话，保证审计连续性。
3. 会话更新必须能反映最近一次任务状态。

## 9. 渠道会话与后台任务会话只读需求

## 9.1 只读语义定义

本次“只读”不只是“输入框灰掉”，而是完整的交互约束。

只读会话至少禁止以下操作：

1. 手工发送消息。
2. 手工附加文件并发送。
3. 清空当前会话消息。
4. 删除单条消息后续链路。
5. 手工修改执行器偏好。
6. 手工重命名会话。

## 9.2 渠道会话只读规则

渠道会话只能由渠道入站消息驱动。

要求：

1. 聊天输入区在渠道会话中必须切换为只读态。
2. 必须显示来源说明，例如“该会话来自飞书渠道，只能通过渠道消息驱动”。
3. 会话仍应允许查看完整历史和执行结果。

## 9.3 后台任务会话只读规则

后台任务会话只能由调度器和后台运行时写入。

要求：

1. 聊天输入区在后台任务会话中必须切换为只读态。
2. 必须显示来源说明，例如“该会话由后台任务写回，只能在后台任务设置中调整”。
3. 需要提供“打开关联后台任务”的快捷入口。

## 9.4 只读会话的推荐补偿动作

为避免只读会话成为死路，必须提供“转本地继续”的补偿路径。

要求：

1. 只读会话应提供“复制为本地会话”或“基于当前内容创建本地会话”的操作。
2. 复制后的新会话类型为 `local`，并恢复可编辑能力。

## 10. 技能与诊断工作台需求

## 10.1 技能页并入主工作台

当前技能页能力需要保留，但入口必须收敛到左侧工作台。

需求：

1. `SkillsView` 的核心能力继续保留。
2. 技能页进入后仍应支持技能启用、关闭、刷新与说明展示。
3. 不再与主聊天工作流割裂。

## 10.2 诊断页并入主工作台

当前可靠性 / 诊断相关能力需要保留，但入口必须收敛到左侧工作台。

需求：

1. `ReliabilityCenterView` 的核心能力继续保留。
2. 诊断页应支持从当前会话上下文进入相关问题。
3. 诊断页在视觉上属于工作台功能层，而不是另一个独立应用。

## 11. 动画系统需求

## 11.1 动画原则

所有动画必须满足以下原则：

1. 表达状态变化，而不是制造持续性视觉噪音。
2. 主要服务于聚焦、切换、创建、锁定、收束。
3. 不允许用大面积无限循环动画替代结构反馈。
4. 需要兼容系统的减少动态效果设置。

## 11.2 必须重点增强的动画场景

### 场景 A：左侧工作台标签切换

需求：

1. 当前标签的选中状态需要带有系统级材质变化。
2. 标签切换需要带有平滑的焦点转移和内容入场。
3. 切换不能只是瞬间替换左栏内容。

### 场景 B：会话目录分类展开与搜索过滤

需求：

1. 分类段落的展开收起应具有层次动画。
2. 搜索结果收敛时，应优先使用内容收束和轻量淡入淡出，而不是整列表抖动。

### 场景 C：后台任务创建成功

需求：

1. 新任务保存成功后，专属会话出现在会话目录中时，应有明确但克制的新增反馈。
2. 任务与会话绑定成功时，应在后台任务页和会话目录之间形成一次清晰的状态确认。

### 场景 D：只读态切换

需求：

1. 输入区切换到只读态时，不应只是直接消失。
2. 必须通过材质、文案和布局形变表达“这是一个来源受控会话”。

### 场景 E：技能页与诊断页进入主工作台

需求：

1. 进入技能或诊断标签时，需要有明显的场景切换感。
2. 但不应打断当前会话与工作区状态。

## 12. Liquid Glass 使用规范

## 12.1 总体原则

Liquid Glass 只应用在导航层和高价值交互层，不进入大面积内容背景。

当前工程的 macOS deployment target 已提升到 26.0，因此本次需求可以直接采用原生 Liquid Glass API，不需要为了主应用目标额外设计旧系统降级版视觉语义。约束重点不在“能不能用”，而在“该在哪些场景用、该避免哪些滥用”。

允许重点使用的区域：

1. 左侧工作台标签栏。
2. 会话目录顶部搜索与筛选条。
3. 会话目录中的关键筛选胶囊和快捷动作组。
4. 聊天输入区外壳。
5. 只读会话的来源提示条与主要补偿动作。
6. 主工具栏中的高价值动作组。

不建议使用的区域：

1. 整个消息列表背景。
2. 整个文件编辑器背景。
3. 大面积列表行背景全量玻璃化。
4. 设置页的所有表单项一刀切玻璃化。

## 12.2 需要使用的 API、使用方式与场景

### API 1：`GlassEffectContainer`

使用方式：把相互靠近、可能发生融合或形变的玻璃元素包进同一个容器。

推荐场景：

1. 左侧工作台标签组。
2. 会话筛选胶囊组。
3. 聊天工具栏中的关联动作组。

示例：

```swift
GlassEffectContainer(spacing: 16) {
    HStack(spacing: 12) {
        // 标签按钮 / 筛选胶囊 / 快捷动作
    }
}
```

### API 2：`.glassEffect(_:in:)`

使用方式：在布局、padding、shape 设定完成之后应用玻璃效果。

推荐场景：

1. 会话搜索条容器。
2. 只读来源提示条。
3. 聊天输入区容器。

示例：

```swift
searchBar
    .padding(.horizontal, 12)
    .padding(.vertical, 10)
    .glassEffect(.regular, in: .rect(cornerRadius: 16))
```

### API 3：`.glassEffect(.regular.interactive(), in: ...)`

使用方式：仅对可点击、可聚焦、可切换的元素启用交互式玻璃。

推荐场景：

1. 左侧工作台标签按钮。
2. 会话筛选胶囊。
3. 只读提示条中的主动作按钮周边控件。

要求：

1. 静态展示元素不要滥用 `.interactive()`。
2. 所有交互式玻璃元素必须具备可访问性标签。

### API 4：`.buttonStyle(.glass)`

使用方式：用于导航层和辅助动作层的标准按钮。

推荐场景：

1. 工作台标签按钮。
2. 会话目录里的辅助动作。
3. 只读会话中的“打开来源设置”类操作。

### API 5：`.buttonStyle(.glassProminent)`

使用方式：用于少量高优先级动作。

推荐场景：

1. 新建本地会话。
2. 复制为本地会话。
3. 新建后台任务。

要求：

1. 同一区域中 prominent 动作不能过多。
2. 不允许所有按钮都变成 prominent。

### API 6：`.glassEffectID(_:in:)` 与 `GlassEffectTransition`

使用方式：用于同类元素间的选中态迁移和材质形变。

推荐场景：

1. 左侧工作台标签的选中态切换。
2. 分类筛选胶囊从一个选项切到另一个选项时的形变。
3. 输入区从可编辑态切到只读态的提示条形变。

### API 7：`.backgroundExtensionEffect()`

使用方式：让内容视觉上“延展到”侧边栏或检查器背后，提升分栏结构的一体感。

推荐场景：

1. 工作区标签下的编辑器与聊天主背景。
2. 会话标签下的主内容背景，与左侧目录形成连续层次。

## 12.3 Liquid Glass 约束要求

1. 必须复用标准形状与圆角，不允许在同一区域混用大量不相关曲率。
2. 必须优先使用系统按钮样式，不鼓励手工堆叠自制玻璃按钮。
3. 同屏玻璃元素数量必须受控，避免密集叠加。
4. 涉及列表滚动的自定义浮层需要关注与滚动内容的可读性关系。
5. 不允许把 Liquid Glass 当成默认背景填充方案。

## 13. 视图与状态边界需求

## 13.1 需要新增统一工作台状态

主工作台必须拥有独立的壳层状态，不应把“当前工作台标签”塞回 `WorkspaceState.selectedSession` 一类业务状态中。

至少需要管理：

1. 当前工作台标签。
2. 会话目录搜索词与筛选条件。
3. 各工作台标签的局部滚动与展开状态。

## 13.2 需要新增统一会话目录层

会话搜索、分类、重命名、只读判断、来源映射不应继续散落在视图里。

必须抽象出统一目录层，承担：

1. `Session` 到目录展示项的映射。
2. 来源类型到只读策略的映射。
3. 分类、搜索、排序和筛选。

## 13.3 后台任务需要独立的会话工厂

后台任务会话的创建与绑定逻辑不应散落在表单视图与结果写回器中。

必须有明确职责边界：

1. 创建任务时负责创建并绑定会话。
2. 编辑任务时负责复用并校验绑定会话。
3. 删除任务时负责处理关联会话的删除或保留策略。

## 14. 测试需求

## 14.1 单元测试

至少覆盖：

1. 会话类型映射与来源元数据解析。
2. 渠道会话与后台任务会话的只读判定。
3. 后台任务首次保存时的自动会话创建。
4. 同一后台任务重复保存时的会话复用。
5. 本地会话允许重命名，渠道 / 后台任务会话禁止重命名。

## 14.2 集成测试

至少覆盖：

1. 渠道入站消息触发渠道会话创建。
2. 后台任务运行结果写回其专属会话。
3. 任务标题变更后会话标题同步更新。
4. 删除后台任务时的关联会话处理策略。

## 14.3 UI 测试

至少覆盖：

1. 左侧工作台标签切换。
2. 会话目录按本地 / 渠道 / 后台任务分类展示。
3. 会话搜索。
4. 本地会话重命名。
5. 渠道会话输入区只读。
6. 后台任务会话输入区只读。
7. 新建后台任务后自动生成专属会话。
8. 技能页与诊断页从左侧工作台进入。

## 15. 验收标准

满足以下条件，视为本需求完成：

1. 主窗口左侧栏可以在“会话 / 工作区 / 技能 / 诊断”之间切换，且不存在双重主导航。
2. 会话目录能清晰区分本地、渠道、后台任务三类会话。
3. 会话目录支持搜索与本地会话重命名。
4. 新建后台任务不再要求手动选择会话，保存成功后会自动创建并绑定专属会话。
5. 渠道会话和后台任务会话在聊天区为只读态，并显示来源说明。
6. 用户可以从只读会话复制出一个本地可编辑会话继续工作。
7. 动画和 Liquid Glass 已用于导航层与关键交互层，且不破坏内容可读性。

## 16. 风险与约束

本次需求必须特别警惕以下风险：

1. 如果只新增左侧标签而不移除顶层 `TabView`，将继续保留双轨导航结构债。
2. 如果不引入显式会话类型模型，后续只读逻辑和后台绑定逻辑仍会四处分叉。
3. 如果后台任务继续允许绑定普通会话，用户数据会在人工会话与调度会话之间持续混杂。
4. 如果把 Liquid Glass 大面积铺到内容层，会直接违背 Apple 的导航层优先原则。
5. 如果只把输入框设为 disabled，却不处理删除、重命名、清空等行为，所谓“只读会话”会停留在表面。

## 17. 最终建议

本次需求不应被理解为“把左侧栏多塞三个页面”，而应被理解为一次主工作台收敛：

1. 左侧栏从单一 `WorkspacePanel` 升级为统一 `Workbench Sidebar`。
2. 会话从普通聊天记录升级为带来源、带权限、带治理的对象。
3. 后台任务从“借用人工会话写回”升级为“持有专属只读会话”。
4. 技能与诊断从顶层平行页面收敛回主工作台。
5. Liquid Glass 与动画从“点缀”升级为“导航层与关键动作层的系统化表达”。

如果后续要进入实施阶段，建议先以本文件为基准拆出单独的实现计划文档，而不是直接在现有视图上零散改动。
