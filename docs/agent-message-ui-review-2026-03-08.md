# agentGui Message 样式与交互改造建议

日期：2026-03-08

## 1. 评审目标

本文聚焦当前 agent message 区域的样式与交互，重点回答三个问题：

1. 现有交互为什么“不理想”
2. 主流 agent 产品在消息区通常如何处理“回答、过程、工具、状态”四类信息
3. agentGui 下一版应该如何改，才能既保留 agent 感，又不破坏阅读效率

本次评审基于以下现状实现：

- `agentGui/Views/ChatView+MessageList.swift`
- `agentGui/Views/MessageBubbleView.swift`
- `agentGui/Views/ThinkingBubbleView.swift`
- `agentGui/Views/ToolCallBubbleView.swift`
- `agentGui/Views/AgentStepTimelineView.swift`
- `agentGui/Views/SubagentTimelineView.swift`

对照参考不是某一个产品的外观复制，而是主流 agent 产品的共通设计策略，主要可归纳为以下几类：

- Claude / ChatGPT：优先稳定呈现最终回答，过程信息按需展开
- Cursor / Devin / OpenHands 类 coding agent：将执行过程做成独立状态流，不与正文抢主层级
- Perplexity / 搜索型 agent：把“答案”和“证据来源”拆层，避免正文被过程信息打断

结论先说：当前 agentGui 的问题不在于单个控件不好看，而在于“消息正文、thinking、round timeline、tool call”被同时放到了一个阅读平面上。用户在看回答时容易被过程打断，在看过程时又缺少一个清晰的执行主线。

## 2. 当前设计的核心问题

### 2.1 主回答缺少稳定的视觉锚点

当前 agent 消息是“扁平全宽内容 + 上方轻量 header + 下方直接堆叠过程内容”。这会带来两个问题：

- 当一条消息同时包含正文、thinking、tool call、timeline 时，用户很难一眼判断“最终回答到底在哪”
- 消息没有形成一个稳定的主卡片，阅读焦点会在多个小块之间来回跳

主流 agent 的一个共识是：最终回答必须是第一阅读目标，执行过程只能作为辅助层。现在的实现里，过程信息经常和正文同级，导致视觉重心不稳。

### 2.2 过程信息暴露过多，但缺少抽象

`AgentStepTimelineView` 和 `ToolCallBubbleView` 已经把执行过程完整地露出来了，但目前更像“原始日志可视化”，而不是“用户可理解的执行叙事”。

典型问题：

- 每轮 round 都直接展示 thinking、text、tool call，信息粒度偏底层
- tool call 以单次调用为单位展开，缺少批量归纳
- 子代理也沿用同一套时间线结构，层层嵌套后阅读负担迅速上升

这类设计对开发者调试有价值，但对正常对话并不友好。主流产品通常不会默认展示“完整原子步骤”，而是先展示“本轮在做什么”，只有用户主动展开才看细节。

### 2.3 Thinking 的层级过高，且表现方式不对

`ThinkingBubbleView` 现在使用紫色描边、材质背景、独立折叠卡片，视觉存在感很强。但在主流 agent 设计里，thinking 通常不会作为正文同等级内容强展示。

原因很简单：

- 用户通常关心的是结论，不是完整推理原文
- thinking 一旦视觉权重过高，会让界面显得“总在解释自己”，而不是“正在完成任务”
- 大段思考文本的阅读效率很低，尤其在连续多轮 tool use 时

更合理的做法是把 thinking 降级为“过程摘要”或“推理片段”，默认隐藏在过程层，而不是作为一个高存在感的小卡片反复插入时间线。

### 2.4 工具调用卡片太像日志，不像行动反馈

`ToolCallBubbleView` 当前的信息结构偏技术实现视角：状态图标、工具名、命令、diff、输出。这种结构对调试是好的，但普通用户更需要先知道三件事：

1. 它在做什么
2. 是否成功
3. 产生了什么结果

现在的问题是：

- 执行命令、编辑文件、读取文件、子代理这些行为都采用近似相同的卡片结构
- 工具输出默认以原始文本块呈现，缺少摘要层
- 用户需要自己从日志里提取结果，系统没有帮他完成“翻译”

主流 agent 更常见的模式是：先给一句动作摘要，例如“已读取 3 个文件”“已修改 2 处代码”“命令执行失败，原因是端口占用”，再允许用户查看原始输出。

### 2.5 时间线设计表达了“顺序”，但没有表达“状态”

当前时间线能表达 round 的先后顺序，但用户依然不容易回答这些问题：

- 现在卡在哪一步
- 这一轮是探索、执行、失败还是等待用户
- 整条消息目前是否还在工作中

原因是时间线节点主要表达内容类型，而不是任务状态。圆点颜色的语义也比较弱，更多是装饰，不足以承担系统状态表达。

主流 agent 会把“当前活跃步骤”做成一个明确的状态行，或者一个持续更新的执行条，而不是只依赖时间线来传达进度。

### 2.6 Hover 才出现的操作过于隐蔽

`MessageBubbleView` 的复制、重试、重新生成、删除等操作依赖 hover 才出现。这在 macOS 上不是不能用，但存在两个问题：

- 发现成本高，新用户不容易知道消息可操作
- 危险操作和高频操作被放在同一组轻量图标里，权重区分不够

更稳妥的做法是：

- 高频操作保留显式入口，例如复制、重新生成
- 低频或破坏性操作放到更多菜单里
- 对当前活跃消息提供更稳定的控制条，而不是完全依赖 hover

### 2.7 流式过程中缺少一个“单一工作焦点”

当前流式状态主要靠消息底部的 `ProgressView` 和若干 in-progress 的 tool call 卡片表达。问题是界面在流式阶段会同时动很多地方：

- 正文在变
- timeline 在增量插入
- tool call 自动展开
- 底部还有“正在思考…”

这会让界面显得忙，但不清楚。主流 agent 一般会在流式时给用户一个单一焦点：

- 正在起草回答
- 正在读取文件
- 正在运行命令
- 正在等待工具结果

其它细节延后再看。

## 3. 主流 Agent 产品的共通设计规律

这部分不谈具体品牌外观，只谈成熟交互里反复出现的共识。

### 3.1 答案优先，过程后置

用户的第一任务是“理解回答”，不是“观看内部机制”。因此主消息区通常遵循：

- 第一层：最终回答或阶段性回答
- 第二层：执行摘要
- 第三层：原始过程和工具细节

当前 agentGui 最大的问题，正是把第二层和第三层提得太前。

### 3.2 过程默认摘要化，而不是原子化

成熟 agent 不会默认把每一次内部动作全部摊开，而是先做过程归纳，例如：

- 查看了哪些资源
- 做了哪些修改
- 遇到了什么阻塞
- 下一步准备做什么

只有在用户显式需要验证、审查、调试时，才展开原始步骤。

### 3.3 正文、状态、工件分区

主流设计往往把一条 agent 消息拆成三个区域：

- 正文区：自然语言回答
- 状态区：执行中、已完成、失败、等待输入
- 工件区：文件改动、命令输出、引用来源、子任务结果

现在 agentGui 把这些内容都混在一个垂直流里，导致信息结构不清。

### 3.4 当前活动步骤必须强感知

当 agent 正在工作时，用户最关心的不是完整历史，而是“现在正在干什么”。主流产品通常会把当前步骤做得非常明确：

- 单独一行状态
- 一个可展开的活动条
- 或一个 stick 到当前消息底部的 live panel

这能显著降低焦虑感。

### 3.5 调试视图与默认视图分离

很多 agent 产品内部其实有大量中间步骤，但默认模式只展示摘要。详细日志通常被放入：

- 展开区
- Inspector
- 侧边栏
- 开发者模式

这个原则很重要。因为“好用的 agent UI”和“好调试的 agent UI”通常不是同一个界面层级。

## 4. 对 agentGui 的重构建议

## 4.1 总体方向：从“消息时间线”改成“回答卡 + 执行条 + 工件抽屉”

建议下一版把 agent message 的结构调整为：

1. 回答卡（默认展开）
2. 执行摘要条（默认展开，但高度很小）
3. 工件抽屉（默认折叠）

对应含义：

- 回答卡承载用户真正要读的内容
- 执行摘要条承载“正在做什么 / 做过什么”
- 工件抽屉承载 tool call、diff、终端输出、子代理明细等重内容

这会让一条复杂 agent 消息的主结构清晰很多。

建议信息层级如下：

### 第一层：回答卡

- 使用更稳定的卡片容器承接 agent 正文，而不是扁平散落在页面上
- 强化排版宽度控制、段落间距和标题层级
- 将消息头部和正文合并成一个统一容器，避免 header 飘在内容外面

### 第二层：执行摘要条

示例文案：

- 已读取 4 个文件，正在整理答案
- 正在运行 1 个命令
- 已修改 3 个文件
- 执行失败，点击查看详情

这个摘要条应该是当前消息的状态锚点，永远比完整时间线更先看到。

### 第三层：工件抽屉

这里再放：

- tool call 明细
- 文件改动 diff
- 命令原始输出
- 子代理过程
- thinking 详情

这样可以把高密度技术细节放到需要时才打开的层里。

## 4.2 回答卡要重新做成稳定的主消息组件

建议把 agent 消息重心放回正文，并建立明确的容器感。

推荐改法：

- agent 消息不再是完全扁平的 full-width 内容，而是带轻边界和更稳定内边距的“回答卡”
- user message 保持右对齐，但 agent message 也要拥有自己的卡片主体，否则两边语言不对等
- 时间戳、模型名、状态不要占据正文上方太多视觉资源，尽量压缩到次级 header

样式建议：

- 少用紫色和多重材质叠加，减少“插件感”
- agent 正文容器优先清晰度，不优先花哨质感
- 将正文最大宽度与 tool detail 最大宽度分离；正文可稍宽，日志可更窄

一句话概括：要让用户感觉自己在读“答案”，而不是在看“执行控制台”。

## 4.3 把 Thinking 从“内容块”改成“过程元信息”

这是最值得调整的一项。

建议不要继续让 `ThinkingBubbleView` 在时间线里反复作为一个显著卡片出现，而是改成两层：

- 默认态：只显示一句或两句“思考摘要”
- 展开态：显示原始 thinking 内容

推荐交互：

- 标题从“思考过程”改为更克制的“推理摘要”或“内部分析”
- 默认折叠，且仅在消息存在较长执行过程时出现
- 放入工件抽屉或执行条内部，而不是直接插入正文阅读流

如果后续希望兼顾开发者调试，可以增加一个全局开关：

- 普通模式：隐藏原始 thinking，只显示摘要
- 开发模式：允许展开原始 thinking

这样既保留能力，又不会让默认界面过载。

## 4.4 Tool Call 不要直接堆卡片，先做“动作分组”

建议把现有 `ToolCallBubbleView` 的呈现逻辑从“单调用卡片列表”升级为“动作分组 + 明细展开”。

例如把这些原始动作：

- read file A
- read file B
- read file C
- grep search
- edit file X
- edit file Y

先归纳为：

- 已阅读 3 个文件
- 已搜索 2 次代码
- 已修改 2 个文件

用户点开后，再看到每一条原始调用。

对子代理同理：默认只显示：

- 已调用 Explorer 子代理
- 完成 2 轮分析
- 产出结论摘要

而不是直接把子代理内部 rounds 铺开。

这样做的好处是：

- 大幅降低垂直长度
- 用户先看懂结果，再决定是否审计细节
- 工具行为终于从“日志”变成“可理解的行动反馈”

## 4.5 时间线从“每轮都画”改成“只强调关键阶段”

当前 round timeline 对开发很友好，但它不适合作为默认主结构。

建议时间线退到次级层，只承担关键阶段表达，例如：

- 分析问题
- 检查文件
- 执行修改
- 验证结果
- 完成回答

每个阶段下面再挂具体工具明细。

换句话说，不要让 UI 直接暴露模型内部 round，而要暴露用户能理解的任务阶段。因为用户并不关心“第 4 轮和第 5 轮”本身，他关心的是“为什么现在在运行命令”。

## 4.6 给流式阶段一个固定的 Live 状态区

建议在当前活跃 agent 消息底部增加一个固定的 live status 区，而不是让多个局部组件同时表达“正在进行中”。

这个区域只承担三件事：

- 当前状态文案
- 最近一个动作
- 是否可展开更多细节

示例：

- 正在分析仓库结构
- 正在读取 2 个文件
- 正在执行命令：xcodebuild
- 正在等待你的确认

这样用户即使不展开工件，也能知道 agent 没卡死、没乱跑、没失控。

## 4.7 消息操作栏需要重新分层

建议重做 `messageActionsRow` 的策略。

推荐拆成两组：

- 显式常用操作：复制、重新生成
- 收纳操作：编辑、删除、从此处删除

并且：

- hover 时可以显示完整工具栏
- 非 hover 状态下，也应保留一个更轻的更多菜单入口
- 失败消息应提供清晰的重试主按钮，而不只是附加在下方

当前的主要问题是“动作是有的，但不够可预期”。重构目标不是增加功能，而是让功能更容易找到。

## 4.8 子代理结果应该像“委托任务”，不是“内嵌第二条对话”

当前子代理时间线直接嵌进主消息里，容易让界面出现“消息里套消息”的感觉。

更好的模式是把子代理呈现成一个任务卡：

- 子代理名称
- 任务描述
- 完成状态
- 结论摘要
- 查看详情

详情里再展开 rounds、tool calls、thinking。

这样能明显降低嵌套深度，也更符合“主代理委托了一个子任务”的用户心智。

## 5. 具体到样式层面的建议

### 5.1 重新拉开三种消息的视觉语言

建议把三类消息做得更明确：

- User message：保留右对齐和气泡感，强调输入
- Agent message：左对齐主卡片，强调回答与工作状态
- System message：弱化处理，作为事件通知而非对话主体

现在 agent 和 system 的头部样式相近，识别度还不够。

### 5.2 降低材质使用频率

当前 thinking、tool call、附件 badge 等多处使用 material，会让复杂消息在视觉上偏碎。建议：

- 正文区尽量使用稳定底色和轻边框
- 只有浮层、菜单、次级抽屉再使用 material
- 同一条消息内部不要同时出现太多不同层级的玻璃质感

### 5.3 强化正文排版，弱化元数据排版

建议：

- 增加正文段落 spacing
- 减少 header 图标和小字的视觉占比
- 让时间戳、模型、状态都退到次级信息

用户读 agent 回复时，排版质量比花哨装饰更重要。

### 5.4 控制展开内容的最大高度和密度

工具输出、thinking 原文、diff 都是高噪声内容。建议：

- 默认固定最大高度
- 提供“展开全部 / 折叠”
- 对超长终端输出支持按块折叠，而不是一整个大滚动区

否则一条失败命令就会吞掉整屏。

## 6. 建议的结构调整方案

为了兼顾现有架构，建议不要一次推翻，而是按下面顺序演进。

### Phase 1：只重构信息层级，不动数据模型

目标：先把消息读起来顺。

建议动作：

- `MessageBubbleView` 重组为“正文卡 + 状态条 + 可展开详情”
- `ThinkingBubbleView` 降级到详情区
- `ToolCallBubbleView` 增加摘要态
- `AgentStepTimelineView` 只在详情态展示

这是投入最小、体验收益最大的一步。

### Phase 2：引入过程摘要模型

目标：让 UI 不再直接依赖原始 round 粒度。

建议增加一层 view model 或 presenter，把当前 message 先转换成：

- answer content
- live status
- summarized actions
- artifacts
- debug details

这样 UI 才能脱离“有什么数据就画什么”的状态，进入“按用户心智组织信息”。

### Phase 3：区分默认模式和开发模式

目标：同时服务普通用户与高级用户。

建议提供开关：

- 默认模式：答案优先，过程摘要化
- 开发模式：显示完整 thinking、tool call、subagent timeline

这一步会让 agentGui 更像产品，而不是调试面板。

## 7. 对现有文件的具体改造建议

### `MessageBubbleView.swift`

建议作为本次改造的主战场：

- 重新定义 agent message 的主容器
- 把 header、正文、状态、详情分层
- 精简 hover actions，加入稳定入口

### `ThinkingBubbleView.swift`

建议改成“摘要优先、原文后置”的组件，不再默认承担主流程节点职责。

### `ToolCallBubbleView.swift`

建议支持两种模式：

- summary mode
- detail mode

并增加“结果摘要”而不是只展示原始输入输出。

### `AgentStepTimelineView.swift` / `SubagentTimelineView.swift`

建议从默认可见区域撤到详情抽屉，只保留关键阶段摘要暴露给主界面。

### `ChatView+MessageList.swift`

建议配合流式状态，优化当前活跃消息的滚动策略和在途状态固定展示，避免流式过程中界面跳动感过强。

## 8. 优先级排序

如果只做最关键的几件事，建议按下面顺序处理：

### P0

- 让 agent message 回到“答案优先”
- 给流式过程增加单一 live 状态区
- 把 thinking 和 tool call 从主阅读流降级

### P1

- 工具调用增加摘要分组
- 子代理改为任务卡，而不是嵌套时间线
- 操作栏重新分层

### P2

- 引入默认模式 / 开发模式
- 将 round 转换为阶段型 timeline
- 优化长输出折叠和结果摘要

## 9. 最终建议

当前界面的核心问题不是“还不够像 agent”，而是“太像 agent 内部实现本身”。

下一版最重要的方向不是增加更多可视化块，而是重新建立消息区的信息秩序：

- 先让用户看到稳定答案
- 再让用户理解 agent 正在做什么
- 最后才允许用户审计细节

如果按这个方向重构，agentGui 的 message 区会从“能展示很多东西”升级为“能让用户快速理解并信任 agent 的工作过程”。这才是主流 agent 产品在消息交互上最值得借鉴的地方。
