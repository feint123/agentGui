# MarkdownMessageView Markdown 解析与增量渲染修正需求说明

日期：2026-03-10

关联对象：`MarkdownMessageView`、`BlockMarkdownCodec`、`AgentMessageResultBlockView`、`SubagentTimelineView`、Markdown 相关测试

设计基准：消息渲染与编辑器块级 Markdown 解析保持同源；在流式输出场景下保证表格、代码块、引用、列表等复杂块按完整结构渲染，而不是被追加过程拆碎后错误展示。

## 1. 背景

当前项目中已经存在两套 Markdown 处理路径：

- 编辑器侧使用 `BlockMarkdownCodec` 将 Markdown 解析为 `BlockDocument`，支持标题、段落、引用、列表、待办、代码块、表格、图片、链接、callout、toggle 等块级结构
- 消息侧 `MarkdownMessageView` 维护了一套独立的 `CachedBlock` 解析与缓存逻辑，当前主要覆盖标题、分割线、代码块、表格和普通文本

这导致两个直接问题：

- 同一份 Markdown 在“编辑器”和“消息渲染”两处的结构理解不一致，语法覆盖范围和边界行为不同
- `MarkdownMessageView` 的增量渲染目前以“追加文本后尽量拼接最后一个 text block”为核心，这对纯文本有效，但对表格、代码块、引用块、列表等需要前后文才能成型的结构不稳定

实际表现上，流式回复中经常会出现以下现象：

- 表格表头、分隔行、数据行分几次到达时，被拆成多个普通文本块或多个不完整表格
- 未闭合代码块先以普通文本展示，闭合后又突然重排，用户在生成过程中看到的结构不正确
- 列表、引用、任务列表在流式阶段缺少一致的块级识别，最终结果与编辑器侧结构不一致

对于本项目，Markdown 渲染不是普通聊天附属功能，而是 agent 结果展示的基础设施。因此本次需求不是单纯“修一个表格 bug”，而是要统一消息侧 Markdown 结构来源，并重建流式增量阶段的正确性边界。

## 2. 问题定义

### 2.1 双解析器导致结构语义不一致

当前 `BlockMarkdownCodec` 已承担编辑器 Markdown 的块级语义定义，但 `MarkdownMessageView` 没有复用它，而是维护一套单独解析器。

结果是：

- 两套实现的支持语法集合不同
- 后续新增或修复 Markdown 语法时，需要在两处重复维护
- 消息视图与编辑器视图对同一内容的展示可能不一致，增加用户认知成本

### 2.2 当前“追加解析”模型不能保证复杂块原子性

`MarkdownMessageView` 目前会在 append-only 场景下尝试只解析新增片段，并在“没有复杂结构”的情况下把新增内容直接拼接到最后一个文本块。

这个模型的问题不在于性能，而在于结构正确性：

- Markdown 的很多块级元素并不是“新增片段自洽”即可识别
- 一张表格可能跨多次流式分片才完整出现
- 一个 fenced code block、blockquote、ordered list 都可能依赖前文状态判断当前行属于哪个块
- 仅解析追加文本，无法知道它应当并入上一个未完成块，还是应形成新块

因此当前增量策略本质上只是“渲染层减轻重算”，并没有真正建立“未完成块”和“完整块”的边界模型。

### 2.3 消息流式阶段缺少“结构稳定性优先”的规则

现在的消息渲染更偏向于“尽快把新增文本显示出来”，但对于块级 Markdown，这会让用户在流式阶段看到错误结构。

本需求需要明确一个原则：

- 对复杂 Markdown 块，生成中可以暂时以“未完成态”显示
- 但不能因为分片不完整而错误地产生多个独立块，尤其不能把最终应为一个表格或一个代码块的内容长期拆碎渲染

## 3. 目标

本次需求需要达成以下目标：

- 让 `MarkdownMessageView` 复用 `BlockMarkdownCodec` 作为唯一块级 Markdown 解析来源
- 让消息渲染与编辑器渲染在块级结构判断上保持一致
- 修复流式增量渲染中复杂块被拆碎、误判、反复重排的问题
- 在 append-only 场景下，优先复用既有解析结果，但不能以牺牲结构正确性为代价
- 为后续 Markdown 功能扩展建立单一解析基线和可测试的增量语义

目标效果：

- 同一份 Markdown 在消息视图和编辑器视图中的块级结构一致
- 表格、代码块、引用、列表等复杂元素在流式阶段具备可预期的展示行为
- 复杂块在未完成时不会被错误拆成多个独立渲染块
- 最终渲染结果与整篇一次性解析的结果一致

## 4. 方案对比

### 方案 A：保留 `MarkdownMessageView` 自定义解析器，只修补表格与代码块边界

做法：继续在 `CachedBlock` 和当前 `parseBlocksImpl` 基础上增加更多语法和追加规则。

优点：

- 改动局部
- 短期可较快缓解部分案例

缺点：

- 仍然维持两套块级语义系统
- 语法覆盖会持续分叉
- 后续维护成本高，回归风险大
- 无法从根本上解决“消息与编辑器不一致”问题

### 方案 B：`MarkdownMessageView` 复用 `BlockMarkdownCodec`，并在其之上建立消息侧增量复用层

做法：将消息渲染的块级来源切换到 `BlockMarkdownCodec.parse` 输出的 `BlockDocument`，再在消息侧建立一层“前缀复用 + 尾块重解析”的增量策略。

优点：

- 统一块级语义来源
- 能复用编辑器已覆盖的列表、引用、待办、callout、toggle 等能力
- 增量逻辑可以围绕 `DocumentBlock` 做更稳定的边界复用
- 更利于测试“流式阶段结果”和“最终整篇结果”的一致性

缺点：

- 需要重构 `MarkdownMessageView` 当前缓存模型
- 需要明确哪些块允许复用，哪些尾块必须回退重解析

### 推荐方案

推荐采用方案 B。

原因：

- 用户提出的两个问题本质上是同一个方向：统一解析基线，并修正流式结构正确性
- `BlockMarkdownCodec` 已经是项目内更完整的 Markdown 块级能力中心，继续维护第二套解析器没有收益
- 真正可靠的增量渲染必须基于共享语义模型，而不是在两套 parser 上各自修边界

## 5. 范围

### 5.1 本期范围

本期需要完成：

- `MarkdownMessageView` 改为复用 `BlockMarkdownCodec` 的块级解析结果
- 定义消息侧用于渲染的 `BlockDocument -> UI block` 映射规则
- 重构当前缓存与增量更新逻辑，使其适用于复杂块的流式增长
- 补齐与本次改动直接相关的测试，包括整篇解析一致性和流式追加一致性
- 明确复杂块在“未完成状态”下的展示与回退规则

### 5.2 非本期范围

本期不包含：

- 重新设计 `BlockMarkdownCodec` 的全部 Markdown 语法能力
- 引入 WebView 或第三方重型 Markdown 渲染器替代现有 SwiftUI 方案
- 完整实现所有 inline markdown 的自定义解析
- 对代码高亮、Mermaid、图片浏览器等视觉样式做大范围改版
- 解决所有 CommonMark/GFM 兼容性问题

## 6. 核心设计要求

### 6.1 单一块级解析来源

优先级：P0

要求：

- `MarkdownMessageView` 不应继续维护独立的块级 Markdown 解析规则作为主路径
- 消息视图的块级结构必须来自 `BlockMarkdownCodec` 的解析结果，或来自以其为唯一事实来源的轻量适配层
- 任何新的块级 Markdown 语法修复，应优先修改 `BlockMarkdownCodec`，而不是在消息侧另起一套规则

说明：

- 消息侧可以保留面向 UI 的缓存结构，但不能再保留独立的语义判断分支

### 6.2 流式增量更新必须以结构正确性为先

优先级：P0

要求：

- append-only 更新不能只根据“新增片段是否看起来复杂”决定是否追加到最后一个文本块
- 增量更新必须识别“尾部未稳定区域”，并对该区域执行重解析
- 已经稳定且不受新增内容影响的前缀块应尽量复用
- 不能把最终属于同一个表格、同一个代码块、同一个引用块或同一个列表的内容在流式阶段长期拆成多个独立块

说明：

- 这里的核心不是“完全不重算”，而是“只重算必要的尾部范围，同时保持结构正确”

### 6.3 尾部回退重解析模型

优先级：P0

要求：

- 消息侧增量策略必须支持“从最后一个稳定块之后重新解析”或等价机制
- 对于可能被后续文本继续扩展的块类型，不能在第一次识别后立即视为稳定
- 至少以下类型必须纳入尾部不稳定判断：代码块、表格、引用、无序列表、有序列表、待办列表、toggle、callout、段落
- 当无法安全判断尾部边界时，应退回更大的尾部范围进行重解析，而不是冒险错误复用

建议方向：

- 保守优先，先实现“稳定前缀复用 + 尾部全文块重解析”，再考虑更细粒度优化

### 6.4 最终结果必须与整篇解析一致

优先级：P0

要求：

- 对任意一条完整消息，流式逐步追加后的最终块序列必须与一次性整篇调用 `BlockMarkdownCodec.parse` 的结果一致
- 如果流式中间态采取了临时降级展示，文本完成后必须收敛到与整篇解析一致的最终结构
- 不允许出现“流式路径解析结果”和“最终一次性路径解析结果”长期不同步的情况

### 6.5 UI 映射需要覆盖现有 `BlockDocument` 主要块类型

优先级：P1

要求：

- `MarkdownMessageView` 至少需要正确映射以下块类型：段落、标题、引用、无序列表、有序列表、待办、代码块、分割线、表格、链接、图片、callout、toggle
- 对于当前消息视图暂不准备做专门样式的块，可以采用安全的降级展示，但不能丢失块级边界
- Mermaid 仍可作为代码块语言分支保留当前专门渲染逻辑

说明：

- 本期重点是结构正确性，不要求每个块都做到编辑器级交互能力

### 6.6 缓存复用不能引入新的身份抖动

优先级：P1

要求：

- 消息块在 append-only 更新中应尽量保持稳定 identity，避免尾部少量更新触发整条消息大范围 SwiftUI 重建
- 前缀复用部分的块 identity 必须可持续沿用
- 尾部重解析产生的新块可以替换尾部 identity，但不应影响已稳定前缀块

## 7. 详细功能需求

### 7.1 BlockMarkdownCodec 复用方式

要求：

- `MarkdownMessageView` 应通过明确的适配层消费 `BlockDocument`
- UI 层不直接依赖编辑器交互状态，但可以复用 `DocumentBlockKind` 和文本/元数据
- 如需消息侧专属 view model，应保持为对 `DocumentBlock` 的投影，而不是重新定义块语义

### 7.2 表格增量渲染

要求：

- 表格在流式阶段不应因为表头、分隔行、数据行分批到达而被拆成多个长期独立块
- 当仅收到表头、尚未收到分隔行时，可临时按普通段落或未完成态处理
- 一旦分隔行到达，解析结果应将相关尾部内容收敛为单个表格块
- 后续新增数据行应并入同一表格块，而不是创建多个表格块或多个文本块

### 7.3 代码块增量渲染

要求：

- 未闭合 fenced code block 在流式阶段必须有一致处理策略
- 不允许出现前几行作为普通文本、闭合后又与后文拼成错误多块的情况
- 代码块闭合后，应收敛为单一代码块结构；Mermaid 代码块闭合后仍应进入 Mermaid 专用渲染路径

### 7.4 列表与引用增量渲染

要求：

- 连续列表项应在流式阶段尽量保持同类块语义，不应因逐行到达被拆成普通段落
- 引用块追加新行时，应能够并入原引用结构，而不是生成多个彼此独立的文本块
- 任务列表的勾选标记与正文必须保持块边界正确

### 7.5 非追加更新回退规则

要求：

- 当消息文本不是 append-only 更新时，允许直接退回全量解析
- 非追加路径的正确性优先于缓存命中率
- 需要明确区分“流式追加优化路径”和“普通重算路径”

## 8. 性能与稳定性要求

### 8.1 性能目标

- 在常见聊天流式场景中，前缀稳定块应尽量复用，避免每次字符追加都全量重建整个消息视图
- 即使采取保守尾部回退策略，也应只重解析必要尾段，而非默认每次重跑整篇

### 8.2 稳定性目标

- 不得因为缓存命中或增量复用，导致最终渲染结构与一次性解析结果不一致
- 不得因为复杂块分片追加，出现长期错误结构、重复块或顺序错乱
- 不得因为 identity 不稳定造成消息滚动闪烁或明显跳动

## 9. 测试要求

### 9.1 解析一致性测试

必须新增或补强以下类型测试：

- 一次性整篇解析与消息侧映射结果一致
- 段落、标题、分割线、代码块、表格、引用、列表、待办、callout、toggle 的基础样例解析
- Mermaid 代码块在消息侧仍走专门展示路径

### 9.2 流式追加测试

必须覆盖以下样例：

- 表格按“表头 -> 分隔线 -> 数据行”逐步追加，最终收敛为单表格块
- 代码块按“起始 fence -> 内容 -> 结束 fence”逐步追加，最终收敛为单代码块
- 引用块逐行追加时保持单引用结构
- 列表逐项追加时保持正确列表结构
- 普通段落持续追加时，前缀 identity 稳定，尾部更新合理

### 9.3 回归测试

必须补充以下回归类断言：

- 非 append 更新会正确退回全量解析
- 流式路径最终结果与整篇解析结果完全一致
- 复杂块不会因为中间态误判而残留额外文本块

## 10. 验收标准

满足以下条件视为验收通过：

- `MarkdownMessageView` 已不再以独立块级 parser 作为主解析路径
- 消息侧块级结构由 `BlockMarkdownCodec` 或其单向适配层统一提供
- 表格、代码块、引用、列表在流式追加过程中不再出现明显错误拆块
- 流式最终结果与整篇一次性解析结果一致
- 相关单元测试覆盖基础语法、流式追加和非追加回退路径
- 现有消息渲染性能未出现明显退化，UI 未出现大范围闪烁或身份抖动

## 11. 实施建议

建议按以下顺序落地：

1. 先提取 `BlockDocument -> MarkdownMessageView` 的单向适配层，切断当前独立 parser 主路径
2. 再实现保守型增量策略：复用稳定前缀，重解析尾部不稳定区
3. 最后补齐流式追加测试与回归样例，确认最终结构与整篇解析一致

这样做的原因是：

- 先统一解析来源，才能避免后续继续在错误基线上修补
- 先采用保守正确的尾部重解析，比过早追求极致增量更稳妥
- 测试样例应围绕“最终一致性”建立，而不是围绕当前实现细节建立
