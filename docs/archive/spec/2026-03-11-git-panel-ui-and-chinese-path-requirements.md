# Git 面板 UI 交互优化与中文路径修复需求文档

日期：2026-03-11

关联对象：`GitPanelView`、`GitDiffView`、`GitPanelViewModel`、`GitService`、`GitStatusParser`、`WorkspacePanelView`、`WorkspaceState`

## 1. 背景

当前项目已经具备一版基础 Git 面板能力：

- 可识别当前工作目录是否位于 Git 仓库
- 可展示分支、变更数量、变更列表和基础提交入口
- 可查看补丁文本形式的 diff
- 可执行暂存、取消暂存、丢弃改动、删除未跟踪文件、提交等基础操作

但从实际使用质量看，当前实现仍存在两类明显问题：

### 1.1 UI 与交互仍偏“可用”，未达到主流 Git 客户端体验基线

当前面板的主要问题包括：

- 信息层级较弱，仓库摘要、变更分组、提交区权重接近，扫描效率低
- 文件项只提供文本按钮式操作，缺少符合桌面 Git 工具习惯的悬浮动作、右键动作和选中态反馈
- diff 虽可查看，但缺少“从文件树进入 diff”“切换回文件”“定位当前查看对象”等连贯反馈
- 提交区始终常驻，容易在无 staged 变更时占据注意力
- 文件树虽然已具备轻量 Git 标记，但与 Git 面板之间仍缺少统一的选中、聚焦和跳转体验

### 1.2 中文文件名无法稳定处理

当前已知 bug 为：当仓库中存在中文文件名或包含中文目录名的路径时，Git 面板中的部分能力不能稳定工作，可能表现为：

- 变更列表中文件路径显示异常、转义、截断，或与真实文件不一致
- 点击 diff 无法正确获取目标文件变更
- 暂存、取消暂存、丢弃、删除未跟踪文件等操作命中错误路径或执行失败
- 重命名场景下，中文旧路径与新路径的解析结果不稳定

该问题会直接影响中文工作区的基本可用性，因此与 UI 优化并列为本次需求的 P0 项。

## 2. 目标

本次需求目标不是重做整个 Git 功能，而是在现有基础 Git 能力之上完成一次“体验校正”，对齐主流桌面 Git / IDE 的常见实践，并补齐中文路径处理的正确性。

本次需求完成后，应达到以下结果：

- Git 面板在视觉层级、操作效率、状态反馈上达到主流 Source Control 面板的基础体验基线
- 用户可从文件树和 Git 面板两条路径进入同一套变更查看与操作流程
- 中文文件名、中文目录名、中文重命名路径在状态读取、diff 查看、文件级操作中均可稳定处理
- 异常反馈面向普通用户可理解，不暴露底层路径编码细节

## 3. 对标对象与设计原则

本次优化参考以下产品的共同实践，而不是逐项照搬某一产品：

- VS Code Source Control：强调轻量摘要、分组列表、右键动作和低干扰提交区
- GitHub Desktop：强调任务闭环、状态明确、危险动作有确认
- Tower / Fork 等桌面 Git 工具：强调文件状态扫描效率、列表操作效率、diff 预览连贯性

设计原则：

- 先让用户看清状态，再让用户执行操作
- 高危动作必须慢一步，普通动作必须快一步
- 同一文件在文件树、变更列表、diff 区的身份要一致
- 路径处理必须以“真实文件路径”为准，不允许 UI 展示路径和执行路径脱节
- 首版只优化最常用闭环，不引入分支、历史、stash 等扩展复杂度

## 4. 当前问题梳理

### 4.1 信息结构问题

- Git 摘要区与变更区之间缺少清晰层次，用户不易快速判断“当前仓库状态是否可提交”
- `Staged`、`Modified`、`Untracked` 三组仅为静态文本分段，缺少折叠、聚焦和计数强化
- 成功反馈仅以瞬时文本提示出现，缺少与具体文件或操作的就地关联

### 4.2 操作效率问题

- 文件行内操作密度不稳定，易出现“为做一个动作需要额外点选一次”的情况
- 缺少上下文菜单，桌面端用户无法使用更符合习惯的右键动作
- 缺少批量选择和分组级动作的预留结构，后续扩展空间不足

### 4.3 导航一致性问题

- 从文件树进入变更文件后，与从 Git 面板进入 diff 的路径不完全对齐
- 用户在 diff 模式下对“当前看的是哪种 diff、来自哪个分组”感知较弱
- 文件树中的 Git 标记已经存在，但未形成“列表状态 <-> 编辑区状态”的稳定联动

### 4.4 中文路径正确性问题

- Git 状态输出中的路径可能包含引号、转义或 rename 表达式，现有解析契约不足以覆盖中文路径场景
- 路径展示值、命令执行参数值、文件树 URL 匹配值可能来自不同转换阶段，存在不一致风险
- 缺少中文路径专项测试，导致回归风险高

## 5. 功能范围

### 5.1 在本次范围内

- Git 面板的信息架构优化
- 变更列表的视觉与交互优化
- 文件树与 Git 面板的联动优化
- diff 预览链路优化
- 提交区交互优化
- 中文文件名与中文目录路径处理修复
- 相关错误反馈、回归测试与验收补齐

### 5.2 不在本次范围

- 分支管理、历史记录、stash、tag、blame
- hunk 级暂存或行级操作
- 三方冲突解决
- push / pull 的完整图形化流程
- Git 面板的持久化偏好设置系统

## 6. 用户场景

### 场景 A：快速判断当前仓库状态

用户切换到一个工作目录后，应在 1 到 2 秒内明确看到：

- 当前仓库名
- 当前分支
- 当前是否有 staged 变更可提交
- 是否有未暂存或未跟踪内容需要处理

### 场景 B：查看并处理某一个改动文件

用户在文件树或 Git 面板中发现一个已修改文件后，应能稳定完成以下路径：

1. 识别其状态
2. 打开对应 diff
3. 选择暂存、取消暂存或丢弃
4. 操作完成后在原列表位置看到状态变化

### 场景 C：处理中文文件名改动

用户修改 `文档/需求说明.md`、`界面/提交按钮.swift` 等中文路径文件时，应能像英文路径文件一样完成：

- 状态展示
- diff 查看
- stage / unstage / discard / clean
- commit 后状态清空

### 场景 D：重命名中文文件

当文件从 `旧目录/说明.txt` 重命名为 `新目录/说明-已整理.txt` 时，UI 应展示对用户有意义的新路径，并保证对该项执行 diff 与操作时命中正确目标。

## 7. 需求方案

### 7.1 Git 面板布局优化

Git 面板应调整为更明确的三段式结构：

- 顶部摘要区：仓库名、分支、同步状态、变更统计、刷新入口
- 中部变更区：按分组展示文件列表，支持折叠、计数和分组级操作
- 底部提交区：仅在存在 staged 变更或用户主动展开时强调显示

具体要求：

- 摘要区视觉上应强于普通列表内容，至少形成一级标题和二级辅助信息的对比
- 变更区应是面板主视觉中心，列表项密度以“快速扫描文件名和状态”为优先
- 提交区在无 staged 变更时应弱化，不应持续占据主要注意力

### 7.2 变更列表交互优化

每个变更分组应具备以下能力：

- 分组标题显示名称与数量，例如 `已暂存 3`、`已修改 5`、`未跟踪 2`
- 分组支持折叠与展开，默认展开非空分组
- 分组级快捷动作按分组语义提供，例如 `全部暂存`

每个文件项应具备以下交互：

- 明确的状态徽标，区分 `A`、`M`、`D`、`R`、`?`
- 文件名与相对路径分层显示；长路径以中间截断为主，避免末尾信息完全丢失
- 悬浮态出现高频动作，至少包含预览 diff 和当前语义下的一步操作
- 右键菜单提供完整动作集合，避免将所有动作都暴露为常驻按钮
- 当前选中的文件项要有稳定高亮，且与编辑区正在查看的 diff / 文件保持同步

### 7.3 文件树联动优化

文件树中的 Git 状态装饰需要继续保留，并满足以下要求：

- 状态装饰与 Git 面板中的状态颜色、符号语义保持一致
- 从文件树触发 diff 预览时，应与 Git 面板进入同一查看模式，而不是独立分支逻辑
- 若某个文件当前正在 diff 预览中，文件树和 Git 面板列表都应能体现其选中态
- 从 diff 返回文件内容后，选中态应保持可预测，不出现“左侧选中丢失”

### 7.4 Diff 预览体验优化

在保留补丁文本视图的前提下，V2 需求应补齐以下体验：

- 顶部标题清晰展示当前文件路径、diff 来源分组以及返回动作
- 当同一路径同时存在 staged 与 unstaged diff 时，用户应能看清当前查看的是哪一种
- 空 diff、二进制 diff、超大 diff 应展示明确原因，不只返回空白区域
- diff 视图中的统计信息应靠近标题展示，便于快速判断变更规模
- diff 页面中的返回行为应稳定回到先前文件或空编辑态，不制造导航迷失

### 7.5 Commit 区交互优化

提交区应参考主流 Source Control 面板的轻量输入模式：

- 当没有 staged 变更时，提交输入区默认折叠或弱化展示
- 当存在 staged 变更时，提交输入区自动提升可见性
- 提交按钮状态应由 staged 数量和消息合法性共同决定
- 提交成功反馈应与摘要区状态联动，避免用户不确定是否已生效
- 提交失败时，应给出可读错误而不是直接暴露原始终端报错

## 8. 中文路径修复要求

### 8.1 基本要求

系统必须正确处理以下路径类型：

- 纯中文文件名，例如 `需求文档.md`
- 中文目录 + 英文文件名，例如 `文稿/README.md`
- 英文目录 + 中文文件名，例如 `docs/说明书.md`
- 中英混合及包含空格的路径，例如 `设计稿/版本 2/提交说明.swift`
- 中文重命名路径，例如 `旧目录/说明.txt -> 新目录/产品说明.txt`

### 8.2 状态读取要求

- Git 状态读取结果必须产出可直接用于 UI 展示的真实相对路径
- 对中文路径不得出现八进制转义、错误引号包裹或不可逆替换
- 对 rename 行必须能正确区分旧路径与新路径，UI 默认展示新路径
- 状态读取后的路径必须与文件树 URL 匹配逻辑使用同一份规范化结果

### 8.3 操作执行要求

- stage / unstage / discard / clean / diff 等所有按路径执行的命令必须使用与展示一致的真实路径值
- 命令执行层不得依赖 shell 拼接字符串处理中文路径，必须保持参数数组传递
- 不允许为了“兼容中文”而改用脆弱的手工转义字符串方案

### 8.4 错误反馈要求

- 若路径已在仓库刷新间隙发生变化，应提示“文件状态已变化，请刷新后重试”一类的用户态信息
- 若 Git 返回不可解析路径，UI 应提示“该文件路径暂时无法解析”，并保留刷新能力
- 不得向用户展示 `\346\234\254` 一类原始转义路径作为主错误内容

## 9. 技术约束与建议

本节不作为详细实现方案，但对实现边界提出明确要求：

- Git 状态读取应保证返回 UTF-8 可读路径，并避免默认 quote path 导致的中文转义问题
- 状态解析器必须覆盖普通修改、未跟踪、删除、重命名，以及包含中文路径的 rename 输出
- 需要在 `GitStatusParser`、`GitService`、`GitPanelViewModel` 三层分别建立对应测试，避免只在 UI 层发现路径错误
- 任何路径规范化逻辑都必须集中收敛，避免文件树、diff、操作命令各自做一套转换

## 10. 验收标准

### 10.1 UI 与交互验收

- 用户进入 Git 仓库后，可在侧栏快速识别仓库名、分支和变更统计
- 变更列表按分组展示，支持折叠，并能高效完成文件级常用操作
- 从文件树和 Git 面板进入 diff 的体验一致，选中态稳定
- 提交区不会在无 staged 变更时持续干扰浏览，但在可提交时足够明显

### 10.2 中文路径验收

- 中文文件名在 Git 面板中显示正确，无转义乱码
- 点击中文路径文件可稳定打开对应 diff
- 中文路径文件可稳定执行暂存、取消暂存、丢弃与删除未跟踪文件
- 中文路径 rename 项显示正确的新路径，并能正常执行 diff 和后续操作
- 至少覆盖一组中文路径自动化测试，防止后续回归

### 10.3 稳定性验收

- 非 Git 目录、空仓库、二进制 diff、超大 diff、路径失效等场景下 UI 不崩溃
- Git 操作完成后状态刷新稳定，不出现列表残影或错误选中
- 中文路径与英文路径在相同操作上的行为一致

## 11. 优先级

- P0：中文路径修复、路径一致性、变更列表交互优化、diff 导航一致性
- P1：摘要区层级优化、分组折叠、提交区弱化与增强逻辑、文件树联动强化
- P2：批量选择预留、更多快捷键、更多 diff 展示细节优化

## 12. 测试要求

至少补齐以下测试类型：

- `GitStatusParserTests`：中文未跟踪、中文修改、中文 rename、带空格中文路径
- `GitServiceTests`：中文路径 diff / stage / unstage / discard / clean 命令参数传递正确
- `GitPanelViewModelTests`：中文路径文件在选中 diff、执行操作后状态刷新正确
- 视图或展示测试：验证中文路径在列表和 diff 标题中不被错误转义

## 13. 后续扩展方向

在本次需求稳定后，可按以下顺序继续扩展：

1. 批量选择与批量操作
2. pull / push 与远端错误处理
3. 提交历史与提交详情
4. 分支切换与创建
5. hunk 级操作与更高保真 diff 视图
