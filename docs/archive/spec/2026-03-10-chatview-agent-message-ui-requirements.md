# ChatView Agent Message 与 Subagent UI 优化需求说明

日期：2026-03-10

关联对象：`ChatView`、`MessageBubbleView`、`ExecutionSummaryBarView`、`ArtifactDrawerView`、`ToolCallBubbleView`、`ThinkingBubbleView`、`SubagentTaskCardView`、`SubagentTimelineView`

配套线框说明：[docs/spec/2026-03-10-chatview-agent-message-ui-wireframes.md](/Volumes/T7/文稿/Projects/agentGui/docs/spec/2026-03-10-chatview-agent-message-ui-wireframes.md)

设计基准：以 coding agent 场景为主，采用“按执行顺序展示、过程可见但降视觉重点、完成后自动收敛”的消息 UI 风格。

## 1. 背景

当前 `ChatView` 中 agent message 已经具备一定的过程展示能力，但整体仍存在两个方向性问题：

- 一部分结构按“回答优先”的对话产品方式组织，不完全适合 agent 执行流场景
- 另一部分结构又过于接近调试日志，视觉重点过高，且存在嵌套时间线和嵌套卡片

对于本项目，agent message 的本质不是普通聊天回复，而是一次可观察的执行过程。因此本次优化不再以“最终回答是唯一主角”为前提，而是以“执行顺序清晰、过程流畅、重点适度收敛”为主目标。

同时，当前方向已经明确：

- 主消息按执行顺序展示，而不是退化成纯回答卡
- subagent 当前的任务卡方向可以保留
- thinking 与工具调用需要明显降权，避免强烈边框和深层嵌套
- 执行中的内容可展开，执行完成后自动收起，界面恢复紧凑
- 不同工具类型应有适合该操作语义的 UI，而不是全部复用同一种日志卡

## 2. 问题定义

### 2.1 当前主消息结构不够符合 agent 执行流

agent message 在本产品中更像“执行记录 + 阶段结果”，而不是纯自然语言答复。当前如果把正文块放得过重，会削弱用户对执行顺序的理解。

### 2.2 Thinking 与 Tool Call 视觉存在感过高

当前 thinking 和 tool call 多使用较强的材质、描边和块级卡片。结果是：

- 次要信息抢占了阅读注意力
- 多个步骤连续出现时，界面显得碎且重
- 过程虽可见，但不够克制

### 2.3 嵌套结构过多

当前消息中容易出现以下嵌套：

- 消息内嵌套过程块
- 过程块内嵌套时间线
- 时间线内嵌套工具卡
- 子代理内再嵌套另一套过程视图

这会显著增加纵向长度和认知负担。

### 2.4 进行中与完成后的状态切换不够收敛

执行过程中，用户希望看到展开的步骤和实时变化；执行完成后，用户又希望界面自动变得简洁。当前缺少这一套“运行时展开、结束后收起”的自动状态管理。

### 2.5 不同操作类型没有形成稳定视觉语义

读取文件、修改文件、运行命令、搜索代码、获取网页、询问用户，这些动作的目标和产物都不同，但当前呈现方式相近，导致信息辨识度不足。

## 3. 目标

本次优化需要达成以下目标：

- 将 agent message 调整为“按执行顺序展示”的浅层执行流
- 让每个步骤在时间上连续可读，但视觉上不过度抢眼
- 保留 subagent 任务卡模式，不把 subagent 还原成嵌套聊天流
- 去除多层嵌套线框与重边框，整体转为更轻、更浅的层次表达
- 在执行中自动展开当前步骤，在执行完成后自动收起非必要细节
- 为不同工具类型定义匹配其语义的专用 UI 样式

目标效果：

- 用户可以顺着消息流直观看懂 agent 做了什么
- 当前正在进行的动作一眼可见
- 完成后消息自动收敛，不会保留大量展开日志
- thinking 和工具调用是“可见但克制”的辅助层，不再是强视觉主角

## 4. 方案对比

### 方案 A：回答优先，过程后置到抽屉

做法：保持回答块作为第一焦点，执行过程主要放进摘要条和工件抽屉。

优点：

- 适合普通对话产品
- 信息收敛强

缺点：

- 不符合本项目的 agent 执行流定位
- 执行顺序被压缩得过于间接

### 方案 B：执行顺序优先的浅层过程流

做法：agent message 以顺序流展示阶段输出、thinking 摘要、工具动作、subagent 任务卡和阶段性结果；视觉上全面降权，去掉重边框与深层嵌套；执行中展开，完成后自动收敛。

优点：

- 最符合当前产品的 agent 特征
- 能看懂过程，又不会变成日志墙
- 更适合 coding agent 与工具编排场景

缺点：

- 需要更细致地设计不同步骤的折叠策略
- 需要给每种工具类型定义单独的 UI 规则

### 方案 C：完整调试台风格

做法：继续强化 timeline、工具卡、终端输出和思考原文的完整显示。

优点：

- 对开发调试最直接

缺点：

- 视觉压力大
- 不适合长对话中的连续阅读

### 推荐方案

推荐采用方案 B。

原因：

- 它保留了按执行顺序展示的核心诉求
- 它能把当前界面从“嵌套日志流”改成“浅层执行流”
- 它允许 subagent 继续作为任务卡保留，不需要回退

## 5. 产品定位与范围

### 5.1 本期范围

本期需要完成：

- 定义 agent message 的顺序流结构
- 定义执行中、完成、失败、等待用户时的自动展开/自动收起规则
- 定义 thinking 的低权重展示方式
- 定义不同工具类型对应的 UI 表达
- 定义 subagent 卡片与主执行流的关系
- 定义验收标准，供后续实现和评审使用

### 5.2 非本期范围

本期不包含：

- 重写 `ToolCall`、`AgentRound`、`Message` 模型
- 重做整个 ChatView 页面结构
- 新增开发者模式或单独日志面板
- 改动 subagent 的底层执行逻辑

## 6. 总体信息架构

agent message 应采用“顺序流 + 轻结果块”的结构，而不是“重回答卡 + 深抽屉”的结构。

推荐顺序如下：

1. 消息头部
2. 阶段性回答或结果块
3. thinking 摘要行
4. 工具调用行
5. subagent 任务卡
6. 最终结果块或错误块

规则：

- 所有内容按实际执行先后顺序排列
- 除 subagent 外，尽量避免二级嵌套容器
- thinking 与工具调用默认使用浅色、轻边界、低对比样式
- 当前活跃项在执行中展开，完成后自动回到紧凑态

## 7. 详细需求

### 7.1 主执行流展示

优先级：P0

要求：

- agent message 必须按执行顺序展示内容，不应强制把所有过程压缩到消息末尾摘要
- 如果消息经历了多轮思考、读文件、改文件、运行命令、调用子代理，应按先后顺序呈现
- 最终回答或阶段总结可以出现在流的末尾或中间阶段，不要求始终作为第一大块内容
- 主执行流中每个步骤应保持单层、扁平、连续，不应形成“卡片里套卡片”的结构

### 7.2 执行中自动展开、完成后自动收起

优先级：P0

要求：

- 当前正在运行的 thinking、工具调用或 subagent 卡片可以处于展开态
- 一旦该步骤完成，应自动回到紧凑态，除非用户手动锁定展开
- 自动收起后，应保留该步骤的摘要信息、状态图标和必要结果
- 整条消息在执行中可以有局部变化，但执行完成后整体高度应明显收敛

说明：

- “自动收起”是本次交互改造的核心，不应依赖用户手工折叠界面

### 7.3 Thinking 展示

优先级：P0

要求：

- thinking 仍然保留在顺序流中，但必须显著降低视觉权重
- 默认只展示一行摘要，例如“思考中”或“推理摘要 · 420 字”
- 执行中可展开显示当前 thinking 内容
- 完成后默认自动收起为摘要行
- 样式上应移除高饱和色、高存在感描边和厚重材质
- 优先使用浅背景、细分隔、轻图标，而不是独立大卡片

### 7.4 Tool Call 展示

优先级：P0

要求：

- 工具调用必须仍然出现在顺序流中，而不是全部后置到抽屉
- 工具调用应按单次动作顺序展示，但默认是紧凑行，而不是大块日志卡片
- 执行中当前工具可展开显示更多上下文
- 完成后自动收起，仅保留摘要、目标对象、状态和耗时
- 终端输出、diff、完整文本输出只在展开态中显示
- 工具调用行不使用强边框嵌套，不使用层层包裹的时间线外框

### 7.5 不同工具类型的专用 UI

优先级：P0

不同操作类型必须有对应语义化 UI，不能继续完全共用同一模板。

#### 读取文件

要求：

- 突出文件名
- 路径为次级信息
- 可显示“已读取”状态与耗时
- 展开时显示读取摘要或片段，而不是完整大文本优先

推荐形式：文件行项目、文档图标、紧凑元信息。

#### 修改文件

要求：

- 突出文件名和“已修改”语义
- 可显示新增/删除或 diff 摘要
- 展开时展示 diff 片段
- 完成后默认收起为变更摘要行

推荐形式：变更卡、diff 预览块、文件状态徽记。

#### 运行命令

要求：

- 突出命令本身和运行状态
- 执行中显示活跃输出或最近一段输出
- 完成后收起，只保留命令、退出结果、耗时和关键摘要
- 错误时突出失败原因摘要，不默认展开整屏终端内容

推荐形式：命令条、单行终端预览、可展开输出区。

#### 搜索 / 获取内容

要求：

- 突出查询词、目标范围或 URL
- 完成后显示结果数量或命中摘要
- 展开时再看完整结果

推荐形式：查询条目、来源标签、结果数标签。

#### 询问用户

要求：

- 明确区分“等待用户回答”与“已收到回答”
- 已完成后仅保留问题摘要和用户选择摘要

推荐形式：问答条目、回答标签、待确认状态色。

### 7.6 Subagent 展示

优先级：P0

subagent 的现有任务卡方向可以保留，但应继续与主执行流协同。

要求：

- subagent 作为顺序流中的一个独立任务卡出现
- 默认态展示子代理名称、任务摘要、状态、轮次数、耗时、结果摘要
- 执行中可展开显示任务详情和进展
- 完成后自动收起回摘要态
- 默认态不展示完整 rounds 时间线
- 如果用户主动查看详情，再进入完整过程视图

禁止事项：

- 不得把 subagent 变成嵌套聊天流
- 不得在主流中默认铺开多轮 rounds 和多层工具卡

### 7.7 回答 / 结果块展示

优先级：P1

要求：

- 回答或阶段性结果块仍然需要保留，但不再强制占据最高视觉权重
- 结果块应更像“阶段产出”而不是“唯一主卡片”
- 当流程最终产生自然语言结论时，可在消息尾部形成较清晰的结果块
- 结果块样式应比 thinking 和工具行更稳定，但不应压倒整个执行流

### 7.8 视觉风格

优先级：P1

要求：

- 移除明显的嵌套线框感
- 使用更浅的背景色、更轻的描边、更弱的材质感
- 用状态色表达成功、失败、进行中，而不是给每种块都强上色
- thinking 和工具调用整体应比结果块更淡、更细、更轻
- 整个消息在长执行流下仍应显得平整，而不是由许多厚卡片堆起来

### 7.9 头部与操作入口

优先级：P1

要求：

- 头部保持轻量，仅承载身份、时间、必要状态
- 操作仍可放在 hover 区或更多菜单中
- 不需要把“复制、重试”做成强常驻主按钮，避免破坏执行流的连续感

## 8. 状态模型映射要求

UI 层必须至少清晰映射以下状态：

- thinking 中
- 工具执行中
- 子代理执行中
- 等待用户输入
- 已完成
- 已失败

要求：

- 当前活跃项必须有明确状态表现
- 已完成项必须回到紧凑摘要态
- 失败项必须保留更高可见度，但仍不形成厚重嵌套块

## 9. 验收标准

### 9.1 顺序可读性

- 用户可以按从上到下的顺序看懂 agent 做了什么
- 过程项之间的先后关系清晰，无需依赖额外时间线框架
- 即使存在多轮工具调用，默认态也不会形成复杂嵌套结构

### 9.2 视觉收敛

- thinking 与工具调用比结果块更低权重
- 默认完成态下，大部分过程项已自动回到紧凑摘要行
- 整条消息不会因为历史步骤多而长期保持大面积展开

### 9.3 工具语义表达

- 用户可以一眼区分读取文件、修改文件、运行命令、搜索和提问用户等不同动作
- 各类动作的 UI 与其结果语义一致，而不是只靠图标区分

### 9.4 Subagent 体验

- subagent 仍然表现为任务卡，而不是嵌套消息流
- 执行中和完成后的展开/收起行为符合主执行流规则

## 10. 实现建议

建议后续实现优先从以下方向落地：

- 先调整 `MessageBubbleView`，把 agent message 改成扁平顺序流
- 再调整 `ToolCallBubbleView` 与 `ThinkingBubbleView`，把它们重构为轻量步骤行
- 然后为读取、修改、命令、搜索、提问用户定义专门的行级样式
- 最后保留并微调 `SubagentTaskCardView`，让它遵循同样的自动展开/自动收起策略
