# Markdown 渲染完善建议

日期：2026-03-08

## 1. 评审目标

本文聚焦 `MarkdownMessageView` 当前实现，回答三个问题：

1. 现阶段已经解决了什么
2. 还存在哪些功能、性能和交互缺口
3. 下一步应该按什么优先级完善

评审范围主要基于以下实现：

- `agentGui/Views/MarkdownMessageView.swift`
- `agentGui/Views/AgentAnswerCardView.swift`
- `agentGui/Views/FileEditorView.swift`

当前实现已经具备一个很好的基础：

- 支持标题、分割线、表格、代码块、Mermaid
- 普通文本通过 `AttributedString(markdown:)` 获得基础 inline markdown 能力
- 已加入块级 `Equatable` 和稳定 ID，避免 streaming 期间整棵 view 全量销毁重建

这意味着“能显示”和“不会每次全量重绘”这两个基础问题已经处理到位。但如果目标是把它作为 agent 消息和文件预览的长期 Markdown 渲染方案，当前版本仍然明显偏“轻量可用”，距离“完整、稳定、低开销”还有几步。

## 2. 当前实现的优点

### 2.1 结构简单，便于控制

当前不是把整个 Markdown 直接交给 WebView 或第三方重型渲染器，而是做了一个可控的块级解析器。这个方向是对的，因为 agent 场景对以下能力要求很高：

- 流式增量更新
- 对 Mermaid、代码块、表格做定制渲染
- 与 SwiftUI 卡片和消息 UI 深度融合

这类需求下，自定义块解析通常比黑盒渲染器更容易调优。

### 2.2 对 streaming 做了第一层优化

现在通过以下方式避免了最差情况：

- `ForEach` 不再使用 `UUID()` 作为 block id
- block view 使用 `.equatable()`，未变化的块可以跳过 body

这已经能显著降低“消息越长越卡”的程度，尤其适合 append-only 的流式输出。

### 2.3 特殊块支持方向正确

Mermaid 和代码块都做了专门 UI，而不是退化成普通文本。这对 agent 产品很重要，因为代码和图表不是边缘能力，而是主内容类型。

## 3. 还需要完善的核心问题

## 3.1 P0：当前仍然不是“真正的增量解析”

虽然渲染层已经避免了全量 view 重建，但 `parseBlocks(text)` 依然在每次 `text` 更新时从头扫描整篇内容。

这意味着当前优化只解决了“SwiftUI view diff”层的问题，没有解决“解析成本”本身的问题。文本一长，仍然存在以下固定成本：

- 整篇字符串重新按行分割
- 整体重新跑块识别逻辑
- 已完成块也会重新创建 `MarkdownBlock` 值
- 文本块在 `MarkdownBlockView` 中仍会重新走 `AttributedString(markdown:)`

在 agent streaming 场景下，最理想的模型不是“每次全量 parse，再局部 render”，而是：

- 复用上一版已经解析完成的 block 列表
- 只对新增尾部文本重新解析
- 仅替换最后一个未完成 block，或追加新 block

### 建议

引入一个独立的 `MarkdownBlockCache` / `MarkdownIncrementalParser`：

- 输入：上一次文本、上一次 blocks、本次文本
- 输出：尽量复用的 blocks 列表
- 优先支持 append-only 路径
- 对非 append 的全文编辑退回全量解析

这是后续性能优化里收益最高的一步。

## 3.2 P0：块索引 ID 适合 streaming，但不适合通用编辑

当前用 `enumerated().offset` 作为稳定 ID，对“只在末尾追加文本”的聊天 streaming 很有效，但它有一个明确边界：

- 如果正文中间插入或删除一段，后续所有 block 的 index 都会变
- SwiftUI 会把后面的块都视为“身份变化”
- 文件预览模式下，编辑 `.md` 时这种情况很常见

也就是说，现在的 ID 策略是“为聊天流式场景优化的近似稳定”，不是“通用稳定”。

### 建议

后续可以把 block id 改成更稳的组合键，例如：

- `kind + startLine + endLine + contentHash`
- 或者 parser 在增量复用时沿用旧 block 的 identity

这样在文件预览和普通编辑场景下会更稳，不会因为前文插入导致后文全部重建。

## 3.3 P0：Markdown 语法覆盖面仍然明显不足

当前支持的块类型只有：

- 标题
- 分割线
- 代码块
- 表格
- 普通文本

这对于 agent 回复里的很多真实内容还不够。当前至少缺少以下常用块级语法：

- 无序列表
- 有序列表
- 任务列表
- 引用块
- 嵌套列表
- 代码块外的缩进内容

这些内容目前大多会落到 `.text` 分支里，被当成普通段落显示，导致结构信息丢失。

### 建议

按以下顺序补齐：

1. 无序列表 / 有序列表
2. 引用块
3. 任务列表
4. 嵌套列表

这是最直接影响“可读性正确性”的一组能力。

## 3.4 P1：Inline markdown 的一致性和能力还不够可控

当前 inline 渲染完全依赖 `AttributedString(markdown: options: .inlineOnlyPreservingWhitespace)`。这个方案的优点是实现简单，但也有几个问题：

- 链接样式、点击行为、hover 状态不可控
- 图片语法通常不会按预期变成可交互图片
- 删除线、行内代码、自动链接等细节能力受系统实现限制
- 当同一个 text block 高频变化时，`AttributedString(markdown:)` 本身有额外开销

### 建议

分两步做：

1. 短期继续保留 `AttributedString`，但给 text block 增加缓存，避免未变化内容重复构造富文本
2. 中期对常用 inline token 做自定义轻量解析，至少接管：
   - 行内代码
   - 链接
   - 粗体 / 斜体
   - 删除线

不是所有 inline 语法都要自己实现，但高频和高可控性的部分应该逐步收回来。

## 3.5 P1：代码块缺少语义增强

当前 `CodeBlockView` 已经有复制按钮，但仍然偏“纯文本容器”，还缺少以下能力：

- 语法高亮
- 长代码块折叠
- 行号
- 一键复制时的视觉反馈优化
- 对 diff / shell / json / swift 这类常见语言做更强视觉区分

在 agent 产品里，代码块不是附件，而是正文的一部分。当前样式足够可用，但不够强。

### 建议

优先级建议：

1. 行号和语言 badge 规范化
2. 基础语法高亮
3. 超长代码折叠

如果后续要承接 patch / diff 展示，还要单独支持增删行颜色和 chunk header。

## 3.6 P1：表格能力偏基础，复杂表格表现会失真

当前表格实现适合简单 GFM 表格，但边界还比较多：

- 没有处理转义竖线
- 没有处理单元格内复杂 inline 内容
- 对列宽没有策略，长内容容易把表格拉得很宽
- 表头、对齐、空单元格容错仍偏简化

### 建议

短期不要追求完整 CommonMark 表格能力，但至少应补齐：

- 转义 `\|` 处理
- 单元格内 inline markdown 渲染
- 更稳的列宽与换行策略

否则 agent 输出稍复杂的对比表后，易出现结构错位。

## 3.7 P1：Mermaid 渲染还缺少失败兜底和生命周期控制

Mermaid 现在已经能显示，但还可以继续补强：

- 渲染失败时缺少明确错误态
- 宽度是本地 state，消息重绘时可能和用户预期不一致
- 大图 / 复杂图表的性能和高度策略还比较固定
- 没有导出图片、复制源码等更完整操作

### 建议

至少增加两类兜底：

- 解析失败时显示错误信息和源码
- 超大图自动切换为“源码优先”或懒加载模式

## 3.8 P1：流式状态下的视觉反馈还可以更明确

当前 streaming 时，最后一个 block 会频繁增长，但 UI 并没有明确表达“这个块还没结束”。

例如这些场景：

- 正在输出一个尚未闭合的代码块
- 正在输出表格分隔行之前的表头
- 正在输出引用块 / 列表但尚未结束

用户现在只能靠文字猜测这是“未完成内容”，系统没有显式提示。

### 建议

可以考虑给最后一个正在增长的 block 增加弱提示：

- 轻微 shimmer / caret
- “生成中”尾标
- 对未闭合 fenced code block 显示临时状态

这样流式体验会更自然。

## 3.9 P2：缺少系统化测试，后续迭代容易回归

目前这类 parser 非常依赖样例覆盖，否则一旦补语法，很容易出现互相影响：

- 表格误判为普通文本
- 分割线误判为二级标题
- 未闭合代码块破坏后续段落解析
- streaming 半成品文本与最终文本的解析结果不一致

### 建议

补一套以“输入 markdown -> block 序列” 为核心的测试：

- 正常输入测试
- 边界输入测试
- 流式追加测试
- 回退到全量解析的测试

如果不补测试，这块后面会越来越难改。

## 3.10 P2：可访问性和交互细节还没形成统一规范

当前大多数块都能显示，但对以下细节没有统一标准：

- 链接是否可点击、是否能打开外部资源
- 键盘导航顺序
- VoiceOver 朗读语义
- 复制整段 / 复制代码 / 复制图表的交互一致性

这些不是当前最急的问题，但如果 Markdown 成为消息主渲染方案，迟早要补。

## 4. 推荐的落地顺序

建议不要同时追语法完整性和复杂视觉，而是按下面顺序推进。

### 第一阶段：先把性能根问题补上

目标：让长消息和 streaming 下的渲染成本继续下降。

建议项：

1. 增量 parser / block cache
2. text block 的 attributed string 缓存
3. 更稳定的 block identity

### 第二阶段：补最常见的语法正确性

目标：让 agent 常见输出不再“结构丢失”。

建议项：

1. 无序列表 / 有序列表
2. 引用块
3. 任务列表
4. 单元格 inline markdown

### 第三阶段：补内容类型体验

目标：让代码、图表、表格从“能看”变成“好看、好用”。

建议项：

1. 代码高亮与行号
2. Mermaid 错误态与懒加载
3. 表格宽度策略优化

### 第四阶段：补测试与交互一致性

目标：让这套渲染器可持续迭代。

建议项：

1. parser 单元测试
2. streaming 增量测试
3. 复制、链接、辅助功能规范化

## 5. 结论

当前 `MarkdownMessageView` 已经从“全量重建”的低效状态，进入了“基础可用、可继续演进”的阶段。但它离一个成熟的 agent Markdown 渲染器还有三个明显差距：

1. 解析仍是全量，不是真正的增量解析
2. 语法覆盖面不足，列表 / 引用 / 任务列表等常见结构会丢失
3. 代码、表格、Mermaid 等高价值内容类型还缺少更强的语义和交互支持

如果只看短消息，它已经够用；如果把它当作 agent 主消息渲染层和 Markdown 文件预览层的长期方案，下一步最值得投入的是：

- 先做增量 parser / 缓存
- 再补列表和引用
- 然后补代码块与表格体验

这是当前投入产出比最高的一条路线。
