# agentGui User Message 内联引用与命令上下文 UI 需求文档

日期：2026-03-11

## 1. 背景

当前 user message 在消息列表中的展示仍然是纯文本输出，和输入区已经具备的结构化交互不一致：

- `@` 引用：输入区支持候选列表和高亮，但发送后最终只以普通文本写入消息内容。
- `/` 命令：输入区会将 slash command 转换为 directive chip，但写入消息时只保留一段审计尾注文本，例如 `[Active directives] skill=brainstorming`。

这会带来两个直接问题：

1. 用户在输入阶段感知到的是“结构化上下文”，发送后却退化为“不可识别的字符串”。
2. 消息回看时无法快速判断本次提问引用了哪些文件、启用了哪些命令上下文，也无法与普通正文形成视觉分层。

结合当前实现，问题主要发生在以下链路：

- `MessageBubbleView` 对 user message 使用 `Text(content.text)` 直接渲染正文。
- `expandMentions` 会把正文中的 `@relative/path` 扩展成绝对路径字符串。
- `ChatInputDirectiveAudit.appendAuditTrail` 会把 directive 以纯文本尾注追加到消息末尾。

因此，这次需求不是单纯“给文本换个颜色”，而是要为 user message 建立一套可识别、可回看、可兼容历史数据的结构化展示规则。

## 2. 问题定义

### 2.1 当前体验问题

#### P0: `@` 引用不可辨识

- 在消息回放区，文件引用与普通文字没有清晰边界。
- 当 `@` 被展开为绝对路径后，可读性明显下降，尤其在长路径场景下会挤占正文空间。
- 同一条消息如果包含多个引用，用户几乎无法快速扫读出“本次提问到底引用了哪些文件”。

#### P0: `/` 命令语义丢失

- slash command 在发送前已经转成 directive，但发送后只保留审计文本，用户看不到“这是命令上下文”这一层语义。
- `[Active directives] ...` 作为普通尾注混在正文里，既影响阅读，也不符合命令上下文的视觉预期。

#### P1: 输入态与回看态断层

- 输入区已有 mention popup、slash popup、directive chip 等结构化组件。
- 消息区没有对应的展示映射，导致用户对“我刚刚发送了什么上下文”缺少稳定反馈。

#### P1: 历史消息兼容性不足

- 现有数据模型中，user message 只有 `textContent`，并没有单独存储 mention 列表或 directive 列表。
- 新方案如果完全依赖新字段，会导致历史消息仍旧是纯文本，体验割裂。

## 3. 目标

### 3.1 产品目标

1. 让 user message 中的 `@` 引用在阅读上具备清晰的“文件上下文”语义。
2. 让 `/` 命令对应的 directive 在消息回看时具备清晰的“已启用命令上下文”语义。
3. 保持 user bubble 的紧凑、右对齐设计，不引入 agent message 那种重卡片和复杂时间线。
4. 对历史消息提供解析兼容，保证老数据也能获得结构化展示。

### 3.2 设计目标

1. 正文仍然是 user bubble 的第一阅读目标。
2. 引用和命令上下文要比正文更轻，但必须比普通文字更容易识别。
3. 同一条消息中的结构化元素应采用统一的视觉语言，避免一个像标签、一个像日志。

## 4. 非目标

本次需求不包含以下内容：

1. 不重做 agent message 的展示层。
2. 不修改 slash command 的输入交互逻辑。
3. 不新增复杂的富文本编辑能力。
4. 不要求首版支持在消息气泡内直接编辑 mention 或 directive。

## 5. 用户场景

### 场景 A: 文件引用型提问

用户输入“请检查 @agentGui/Views/MessageBubbleView.swift 里的 user message UI”，发送后消息区应能一眼看出这条消息引用了一个文件，而不是显示一整段难读的绝对路径。

### 场景 B: 命令上下文型提问

用户通过 `/brainstorming` 选择一个技能，然后输入需求。发送后消息区应能看出本次提问启用了某个命令上下文，而不是在正文底部看到一行审计字符串。

### 场景 C: 混合型提问

用户同时使用 slash command 和多个 `@` 文件引用。消息区应同时表现“这条消息带了哪些命令上下文”和“正文里引用了哪些文件”，且不破坏主体阅读节奏。

## 6. 需求范围

### 6.1 `@` 引用展示

user message 中识别出的文件引用需要以结构化 token 展示，而不是普通文本。首版需求如下：

1. 在正文内部保留原句顺序，但将可识别的引用片段渲染为 inline token。
2. token 至少包含文件图标、主标签、辅助路径信息三部分。
3. 主标签优先显示文件名，辅助信息显示相对路径；若无法还原相对路径，则显示裁剪后的绝对路径。
4. token 视觉上应明显区别于正文，但权重低于输入区的可操作 chip，避免喧宾夺主。
5. token 支持 hover 态，hover 时显示完整路径。
6. token 首版不强制支持点击跳转，但组件设计应预留点击行为扩展位。

### 6.2 `/` 命令对应 directive 展示

slash command 在消息区不应继续以审计尾注文本直接裸露，而应转成“命令上下文行”展示。首版需求如下：

1. 从 user message 文本中提取 `[Active directives] ...` 尾注。
2. 将尾注从正文中剥离，改为显示在 user bubble 顶部或正文上方的轻量 chip 行。
3. 每个 directive 使用统一的 command/context chip 表达，目前至少支持 `skill` 类型。
4. `skill` directive 的展示文案优先使用 display name，其次回退到 directory name。
5. 正文复制时默认保留原始文本内容不变，纯展示层不改变消息持久化值。

### 6.3 兼容历史消息

首版必须兼容现有落盘格式，不要求先完成数据模型改造：

1. 对旧消息，通过解析正文中的绝对路径和尾注文本恢复结构化展示。
2. 若解析失败，界面回退为原始文本，不得丢失内容。
3. 新旧消息在视觉风格上保持一致，不出现“新消息有 chip、旧消息只有日志尾注”的明显断层。

## 7. 信息架构与展示规则

### 7.1 User Bubble 建议层级

建议 user bubble 从单层文本改成三层结构：

1. 命令上下文层：展示 directive chips，仅在存在 directive 时出现。
2. 正文层：展示普通文本与 inline mention token 的混排内容。
3. 附件层：沿用现有图片、PDF、其他引用文件展示。

其中正文层仍是主层，命令上下文层是弱提示层，附件层保持现有逻辑。

### 7.2 `@` Token 规则

建议采用接近“内联文件卡片”的轻量样式，而不是纯文本高亮：

- 图标：沿用现有 `fileIcon(for:)` 逻辑，保证与输入区和工作区图标一致。
- 主文案：显示 `lastPathComponent`。
- 副文案：显示相对路径；如果只有文件名，则省略副文案。
- 容器：小圆角、弱描边、轻底色，颜色跟随 accentColor 但透明度较低。
- 排版：与正文基线对齐或近似对齐，允许在长消息中换行包裹。

### 7.3 Directive Chip 规则

directive 展示建议复用输入区 chip 语言，但弱化可操作感：

- 使用 `command` 图标作为统一前缀。
- `skill` 类型显示为“Skill: brainstorming”或更本地化的“技能: brainstorming”。
- 不显示删除按钮，因为消息区是回看态，不是编辑态。
- 多个 directive 横向排列并支持换行。

### 7.4 文本解析规则

为了兼容现有数据格式，展示层需要把 user message 文本拆成以下几部分：

1. 主正文
2. directive 审计尾注
3. `Referenced files` 附件段
4. 正文内部可识别的 mention 引用

解析顺序建议为：

1. 先剥离 `Referenced files` 段，复用现有逻辑。
2. 再剥离 `[Active directives] ...` 审计尾注。
3. 最后对剩余正文做 mention tokenization。

这样可以避免把附件路径和 directive 尾注误识别为正文中的 inline token。

## 8. 数据与实现约束

### 8.1 当前约束

当前 `Message` 模型没有独立字段存储：

- mention 列表
- directive 列表
- 已解析的正文片段

因此首版必须在展示层做派生解析。

### 8.2 推荐演进方向

为避免长期依赖字符串解析，建议分两阶段推进：

#### 阶段一: 展示兼容

- 不改持久化结构。
- 通过 message text parser 兼容历史与现有消息。
- 优先完成 UI 可读性改造。

#### 阶段二: 结构化持久化

- 在 `Message` 或独立展示模型中补充 parsed metadata。
- 发送时同步记录 directives、mentions、attachments 的结构化信息。
- 展示优先使用结构化数据，字符串解析作为回退路径。

## 9. 交互要求

### 9.1 Hover 行为

1. mention token hover 时显示完整路径。
2. directive chip hover 时显示更完整的命令说明，例如目录名、原始 auditDescription。

### 9.2 Copy 行为

1. 复制消息时，默认复制原始 `textContent`，保证与模型输入一致。
2. 纯展示用的 chip 和 token 不应改变复制结果。

### 9.3 Edit 行为

1. user message 进入编辑态时，仍回退到原始纯文本编辑模式。
2. 不要求在编辑器中保留可视化 token。
3. 编辑后重新发送仍沿用当前发送链路。

## 10. 验收标准

### 10.1 功能验收

1. 包含 `@` 引用的 user message 在消息列表中不再以单纯路径字符串显示，而是以可识别的 inline token 显示。
2. 包含 directive 审计尾注的 user message 不再在正文底部裸露 `[Active directives] ...` 文本，而是以 command chip 形式单独展示。
3. 同一条消息同时包含 mention、directive、附件时，三类信息不会混淆。
4. 不含 mention 和 directive 的普通消息，其样式与现有 user message 基本一致。
5. 历史消息能自动获得同样的展示规则；解析失败时不会丢字或崩溃。

### 10.2 视觉验收

1. user bubble 整体仍保持紧凑、右对齐、轻量的视觉风格。
2. mention token 和 directive chip 的视觉体系统一，但能区分“正文内联元素”和“消息上下文标签”。
3. 在窄宽度下换行表现稳定，不出现 token 截断、文本溢出或高度跳变异常。

### 10.3 测试验收

建议新增以下测试覆盖：

1. 纯文本 user message 的解析回归测试。
2. 含单个 mention 的解析测试。
3. 含多个 mention 的解析测试。
4. 含 directive 尾注的解析测试。
5. directive 与 `Referenced files` 共存时的解析顺序测试。
6. 编辑态与复制行为测试。

## 11. 风险与注意事项

### 11.1 绝对路径识别风险

由于 mention 在发送前会被扩展成绝对路径，展示层如果只基于字符串正则识别，可能会把普通绝对路径误判为引用 token。为降低风险，建议：

1. 优先只识别位于工作区根目录下的路径。
2. 仅在文件真实存在时转成 token。
3. 不能确认语义时回退为普通文本。

### 11.2 历史数据格式风险

审计尾注和正文目前共存在 `textContent` 中，未来如果审计格式变化，解析器也需要同步维护。因此阶段二的结构化存储应尽早推进。

## 12. 建议的实施优先级

### P0

1. user message 文本解析器：拆分正文、directive 尾注、附件段。
2. user bubble 中的 directive chip 行。
3. user bubble 正文中的 mention inline token。

### P1

1. mention token hover 完整路径。
2. directive chip hover 补充说明。
3. 解析与渲染单元测试。

### P2

1. 点击 token 打开文件。
2. 结构化 metadata 持久化。
3. 更丰富的 directive 类型展示。

## 13. 结论

这次优化的核心，不是把 `@` 和 `/` “染色”，而是把它们从普通文本提升为 user message 中可识别的上下文对象。

对 `@` 来说，目标是让文件引用回归可读、可扫视、可扩展的内联上下文。

对 `/` 来说，目标是让命令上下文从审计日志文本升级为稳定的消息元信息展示。

在不立即改动底层持久化模型的前提下，首版应优先通过展示层解析完成体验收敛，并为后续结构化存储预留演进空间。
