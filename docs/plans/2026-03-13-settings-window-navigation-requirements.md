# agentGui 设置独立窗口与分类导航需求文档

日期：2026-03-13

## 1. 背景

当前应用把“设置”作为主窗口中的一个 Tab 放在 `ContentView.swift` 里，与“对话”“Skills”“诊断”并列。这种实现虽然直接，但已经暴露出三个明显问题：

1. 设置是全局配置，不属于会话级工作流，却长期占据主工作区一级导航。
2. `SettingsView` 承载了 API、代理、模型、工具、推理、记忆、关于等大量内容，单页表单过长，信息密度过高。
3. 设置视图和主窗口结构耦合在同一个文件中，导致窗口职责、导航语义和视图拆分都不清晰。

结合当前代码，现状主要表现为：

1. `ContentView` 通过 `TabView` 直接承载 `SettingsView`。
2. `SettingsView` 使用一个长 `Form` 串联所有设置分组，没有二级导航。
3. UI 测试通过 `-com.agentgui.test.initialTab settings` 直接启动到设置页，这意味着移除 Settings Tab 后需要同步调整测试入口。

因此，这次需求不是简单地“把视图弹成一个 sheet”，而是要把设置体系改造成一个独立窗口，并按设置类型建立稳定的导航信息架构。

## 2. 问题定义

### 2.1 当前体验问题

#### P0: 设置与主工作流混在同一级导航

“设置”作为主 Tab 出现在聊天工作区中，会让全局配置和高频工作流竞争一级导航位置。对 macOS 用户来说，这也不符合“设置属于独立窗口”的平台习惯。

#### P0: 单页表单过长，查找成本高

当前设置页把连接、代理、工具、LSP、推理、记忆、关于全部放在一个页面里。随着配置项继续增长，用户需要长距离滚动，难以快速定位具体配置域。

#### P1: 视图职责不清晰

`ContentView.swift` 既管理主界面 Tab，也包含完整的 `SettingsView` 和 `SkillsView` 实现。后续一旦要扩展设置导航或引入新的设置入口，维护成本会持续上升。

#### P1: 自动化测试入口依赖旧导航结构

现有 UI 测试默认通过选中 `settings` Tab 验证设置页显示。设置改成独立窗口后，如果没有新的测试入口和稳定的 accessibility 标识，回归测试会失效。

## 3. 目标

### 3.1 产品目标

1. 将设置从主窗口 Tab 中移出，改为独立设置窗口。
2. 在设置窗口中按设置类型提供清晰的导航项，降低查找与切换成本。
3. 保持所有现有设置能力可达，不因窗口拆分而丢失配置项。
4. 让新的设置入口符合 macOS 常见交互预期。

### 3.2 设计目标

1. 设置窗口应是全局配置中心，而不是聊天流程中的一页内容。
2. 一级导航项应围绕“配置领域”划分，而不是沿用当前实现中的随机 Section 顺序。
3. 设置详情页保留现有表单输入范式，优先做信息架构调整，而不是同时重做视觉系统。

## 4. 非目标

本次需求不包含以下内容：

1. 不重做各个设置控件的视觉皮肤。
2. 不修改 `AppSettings` 的持久化模型字段。
3. 不把所有设置都强行并入现有 `SkillsView` 或其他业务页。
4. 不顺带改造设置项背后的业务逻辑，例如代理实现、LSP 注册逻辑、统一记忆运行时逻辑。

## 5. 用户场景

### 场景 A: 首次配置连接能力

用户首次启动应用后，需要快速找到 API Key、Base URL、模型与代理配置。新的设置窗口应提供明确入口，并在“连接”类导航项下集中呈现这些内容。

### 场景 B: 调整工具开关

用户需要启用 Bash、Web Search 或 LSP 时，不应在一个超长表单里反复滚动查找，而应直接进入“工具”导航项。

### 场景 C: 调整记忆或推理策略

用户希望修改统一记忆运行时、TTL Sweep、Extended Thinking 或反思阈值时，应能在独立的“智能”或“记忆”导航页中完成，而不是和连接配置混杂在一起。

### 场景 D: 从主工作区进入设置

用户在聊天过程中需要修改配置时，应能通过系统标准入口或应用内可发现入口打开设置窗口，而不是被迫切换主窗口 Tab。

## 6. 需求范围

### 6.1 窗口形态

1. 设置必须从主窗口 `TabView` 中移除，不再作为 `AppTab.settings` 出现。
2. 设置必须以独立窗口承载，并支持重复打开时复用同一个设置窗口实例，而不是不断创建新窗口。
3. 设置窗口应遵循 macOS 平台习惯，至少支持系统级“设置...”入口和快捷键入口。
4. 若移除主窗口中的设置 Tab，需要提供一个应用内可发现入口，避免设置只能从菜单访问。

### 6.2 导航结构

设置窗口首版需要提供基于类型的一级导航，推荐至少拆分为以下 5 个导航项：

1. 连接
2. 工具
3. 智能
4. 记忆
5. 通用

各导航项的内容范围如下。

#### 连接

包含：

1. Anthropic API Key
2. Base URL
3. 模型选择
4. 代理配置
5. 连接状态

#### 工具

包含：

1. 文本编辑器工具开关
2. Bash 工具开关与工作目录
3. Web Search 与 Ollama Web Search 配置
4. Web Fetch 开关
5. LSP 开关、自动启动、默认路由策略、自定义 Profile JSON

#### 智能

包含：

1. Extended Thinking 开关与预算
2. 反思与自我修正开关与阈值

#### 记忆

包含：

1. 统一记忆运行时开关
2. 上下文预算
3. 记忆治理与统一写路径
4. 后台巩固与调度周期
5. TTL Sweep 与调度周期
6. 待确认阈值
7. 长期记忆编辑器
8. 打开记忆治理面板入口

#### 通用

包含：

1. 主题模式
2. 版本信息
3. AI 服务信息

说明：`SkillsView` 继续保留在主窗口，不作为本次设置窗口重组的必选范围。后续如果希望把“启用的 Skills”并入设置，可单独增加“技能”导航项，但不纳入本期必做。

### 6.3 详情页行为

1. 各导航项详情页应继续沿用当前 `Form` 为主的录入方式，降低迁移风险。
2. 详情页中已有的即时保存行为应保持一致，不要求引入统一“应用全部”按钮。
3. 只有与当前导航项相关的设置才应出现在该页面，避免跨域混放。
4. 长文本输入区域，如 LSP JSON 和长期记忆编辑器，应保留足够的编辑高度。

### 6.4 入口与可发现性

1. 设置窗口必须支持系统菜单“设置...”入口。
2. 应支持 `Command + ,` 快捷键打开设置。
3. 主窗口中应提供一个明显但不打断主流程的入口，例如 toolbar 按钮或统一命令入口。
4. 从应用内入口打开设置时，应默认落在上次访问的导航项；如果无历史状态，则默认落在“连接”。

### 6.5 状态与持久化

1. 现有 `AppSettings` 字段不变，继续作为唯一持久化来源。
2. 导航切换只影响展示结构，不改变设置保存机制。
3. 设置窗口关闭后再次打开，应保持最近一次选中的导航项，除非显式重置。

## 7. 信息架构建议

### 7.1 窗口结构

推荐采用左右结构：

1. 左侧为设置导航列表。
2. 右侧为当前导航项的详情页。

这样可以承接后续设置项继续增长的情况，比单页滚动表单更稳定。

### 7.2 导航排序

建议按照使用频率与认知路径排序：

1. 连接
2. 工具
3. 智能
4. 记忆
5. 通用

优先把“首次可用性”和“运行时行为”相关项放前面，把主题和版本等低频配置放后面。

### 7.3 命名原则

一级导航项名称需要短、稳定、面向用户心智，而不是直接复用内部模型名。比如：

1. 使用“智能”而不是“Extended Thinking / Reflection”。
2. 使用“连接”而不是“Anthropic API 配置”。
3. 使用“通用”而不是“关于”，避免出现一个只承载版本信息的孤立页面。

## 8. 实现约束

### 8.1 当前代码约束

1. `ContentView.swift` 当前同时包含 `ContentView`、`SettingsView`、`SkillsView`，职责耦合较重。
2. `TestLaunchOptions` 仍以 `AppTab` 为启动路由依据，设置窗口改造后需要补充新的测试打开方式。
3. `agentGuiApp.swift` 当前只有主 `WindowGroup`，尚未声明专门的设置场景。

### 8.2 推荐实现方向

1. 使用专门的设置场景承载独立窗口，而不是在主窗口中临时弹出 sheet。
2. 将设置窗口拆成独立目录和多个子视图，避免继续把所有实现留在 `ContentView.swift`。
3. 把各导航项的视图和复用的保存辅助逻辑抽离为独立组件，减少跨页面复制粘贴。

## 9. 测试要求

### 9.1 单元与集成测试

建议至少覆盖：

1. 设置导航枚举的默认项与排序。
2. 设置窗口默认打开项逻辑。
3. 各详情页对 `AppSettings` 的绑定与持久化行为不回退。
4. 连接、工具、记忆等核心页面在拆分后仍能加载原有默认值。

### 9.2 UI 测试

必须补足：

1. 从设置入口打开独立窗口。
2. 默认显示“连接”页并出现 API Key 输入框。
3. 导航切换到“工具”“记忆”等页面时，能看到对应控件。
4. 移除主窗口设置 Tab 后，原有 UI 测试应更新或替换，不得继续依赖 `initialTab = settings`。

## 10. 验收标准

### 10.1 功能验收

1. 主窗口不再显示“设置”Tab。
2. 应用可以通过标准入口打开独立设置窗口。
3. 设置窗口包含按类型划分的一级导航项。
4. 现有设置项全部可在新的分类页面中访问和保存。
5. 关闭并重新打开设置窗口时，不会丢失保存结果。

### 10.2 体验验收

1. 用户可以在 2 次导航操作内定位任一常用设置项。
2. 设置页不再需要长距离滚动才能跨域查找配置。
3. 新窗口形态符合 macOS 应用的常见设置习惯。

### 10.3 回归验收

1. 聊天、Skills、诊断主流程不因移除 Settings Tab 受损。
2. 现有设置保存逻辑仍可正确写入 `AppSettings`。
3. UI 测试在新入口下可稳定运行。

## 11. 风险与注意事项

### 11.1 入口缺失风险

如果只删除主窗口 Settings Tab，却没有补上明显入口，设置会变成“存在但难以发现”的隐藏能力。因此入口设计必须与 Tab 移除同步完成。

### 11.2 视图拆分回归风险

当前 `SettingsView` 和 `SkillsView` 与 `ContentView` 共处一文件，拆分时容易带入环境依赖、私有辅助方法和状态变量的回归问题。应先明确哪些是设置窗口共享逻辑，哪些属于单个详情页。

### 11.3 UI 测试稳定性风险

设置改成独立窗口后，测试不再能通过切换 Tab 进入页面，必须提前设计新的测试打开方式和稳定的 accessibility 标识，否则会造成较大回归成本。

## 12. 建议实施优先级

### P0

1. 建立独立设置窗口场景与打开入口。
2. 从主窗口移除 Settings Tab。
3. 建立设置导航枚举与左右分栏布局。
4. 完成“连接”“工具”“记忆”三类页面迁移。

### P1

1. 完成“智能”“通用”页面迁移。
2. 保存最近访问导航项。
3. 补齐 UI 测试和启动参数适配。

### P2

1. 评估是否把 Skills 启用管理并入设置窗口。
2. 统一设置页面的复用组件和更细的视觉优化。
